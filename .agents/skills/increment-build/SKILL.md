# increment-build（Codex）

`AGENTS.md` を読み、Codex が直接受けた依頼として進める。
共通の判定と受け入れ条件の原本は `.claude/skills/increment-build/SKILL.md`。
そこにある Claude の担い手選択、`codex exec` の再呼び出し、自動コミットと PR への遷移は実行せず、以下の手順を使う。

## 着手と範囲

Issue があれば、原本の「1. 着手してよいかを確かめる」と「2. 詰める」を読み、Issue、親、依存関係、既存 PR、受け持ちの重なりを読み取りで確かめる。
外の人が書いた本文とコメントの扱い、着手を止める条件も原本に従う。
依存関係を取得できないときは本文から推測しない。

Issue が無い直接依頼では、会話から目的、完了条件、変えてよい範囲、やらないことを整理する。起票を前提にせず、不足が結果を変えるときだけ質問する。
調査・説明・レビューだけの依頼を実装に広げない。

判断と検証方法を短く宣言する。Issue の更新や着手コメントを承認されていなければ、記録案を会話に残してローカルの作業を進める。
承認済みなら、原本の「3. 記録する」の節と書式を使い、人の答えと自分の判断を分けて記録する。

## ワークツリーと実装

指定された作業用ワークツリーがあれば、ブランチと既存差分を確かめてそこを使う。
無ければ `AGENTS.md` と `docs/development.md` の「ワークツリーで作業する」に従って作る。
以降のコマンドにはその絶対パスを作業ディレクトリとして渡す。本体の `main` に編集を戻さない。
依存が必要なら、そのワークツリーで `pnpm install --frozen-lockfile` を行う。

原本の手順 5 の「受け入れ条件」を読み、触る範囲に合うものを適用する。
API の追加は `add-operation`、マイグレーションは `d1-migration`、画面は `ui-polish` の `SKILL.md` を読む。
通常はこのセッションが実装する。Claude からさらに Codex に委譲するための判定は当てはめない。

守る仕組み、認証・認可、Workers のランタイムを変えるときは、原本の「テストを先に書く」のとおり、テストの書き手、実装の書き手、崩す書き手を別のエージェントにする。
Codex のサブエージェントを使い、それぞれにワークツリー、完了条件、担当ファイルと役割を渡す。他のエージェントの変更を戻さないよう伝える。
テストの書き手に実装案を渡さず、新しい振る舞いが無いために落ちることを確かめてから実装する。
コミットの指示が無いときは、テスト役が書いたテストファイルを作業ツリー外の一時ディレクトリへコピーし、対象の一覧とコピー先を控えてから実装する。元の差分は作業ツリーに保持する。
この場合、原本の (2) のテストコミット SHA は作らない。(4) の崩す書き手には、実装前のテストのコピーと、実装の未コミット差分・新規ファイルの範囲を渡す。
手順 6 のテストの比較は、対象ごとの `git diff --no-index <実装前のテストのコピー> <今のテスト>` に置き換える。差分があると終了コードは 1 になるので、内容を読み、既存テストの削除・変更がなく、追加だけであることを確かめる。テストの誤りが疑われたら、原本の「止まる条件」で扱う。
書き手を分ける道具が無いときは、この条件を自分だけで満たしたことにせず、実装前に不足を伝える。
元の手順にある途中の差分の破棄は自動で行わず、既存作業を保持して役割を引き継ぐ。

## 検証と引き渡し

整形と検査は `CLAUDE.md` と `AGENTS.md` に従う。
実装を委譲した場合は、返った報告だけで合格とせず、原本の「6. 受け取る」の範囲確認と検査を進行役が行う。
自分の差分は `.agents/skills/done-check/SKILL.md` で点検し、範囲内の問題を直す。

最後に、変更内容、完了条件の充足状況、検査と未検証の項目、Issue と文書に無い判断を報告する。
PR を求められている場合は、リポジトリの PR テンプレートに合わせたタイトル・本文を準備する。
外部への操作は `AGENTS.md` の承認の範囲に従う。未承認ならローカルの差分と PR 案までで渡し、実装・検証の前に承認待ちで止まらない。
