# DB（Cloudflare D1）

表と列の決まりは `docs/data-model.md` の「決まりごと」。ここには、外れたときに指摘する項目を置く。

## クエリ

- WHERE や JOIN に使う列にインデックスが無い。外部キーにインデックスが無い
- 複合インデックスの列順が、等価条件の列より範囲条件の列が先になっている
- 論理削除のある表の一覧のインデックスが、`deleted_at IS NULL` の部分インデックスになっていない
- 大きな表で OFFSET を使ったページングをしている（`WHERE id > ?` のカーソル方式にする。`id` は UUIDv7 なので作成順に並ぶ）
- 本番のコードでの `SELECT *`
- 利用者向けの一覧に `LIMIT` が無い
- 値を文字列連結で SQL に入れている（`prepare()` と `bind()` で渡す）
- 1つの文に多くの値をバインドしている（`IN (?, ?, ...)` に件数の決まらない配列を並べる）。D1 は1つの文でバインドできる数に上限がある。分割するか、JSON にして `json_each` で展開する
- 日時と日付を、決まった形（UTC の ISO 8601、`YYYY-MM-DD`）以外の文字列と比べている。文字列の比較なので、形が揃っていないと順序が壊れる

## スキーマ

- 決まりごとから外れている（主キーが UUIDv7 の `TEXT` でない、日時の列名が `_at` で終わらない、日付や月や JSON や列挙に CHECK が無い、真偽が `is_` で始まらない）
- 金額を `REAL` で持っている（最小単位の整数で `INTEGER` に持つ）
- NOT NULL、外部キー、CHECK を付けられるのに付けていない
- `ON DELETE` を付けている（付けない決まり。物理削除はアプリが順に行う）
- 論理削除があるのに、ユニーク制約が削除済みの行を考慮していない（部分ユニークインデックスにする）
- 本文やコメントの列に `CHECK (length(x) <= 100000)` が無い
- 集計（積載量、経験値の合計、ポイントの合計、ベロシティ）を列に保存している（読むたびに計算する決まり）

## マイグレーション

- 既にあるマイグレーションのファイルを書き換えている（新しいファイルを足す）
区分（広げる、値を広げる、縮める）と手順は `d1-migration` の「広げる変更と縮める変更」。

- 縮める変更と、それを使わなくするか新しい制約を守るようにするコードの変更が、同じ版に入っている。1つ前の版のコードに戻すと、消えた列を読むか新しい制約に当たる行を書いて動かない
- 値を広げる変更（列挙に値を足す、`NOT NULL` を外す、CHECK や UNIQUE を緩める）の新しい値を、その値を読めない古いコードが本番にあるうちに書いている
- 既にある表を指す外部キーを持つ表や列を足したのに、古いコードの親の物理削除が子の行で止まることを扱っていない
- 足した列を既にある行から埋めただけで、新しいコードがその列の空の行を扱えない
- 縮める変更を後に回したのに、縮める Issue（`migration` のラベル付き）が立っていないか、PR の本文から指されていない
- 縮める変更の PR に、1つ目の PR の版が本番に出て、今も対象を使っていないことを確かめた結果が無い
- `NOT NULL` の列を既定値なしで `ADD COLUMN` している
- マイグレーションの中で、表の作り直しの写し、足した列を既にある行から計算して埋める文、制約の前に行を整える文のほかに、行を書き換えている（決まった行の投入、開発用の値）。行を整える文の対象の行数と扱いが PR に無い
- 表の作り直しか、制約や一意の索引を足す変更を、行の入った D1 で確かめていない。一意や CHECK を足すのに、本番の既にある行が満たす理由が PR に無い
- SQLite の `ALTER TABLE` でできない変更（制約の追加と変更、列の型の変更）を、表の作り直し以外の方法で行っている
- 表の作り直しの後に `PRAGMA foreign_key_check` を確かめていない。末尾の `PRAGMA defer_foreign_keys = false` は手元ではそれまでの違反を数えずに通すので、写しで落とした行の子が黙って残る
- 表の作り直しで、張り直していない索引かトリガーがある（`DROP TABLE` で消える）
- 組織の中の表から共通の表へ、決まった列（`users.account_id` と、`users`、`workspaces`、`organization_holidays`、`change_logs` の `organization_id`）以外の外部キーか、共通の表から組織の中の表への外部キーがある
- スキーマを変えたのに `docs/data-model.md` が同じ差分で直っていない
- 本番のデータ量で時間のかかる変更（大きな表の作り直し、全行の更新）に、その旨の説明が無い

## 書き込みの単位

- まとめて書くべき文を、別々の `run()` で送っている（`batch()` で1回に送る。主な操作は `docs/data-model.md` の「書き込みの単位」）
- 先に読んだ値で判定してから書いているのに、書く文の `WHERE` に同じ条件が無い。影響した行の数（`meta.changes`）で競合を確かめていない
- 1回の `batch()` に、共通の表と組織の中の表を混ぜている
- 共通の表と組織の中の表を1つの SQL で結合している
- D1 と R2 の両方に書く操作で、途中で失敗したときの扱いが `docs/data-model.md` と違う（上げるときは R2 が先、消すときは D1 が先）
- ループの中で1行ずつ書いている（文を並べて `batch()` にする）
- 取り込み元の応答 JSON を、大きさを確かめずに1行に入れている（D1 の行の大きさに上限がある。大きすぎる分は切り詰める）
