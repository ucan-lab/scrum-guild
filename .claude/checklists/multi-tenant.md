# 組織の分離

全組織（顧客）が1つの D1 と1つの R2 のバケットに入る。組織をまたいでデータが見えることは、このサービスで一番重い事故として扱い、確信が低くても指摘する。決まりは `docs/data-model.md` の「決まりごと」と「データベースの分け方」、`docs/requirements.md` の「組織と運用者」。

## 絞り込み

- 組織の中の表の行を、ID だけで引いている、書き換えている、消している（`organization_id` か、組織を確かめた `workspace_id` で絞る）
- URL やリクエストの body に入った `workspace_id`、`epic_id`、`task_id` などを、リクエストの組織（URL の slug）のものか確かめずに使っている
- 親の ID を確かめたことを根拠に、子の ID を絞らずに使っている（`/workspaces/:w/tasks/:t` で `:w` を確かめても、`:t` が `:w` のものとは限らない）
- 組織の中の表を、組織の DB を選ぶ入口の関数を通さずに読み書きしている
- 組織をまたいで読む処理（ログインできるか、ログイン直後の組織の選択、届いた招待の一覧、初めてのログインでの `users.account_id` の補完）を、決まった1つの関数の外に書いている
- 一覧や集計で、組織の絞り込みが JOIN の片側にしか付いていない

## 入れるか

- 停止した組織に入れる。停止した組織の定期処理（取り込み、日をまたぐ処理）が止まっていない
- その組織の `users` が無効になった人や、ワークスペースから外れた人が、セッションが残っているだけで入れる（組織に入れるかはリクエストのたびに確かめる）
- 運用者が、管理者として指名されていない組織の中のデータを読める。運用者の画面に、決まった数値（ユーザー数、ワークスペース数、タスク数、添付ファイルの合計、最後に使われた日時）以外を出している

## 添付ファイル（R2）

- R2 のキーの先頭が組織の ID になっていない
- R2 のキーをリクエストから受け取って、そのまま読んでいる、消している（`attachments` の行を組織で絞って引き、そのキーを使う）
- バケットを公開して URL で配っている（Worker で権限を確かめてから返す）
- 容量の上限を組織ごとに数えていない

## 定期処理

- 組織ごとの処理で、1つの組織の失敗が他の組織の処理を止める
- 前の組織の値を持ち越して次の組織の処理に使っている（ループの外の変数、使い回しの配列）

## 状態を持つもの

- モジュールの最上位の変数や `Map` に、組織の中のデータを組織の ID を含まないキーで持っている（同じ isolate の別の組織のリクエストから見える）
- 取り込み元の認証情報を、組織とワークスペースで絞らずに引いている

## ログと応答

- ログに、本文、コメント、取り込んだ内容、認証情報、トークンを出している
- エラーの応答に、別の組織の行があることを示す情報を出している（他の組織の ID を指定したときは、存在しないときと同じ 404 にする）

## テスト

- 新しい API の操作に、別の組織の ID で呼ぶと 404 になることを確かめるテストが無い
- 組織の分離のテストが、同じ組織の中のデータだけで組まれていて、別の組織の行を用意していない
