この計画・設計のあらゆる側面について、共通理解に到達するまでユーザーを徹底的にインタビューする。設計ツリーの各分岐を順番に辿り、決定間の依存関係を 1 つずつ解消していく。

## 始め方（最初のターン）

いきなり詰め始めない。まず**何を一緒に詰めようとしているのかを口語で噛み砕いて確認**してから、インタビューに入る。

1. **対象とゴールを自分の言葉で言い直して確認する**: 「いま詰めたいのは〇〇の計画で、ゴールは △△、という理解で合ってる?」のように、固い言い回しを避けて平易に返す。ズレていれば直してもらう。
2. **これから何をするか予告する**: 「論点を洗い出して 1 つずつ一緒に決めていく」という進め方と、おおよその規模感（論点が何個くらいになりそうか）を先に伝える。
3. 合意できたら論点ボードを出して最初の質問に入る。

詰める対象が GitHub の Issue なら、最初の質問の前にその Issue へ `status:refining` を付ける（`gh issue edit <番号> --add-label status:refining`）。並行するセッションと進捗の図に、要件整理中と分かるようにするため（`docs/development.md` の「Issue の状態」）。Issue がまだ無い計画には付けない。ワークツリーを切ると `post-checkout` のフックが `status:in-progress` に付け替えるので、外すのは手でしない。

## 進捗の可視化（論点ボード）

インタビュー中は、答える側が残り作業量を把握できるよう、**各質問の冒頭に論点ボードを再掲する**。

```
論点: 解決 2 / 全 7（残り 5 ・本回答で +1）
- [x] データモデル
- [x] 認証方式
- [→] エラー時のリトライ方針  ← 今ここ
- [ ] 並行更新
- [ ] ロールバック手順
- [ ] 権限境界
- [ ] 移行手順
```

- **正本はこのテキスト自体**。内部カウンタに頼らず、毎回ボードを書き直して数を導出する（数字のズレを防ぐ）。
- 各行の状態: `[x]` 解決済み / `[→]` 今ここ（対応中）/ `[ ]` 未解決。解決済みも残し、全体の流れを一目で追えるようにする。
- 観点は固定リストではなく、**回答によって増える**前提で扱う。増えたら `[ ]` 行を追記し、その回で増えた件数を `本回答で +N` として明示する（減るだけのカウンタにしない）。新たな論点が出なかった回は `本回答で +0` とする。

## 進め方

1. **質問は一度に 1 つだけ**出す。冒頭に上記の論点ボードを置いてから問う。選択肢が明確に分かれる論点は `AskUserQuestion` ツールで提示し、各選択肢に推奨（Recommended）を添える。自由記述で答えるべき論点は文章で問い、自分の推奨回答を併せて示す。
2. **明白な質問はしない**。コードベースや既存資料を調べれば答えが分かることは、ユーザーに聞く前に自分で調べる。表面的な確認ではなく、ユーザーがまだ検討していない可能性の高い**難所（hard parts）**を掘り下げる。
   - **事実を調べるのは自分の仕事、決めるのはユーザーの仕事**。この線引きを守る。
   - 調査が要る論点は、問う前に Backlog MCP で課題を読み、リポジトリ構造やコード横断検索は `Explore` に委譲して事実を揃える。調べれば分かることを聞くと、ユーザーの時間を奪ううえに論点がぼやける。
   - 調査待ちで止めない。調査中の論点は「前提が未解決」として扱い、その間は他の論点を進める。
3. 一つの論点で合意を確定してから次の分岐へ移る。決定ツリーの分岐ごとに結論を固める。回答を受けて新たな論点が派生したら、ボードの未解決に追加する。
4. **次に問う論点は「前提が解決済みのもの」から選ぶ**。未解決の論点のうち、他の未解決な論点の結論に答えが左右されるものは後回しにする（先に聞いても仮定でしか答えられず、前提が覆ったら聞き直しになる）。ボードの並び順はこの依存関係に従わせ、前提が解けて初めて問える状態になった論点を `[→]` に上げる。

## 質問の伝え方

ユーザーに「それってどういうこと?」と聞き返されないよう、質問は噛み砕いて伝える。質問だけを単独で投げず、以下をセットにする:

- **なぜ聞くかを先に一言**: その論点が何に効くのか・どこで詰まりやすいのかという前提を添えてから問う。
- **用語を噛み砕く**: 専門用語・略語はその場で平易に言い換えるか、具体例を 1 つ添える。
- **選択肢は「意味」と「選ぶとどうなるか」をセットで示す**: `AskUserQuestion` を使う場合は各 option の description に帰結まで書く。
- **何を答えればよいかを明示する**: Yes/No・二択・自由記述のどれで返せばよいかが一目で分かる形にする。
- **「分からない / おまかせ」の逃げ道を必ず添える**: 最初の質問ほど難しくてフリーズしやすい。`AskUserQuestion` を使うときは「まだ判断できない（一緒に考えたい）」「おまかせ（推奨に従う）」に当たる選択肢を入れる。これが選ばれたら、推奨案の理由をもう一段噛み砕くか、前提を補う小さな質問に切り替えてほぐす。
- それでも伝わりにくければ、抽象度を下げて**具体例や仮の数値で言い換える**。

## カバーする観点

最低限、以下を網羅するまでインタビューを続ける（該当しない観点は明示的に飛ばしてよい）:

- **技術実装**: アーキテクチャ、データモデル、依存関係、既存コードとの整合
- **UI/UX**: 利用者の操作フロー、状態遷移、エラー時の見せ方
- **エッジケース・異常系**: 空入力、null、境界値、並行アクセス、失敗時のリカバリ
- **トレードオフ**: 採用案の代償、却下した代替案、将来の拡張・保守コスト
- **懸念・リスク**: セキュリティ、データ破壊、ロールバック手順、運用影響

## 完了時

すべての論点が解消したら、**確定した結論と未対応の TODO を要約**する。

**要約したまま終わらない**。チャットの要約はセッションが切れると消え、次のセッションは同じ論点を最初から詰め直す。落とし先に書くところまでがこのスキルの仕事。

1. 落とし先を `AskUserQuestion` で確認する。
   - **GitHub Issue の実装計画にする** → `issue-plan`（書くモード）へ渡す。既定。
   - **地図 Issue に決定として記録する** → `wayfinder` で回している途中のとき。
   - **ファイルに書き出す** → ファイル名と出力先はその場で確認する。リポジトリごとに文書規約があるので `SPEC.md` 等を勝手に作らない。
   - **残さない** → その場限りの検討だったとき。
2. 決まった落とし先に書くところまでやる。提案して終わりにしない。

**共通理解に到達したとユーザーが確認するまで、詰めた内容の実装に着手しない**。要約はインタビューの成果物であって着手の合図ではない。実装に進むかどうかはユーザーが決める。
