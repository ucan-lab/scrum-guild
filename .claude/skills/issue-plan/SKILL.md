# issue-plan

## GitHub の操作

Issue の読み書きは `gh api` の REST で行う。クラウドのセッションでは、GraphQL を使う `gh issue` が 403 で止まるため。
`{owner}` と `{repo}` は `gh` がカレントのリポジトリに置き換える。置き換わらずに 404 になるときは、`git remote get-url origin` から owner と repo を読んで直に書く。

## モード選択

| 言われたこと | モード |
| --- | --- |
| 実装計画を書く、Issue（エピック、ストーリー、タスク）を立てる、サブ Issue に分割する | 書くモード |
| 人が書いた計画をレビューする、考慮漏れを洗い出す | レビューモード |

判断がつかないときは、対象 Issue を書いたのが自分かどうかで決める。

## 書くモード

要件が固まったあと、着手前に実装計画を Issue に書く。

### 絶対にやらないこと

- ソースコードを変更しない（理由: 計画が決まる前に手を動かすと、計画がコードの後追いになる）
- 完了条件を書かずに計画を出さない（理由: 後工程の self-review と pr-review が判定できなくなる）
- 影響範囲を調べずに書かない（理由: 呼び出し元を見落とすと、着手後に計画ごと崩れる）
- 最初に思いついた案をそのまま計画にしない（理由: 1 案しか見ていない状態では、その案の代償が見えない）
- 1 つの Issue に収まらない量を 1 つに詰めない

### 1. 要件を確認する

`docs/` の要件と関係する文書（`requirements.md`、`data-model.md`、`design.md`、`development.md`）を読む。
確認が要る点が残っているなら、計画に入る前に潰す。
`docs/` で決まっている点は潰さずに、計画の「背景」に前提として書く。

### 2. 影響範囲を調べる

変更対象のコードを開いて、次の 3 つを押さえる。

- 変更する関数やクラスの呼び出し元
- 壊れる可能性のある既存のテスト
- 設定値、環境変数、DB スキーマへの波及

参照側のガード（三項演算子、early return、テンプレートの条件分岐）まで読む。

### 3. 案を 2 つ並べて選ぶ

実装方針が 1 通りに定まらない変更では、対案を 1 つ出して比較してから選ぶ。

1. 自分の案を、やること、データの持ち方、影響範囲の 3 点で 5 行以内にまとめる。
2. 別のサブエージェントに同じ論点を渡して独立に案を出させる。手元で `ucan:fable-advisor` が使えればそれを、使えなければ（クラウド）Agent ツールの汎用のサブエージェントを使う。渡すのは「判断したい論点」「関連ファイル」「制約と完了条件」の 3 つ。**自分の案は渡さない**（理由: 渡すとその案の追認になり、対案として機能しない）。
3. 2 案を突き合わせ、割れた点だけを比較する。軸は、既存コードとの整合、壊れる範囲の広さ、後から変えやすいか。
4. 採用案と、却下した案とその理由を次の手順の「背景」に 1 行ずつ残す。
5. **決着しなければ割れたままユーザーに渡す**。どちらを採るかで完了条件が変わるのに決め手が無いときは、`AskUserQuestion` で 2 案を並べて判断を仰ぐ。理由を後付けして片方に寄せない（理由: 比較を通した体裁だけ整えた計画は、1 案で書いた計画より始末が悪い）。

飛ばしてよいのは、変更が 1 箇所で完結し、書き方の選択肢が実質 1 つしかないとき。飛ばしたときはその旨を 1 行書く。

### 4. 計画を書く

Issue はエピック、ストーリー、タスクの3階層で書く（`docs/development.md` の「Issue の運用」）。書き始める前に、書く Issue の階層と親を決める。

| 書くもの | 当てはまるとき | 親 | 形 |
| --- | --- | --- | --- |
| エピック（`epic`） | 確かめられるふるまいが2つ以上まとまる | 無し | 下の 6 つ。「やること」に子のストーリーの並ぶ順と前に要るものを書く |
| ストーリー（`story`） | 確かめられる1つのふるまい。1つの PR に収まるときもストーリーにする。土台の作業（マイグレーション、入口、CI）は、運用者か開発者が確かめられるふるまいを受け入れ条件にした土台のストーリーにまとめる | エピックか無し | `.github/ISSUE_TEMPLATE/story.md`。タスクに分けないときは「やること」「確認方法」「マイグレーション」も書く |
| タスク | ストーリーの中の、1つの PR で入れる変更 | ストーリー。不具合と単発の作業は無し | 下の 6 つ（`.github/ISSUE_TEMPLATE/plan.md`） |

タスクをエピックの直下に置かない（理由: Scrum Guild の木で、タスクの親は無しかストーリーと決まっている。`docs/requirements.md` の「概念」）。
親は、開いている `epic` と `story` の Issue から選ぶ（`gh api "repos/{owner}/{repo}/issues?labels=epic&state=open" --jq '.[] | {number, title}'`、`story` も同じ）。合う親が無ければ、親の案も一緒に書く。

タスクとエピックに書くのは次の 6 つ。

| 見出し | 中身 |
| --- | --- |
| 背景 | なぜやるか。要望と要件へのリンク |
| やること | 変更する対象と、どう変えるか |
| 完了条件 | 満たされたかを他人が判定できる形で書く |
| 確認方法 | 動作確認の手順 |
| 触る領域 | 付ける `area:` のラベル。人が差分を読む領域（`docs/development.md` の「マージの判定」）なら `needs-human` も |
| マイグレーション | 有りか無しか。有りなら `migration` のラベル |

### 5. 詰める

決まっていない分岐が残っていれば grill-me を使って 1 つずつ潰す。
分岐が多すぎて 1 セッションで潰し切れないなら、`wayfinder` で地図を作ってから戻る。

### 6. 大きければ分割する

次のどれかに当てはまったらサブ Issue に分ける。

- 完了条件が 2 つ以上の独立した機能にまたがる
- 別々の人が並行して着手できる
- レビューする差分が読み切れない量になる

分ける先は1つ下の階層にする。エピックはストーリーに、ストーリーはタスクに分ける。分けた元が1つ下の階層の大きさだったときは、手順 4 の表で階層を決め直す。

- ストーリーの受け入れ条件は、確かめる人（利用者、運用者、開発者）から見えるふるまいで、本番か e2e で確かめられる形で書く。テーブルや関数の名前で書かない（理由: ストーリーは人が受け入れる単位で、技術の言葉で書くと人が確かめられない）
- 1つの PR で収まるストーリーは、タスクに分けない
- 親には、子の並ぶ順と前に要るもの、全体の完了条件を残す

### 7. 登録する

投稿の前にユーザーに内容を確認する。

親から先に作る。子をつなぐには親の番号が要るため。

```bash
gh api repos/{owner}/{repo}/issues -f title="<件名>" -F body=@<file> -f 'labels[]=<名前>' -F milestone=<番号> --jq '{number, id, url: .html_url}'
```

本文はファイルに書いてから渡す（理由: シェルで組むと改行が潰れる）。既にある Issue の本文は `gh api -X PATCH repos/{owner}/{repo}/issues/<番号> -F body=@<file>` で直す。
ラベルは、「触る領域」と「マイグレーション」で決めたものと、階層のもの（エピックは `epic`、ストーリーは `story`、タスクには階層のラベルを付けない）を付ける。マイルストーンは入るリリースのものを付ける。番号は `gh api repos/{owner}/{repo}/milestones --jq '.[] | {number, title}'` で引く。

子は親のサブ Issue としてつなぐ。渡すのは子の番号ではなく、REST の `id`（作成の応答の `id`、または `gh api repos/{owner}/{repo}/issues/<子の番号> --jq .id`）である。

```bash
gh api repos/{owner}/{repo}/issues/<親の番号>/sub_issues -F sub_issue_id=<子の id>
```

- サブ Issue は足した順に並ぶ。着手する順に足す
- 子が既に別の親を持つと 422 になる。付け替えるときは `-F replace_parent=true` を足す
- つないだ後に `gh api repos/{owner}/{repo}/issues/<親の番号>/sub_issues --jq '.[].number'` で並びを確かめる

本文の表で子を並べるだけにしない（理由: サブ Issue でつながないと、GitHub の親の進み具合に出ない）。

## レビューモード

人が書いた実装計画を着手前にレビューし、潰すべき考慮漏れを洗い出し、最終的に **そのまま Issue に投稿できる指摘コメント** を生成する。

### このスキルが担う3フェーズ

- **Phase 1 — レビュー**: Issue 本文（実装計画）を読み、構造化された指摘を出す。
- **Phase 2 — 指摘コメント生成**: リードの判断を受け取り、Issue に投稿できる「本文修正指示＋着手前の調査タスク」形式のコメントを生成する。
- **Phase 3 — スキルへの還元提案**: そのセッションの内容から、次回以降このスキルに反映すべき改善を提案する。

Phase 1 の後は必ずリードの判断を仰ぐ。**判断の仲介は `AskUserQuestion` ツールで選択肢形式で行う**（自由記述で促さない）。Phase 1 の指摘をそのまま投稿しない（指摘は内部レビュー用、投稿用は Phase 2 の形式）。

### 絶対原則

1. **コードベースを憶測で断定しない。** 既存の類似機能・スキーマ・命名規約・呼び出し元の有無などは「あるはず」と書かない。判断できないものは指摘ではなく **「実装前の確認事項」** として本人に調査させる。ローカルにコードがあっても、計画レビューの性質上、既存実装の仕様は本人に確認させるのが原則。
2. **一般論を書かない。** 「テストを書きましょう」「命名を分かりやすく」等は禁止。その計画に固有の内容だけ。
3. **無理に指摘を作らない。** 指摘が無い観点は「問題なし」と明記する。
4. 出力は日本語。

### Phase 1: レビュー手順

#### 1. Issue 本文を取得する

GitHub の場合:
```bash
gh api repos/<owner>/<repo>/issues/<番号> --jq '{title, body, labels: [.labels[].name]}'
gh api repos/<owner>/<repo>/issues/<番号>/comments --paginate --jq '.[] | {user: .user.login, created_at, body}'
```
Backlog の場合は、**そのプロジェクトが使う Backlog スペースに対応する MCP サーバーを選んで** `mcp__backlog-<スペース>__get_issue` / `get_issue_comments` を使う（スペースは複数あるので、対象リポジトリ/プロジェクトに応じて切り替える。どのスペースか不明なら本人に確認する）。

**参照先は本文だけで済ませず、以下を必ず読んでからレビューする**（読まずに指摘を書かない）:

- **Backlog 課題への参照がある場合** — その課題の **本文とコメント全体** を `get_issue` + `get_issue_comments` で読む。実装方針・先方回答・確定事項はコメントに書かれていることが多く、本文だけでは考慮漏れを見誤る。どのスペースの MCP サーバーを使うかは対象プロジェクトに合わせて切り替える。
- **関連 Issue / 関連課題がある場合** — Issue 内でリンク・言及された関連 Issue（同リポジトリの GitHub Issue、別の Backlog 課題など）も辿って読む。前提・依存・重複実装の有無はそちらに書かれていることがある。
- 上記で **アクセスできない外部リンク**（例: 権限の無い取引先 Backlog）だけを「実装前の確認事項」に回す。アクセスできるものを読まずに確認事項へ回さない。

#### 2. 前提を確認する

Issue に技術スタック・システム概要が無ければ、リポジトリの CLAUDE.md 等から把握する。テンプレートのプレースホルダが未記入だったり、記載スタックと実リポジトリが食い違う場合は **その旨を冒頭で明記** してからレビューする（憶測で埋めない）。

#### 3. 3観点でレビューする

各観点の詳細チェックリストは **[references/review-perspectives.md](references/review-perspectives.md)** を参照。

- **整合性** — 既存の類似機能・共通処理の再実装、レイヤ構成/命名規約からの逸脱、既存スキーマとの矛盾、フレームワーク標準の再発明。
- **異常系・データ移行** — 空/NULL/0件/上限超過/重複/想定外の型、権限/未ログイン/他テナント、外部API・DB失敗（タイムアウト・リトライ・部分失敗）、**同時実行・二重送信・冪等性・トランザクション境界**、既存データ移行・バックフィル・ロールバック、非同期(Queue/バッチ)の失敗リカバリ。
- **影響範囲** — 変更する共通処理/モデル/API の **他の呼び出し元**、破壊的変更（APIレスポンス形式・DBカラム・設定値・環境変数）、他機能/他リポジトリ/外部連携/バッチへの波及、既存テストが壊れないか・追加すべきテスト。

#### 4. 構造化して出力する

出力フォーマットは **[references/output-formats.md](references/output-formats.md)** の「Phase 1 出力フォーマット」に従う。要点:
- 計画の要約（3行以内）
- 指摘事項（各: 重大度 Blocker/Should/Nice-to-have・観点・指摘・なぜ問題か・本人への確認質問1問）
- 実装前に確認すべきこと
- この計画で最も壊れやすい箇所 Top3

出力後、**リードの判断を仰いで止まる**（次のステップへ進む）。

### 判断の仲介（Phase 1 → Phase 2）

Phase 1 の各指摘について、リードの処理方針を **`AskUserQuestion` ツールで選択肢形式で確認する**。自由記述で「どうしますか？」と促さない。

- **1指摘 = 1問** とし、`header` は指摘番号（例: `指摘①`）、`question` に指摘の一言要約を入れる。
- 各問の選択肢は原則この4択（`AskUserQuestion` は「Other」を自動付与するので、リードが独自方針を書ける）:
  - **本文を修正/追記** — 確定した前提・実態と異なる記述 → Phase 2 の「A」へ。
  - **着手前に調査させる** — 実装方針が変わりうる未確定事項 → Phase 2 の「B」へ。
  - **対応不要（落とす）** — コメントに含めない。
  - **確定事項として本文更新** — 先方回答等で確定済み → Phase 2 の「A」へ（根拠リンクを添える）。
- 指摘が5件以上あると1回の `AskUserQuestion` に収まらない（最大4問）。その場合は **複数回に分けて** 全指摘の判断を集める。
- リードが選択肢に補足（notes / Other）を付けたら、それを Phase 2 の文面に反映する。

全指摘の判断が揃ったら Phase 2 へ進む。

### Phase 2: 指摘コメント生成

判断の仲介で得たリードの方針（本文修正 / 調査させる / 落とす / 確定として反映）に従い、**そのまま Issue に投稿できる1本のコメント** にまとめる。

生成時は **[references/writing-style.md](references/writing-style.md) に蓄積された書き手の癖（語調・粒度・構成）に合わせる**。

投稿用コメントの構成（詳細テンプレートは [references/output-formats.md](references/output-formats.md) の「Phase 2 投稿用コメントフォーマット」）:

- **A. Issue 本文の修正・追記** — 確定した前提・実態と異なる記述の訂正を、本人が本文を直せる粒度で指示。
- **B. 着手前の調査（結果を Issue にコメントさせる）** — 実装方針が変わりうる未確定事項を調査タスクとして指示。着手の関門にすべきものはその旨を添える。

生成後は **markdown コードブロックに入れて提示** し、コピペ投稿できる形にする。リードが希望すれば `gh api repos/<owner>/<repo>/issues/<番号>/comments -F body=@<file>` で投稿する（勝手に投稿しない。必ず確認を取る）。

### Phase 3: 差分比較による学習とスキルへの還元提案

投稿まで終えたら、**Phase 2 で生成したドラフトと、実際に Issue に投稿されたコメントを差分比較し、書き手の癖を学習する**。そのうえで、次回以降このスキルを良くする改善を提案する。

#### 1. 実投稿コメントを取得する

リードがドラフトをそのまま投稿したとは限らない（手直しして投稿することが多い）。投稿後の実物を取得する。

- GitHub: `gh api repos/<owner>/<repo>/issues/<番号>/comments --paginate`（最新の該当コメントを特定）
- Backlog: 対象スペースの `mcp__backlog-<スペース>__get_issue_comments`

投稿を確認できない場合（リードが手元で編集して投稿した等）は、その編集後テキストをリードに貼ってもらう。

#### 2. 差分を取り、癖を抽出する

「Phase 2 ドラフト」と「実投稿コメント」を突き合わせ、**リードが変えた箇所**を洗い出す。以下の型で分類する（詳細は [references/writing-style.md](references/writing-style.md) のカテゴリ）:

- **語調・敬体**（例: 「〜してください」→「〜をお願いします」、断定→やわらげ、記号の増減）
- **粒度**（箇条書きの細かさ、根拠リンク・引用の付け外し）
- **構成**（見出し・A/B の順序、冒頭文の有無）
- **固有表現**（用語の言い換え）

各差分は「ドラフト → 投稿」の実例と出典（Issue 番号・項目）をセットで記録する。単発の事情による変更（その Issue 固有）と、繰り返し現れる癖を区別し、**再現しそうな癖のみ**を学習対象にする。

#### 3. 学習を反映する（承認制）

- **書き手の文体の癖** → [references/writing-style.md](references/writing-style.md) の「学習済みの癖」に追記。次回 Phase 2 がこれを参照して、最初から書き手の文体で生成できるようにする。
- **繰り返し出た指摘の型** — Blocker になった観点が [references/review-perspectives.md](references/review-perspectives.md) に無ければ追記候補。
- **判断の選択肢の過不足** — 仲介の4択でリードが毎回「Other」で同じ方針を書くなら標準化候補。
- **手順のつまずき** — 取得コマンド・MCP 選択・リンク参照で迷った点。

#### 提案のルール

1. **汎用的な改善だけをこのスキルに入れる。** 特定プロジェクト固有の事実（この Backlog スペースはこの MCP サーバー、この取引先の用語、等）は **スキルに書かず、メモリ（project/reference）に保存**することを提案する。スキルはリポジトリ非依存に保つ。書き手の文体の癖はプロジェクト非依存なので `writing-style.md` に入れてよい。
2. **勝手に編集しない。** 変更案は「対象ファイル・追記/修正内容・根拠の差分」を示して提示し、リードの承認を得てから `SKILL.md` / `references/*` を編集する。
3. 変更後は `skill-creator` の `package_skill.py` で検証する。
4. 学習すべき差分が無ければ「今回反映すべき点は無し」と述べて終える（無理に作らない）。

### 重大度の基準

- **Blocker**: 着手前に必ず解消。放置すると障害・データ不整合・手戻り確定。
- **Should**: 着手前に方針を決めるべき。決めずに進むと後で高くつく。
- **Nice-to-have**: 認識しておくとよい。
