# 出力フォーマット

## Phase 1 出力フォーマット（レビュー結果・内部向け）

```markdown
### 1. 計画の要約（3行以内）
※意図を正しく読み取れているかの確認用

### 2. 指摘事項

#### 指摘① <一言タイトル>
- **重大度**: Blocker / Should / Nice-to-have
- **観点**: 整合性 / 異常系 / 影響範囲
- **指摘**: 何が計画から抜けているか
- **なぜ問題か**: 起こりうる不具合・障害を具体的に（入力 → 誤動作のシナリオ）
- **本人への確認質問**: そのまま Issue にコメントできる粒度で1問

#### 指摘② ...
（以下同様）

（指摘の無い観点は「問題なしと判断した観点: ○○ — 理由」と明記する）

### 3. 実装前に確認すべきこと
コードベースを見ないと判断できず、本人に調査させるべき事項をリスト化。

### 4. この計画で最も壊れやすい箇所 Top3
1. ...
2. ...
3. ...
```

出力後はリードの判断を仰いで止まる。

## Phase 2 投稿用コメントフォーマット（Issue 投稿向け）

判断の仲介（`AskUserQuestion`）で得たリードの選択を反映し、以下を1本のコメントにまとめる。**markdown コードブロックに入れて** コピペ投稿できる形で提示する。「本文を修正/追記」「確定事項として本文更新」を選んだ指摘は A へ、「着手前に調査させる」は B へ、「対応不要」は落とす。

```markdown
実装計画をレビューしました。着手前に、本文の修正（A）と調査（B）をお願いします。

## A. Issue 本文の修正・追記

### A-1. <確定した前提の明記>
<根拠（先方回答リンク等）を添えて、本文にどう書くべきかを指示>

### A-2. <未確定 TODO を「確定済み」に更新 / 実装補足>
...

### A-3. <実態と異なる記述の訂正>
現在の「<引用>」という記述は実態と異なります。実際は<正しい状況>です。この実態に沿って文言を修正してください。

## B. 着手前の調査（結果を本 Issue にコメントしてください）

### B-1. <調査タスク>
<何を確認し、何を記載するか>
- <観点1>
- <観点2>

※ 実装方針が変わりうるため着手前の関門として扱ってください。（関門にすべきものだけ添える）

### B-2. <調査タスク>
...
```

### 生成のコツ

- **A（本文修正）**: リードが「確定」「実態と違う」と判断した項目。本人が本文をそのまま直せる粒度で、根拠リンクを添える。
- **B（調査タスク）**: リードが「調査させる」と判断した項目。実装方針（採番タイミング・波及先など）が変わりうるものは着手の関門にする。
- Phase 1 で出したが、リードが「対応不要」と判断した指摘は落とす。
- 投稿は勝手にしない。提示 → リードの承認後に `gh api repos/<owner>/<repo>/issues/<番号>/comments -F body=@<file>` で投稿する。
