# レビュー3観点 詳細チェックリスト

各観点で「計画から抜けていないか」を確認する。該当する具体リスクがある場合のみ指摘化する。無理に埋めない。

## 1. 整合性（既存コード・設計との整合）

- 既存の類似機能・共通処理・ユーティリティがあるのに再実装しようとしていないか（採番・UUID生成・日付処理・API クライアント等）。
- レイヤ構成（Controller / Service / Repository / FormRequest、または api/ services/ stores/ 等）や命名規約から逸脱していないか。
- 既存の DB スキーマ・リレーション・制約（NOT NULL・UNIQUE・FK）と矛盾していないか。
- フレームワーク標準の機能（バリデーション・トランザクション・キュー・認可）を独自実装で再発明していないか。

→ 既存実装の有無を断定できない場合は「実装前の確認事項」に回す。

## 2. 異常系・エッジケース・データ移行

- 入力の境界: 空 / NULL / 0件 / 上限超過 / 重複 / 想定外の型。
- 権限: 権限のないユーザー、未ログイン、他テナント/他ユーザーのデータへのアクセス。
- 外部連携失敗: 外部 API・DB のタイムアウト、リトライ、部分失敗時の挙動。
- **同時実行・二重送信・冪等性・トランザクション境界**（外部API連携では特に重要。リトライで重複リソースが作られないか、生成値の生成タイミングが1操作1回に固定されているか）。
- 既存データの移行・バックフィル、およびロールバック手順。
- 非同期処理（Queue / バッチ）の失敗時のリカバリ。
- 切替の猶予期間・期限（先方仕様変更待ちなど、記述と実態が一致しているか）。

## 3. 影響範囲

- 変更する共通処理・モデル・API の **他の呼び出し元**（今回の変更対象と同じ値/カラム/APIを参照している箇所）。
- 破壊的変更: API レスポンス形式、DB カラム、設定値、環境変数、採番方式。
- 関連 API への波及: 変更対象が登録系なら、対応する変更系・キャンセル系・照会系・コールバックが同じ値を要求しないか。
- 他機能・他リポジトリ・外部連携・バッチへの波及。
- 運用への波及: サポート/監視/ログ検索が変更前の値をキーに使っていないか。
- 既存テストが壊れないか、追加すべきテストは何か。

## 指摘化の判断

- 具体的な不具合シナリオ（入力 → 誤動作/障害）が描けるものだけ指摘にする。
- 既存コードを見ないと判断できないものは指摘にせず「実装前の確認事項」へ。
- 該当なしの観点は「問題なし」と明記する。
