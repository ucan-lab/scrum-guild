# sprint-review

## 仕事

スプリントレビューの場を進める。流れは、ゴールと状況の共有、受け入れ（Done を決める）、Done のデモ、意見と要望の受け取り、起票の候補、バックログの見直し、報告の順。セッションは確かめる場所を用意し、条件を1つずつ宣言して止まり、見るべき点を出す。合否と、意見と方向性を決めるのは人で、セッションは人の答えを Issue に写す。
終わりは「確かめた条件に印が付き、人が閉じると答えた Issue が閉じ、Done の動画を見せ、意見と見直しの方向性が記録の Issue に残り、見つけたことの起票と、残したものの片付けの報告が済んでいる」状態。

動作の確認をマージから切り離し、受け入れでまとめて行うため（`docs/development.md` の「Issue の運用」。2026-10-28 に決めた。#370）。このリポジトリでは、Done は受け入れで閉じた Issue（`completed`）のこと。受け入れはレビューの中で行うので、Done はレビューの途中で決まる。デモは受け入れの後に、Done のものだけ見せる。

## 絶対にやらないこと

- 人の「OK」を待たずに印を付けない。画面を自分で見て合格と決めない（理由: 受け入れはプロダクトオーナーの判断で、セッションの確かめは e2e と CI が既に済ませている）
- 人に聞かずに Issue を閉じない。閉じるのは、すべての条件に印が付き、手順 7 で人が閉じると答えたときだけ（`docs/development.md` の「Issue の状態」）
- 見つけたことをその場で直さない。コードもブランチも作らない（理由: 受け入れの時間を実装に使わない。直すものは Issue にして、ほかの Issue と同じ流れで進める）
- 本番の D1 と Worker に触らない。`--remote` を付けた `wrangler d1`、`wrangler deploy` などは打たない（`CLAUDE.md` の「守ること」）。本番で確かめる条件は、人が本番の画面を操作する
- 本文を丸ごと書き換えて、人が書き足した行を消さない。印を付ける直前に本文を取り直す
- 手順 11 で、ラベルとポイントを付け替えない。記録の Issue を閉じない。次のスプリントの中身を決めない（理由: 付け替えと計画は `sprint-plan` が人と行う。ここは方向性を記録の Issue に残すところまで）
- 市場や競合を調べて、意見や状況の変化に足さない。人が話した内容だけを要旨にする（理由: 人の判断の材料に、セッションの推測を混ぜない）
- Done にならなかった Issue をデモに出さない

## GitHub の操作

Issue の読み書きは `gh api` の REST で行う。クラウドのセッションでは、GraphQL を使う `gh issue` が 403 で止まるため。
`{owner}` と `{repo}` は `gh` がカレントのリポジトリに置き換える。`gh` は1行に1つで打ち、パイプやリダイレクトでつながない（加工は `--jq` で行う）。
`gh` が無いか認証で失敗するときは、`pr-create/github-mcp.md` に従い、GitHub の MCP ツールで代える（手順ごとの読み替えは各手順に書く）。
作業ファイルはスクラッチパッドに置く。スクラッチパッドが無い環境では `/tmp` の下に置く。

## 手順

### 1. ゴールと状況を共有する

今のスプリントの記録の Issue（開いている `sprint-log` で、`## 締め` で始まるコメントが無いもの）を引く。

```bash
gh api "repos/{owner}/{repo}/issues?labels=sprint-log&state=open&per_page=100" --jq '.[] | {number, title}'
```

記録が1つでなければ（無い、2つ以上）、`AskUserQuestion` で、どの記録をこのレビューの記録にするか、記録なしで進めるかを聞く。推す案は、記録が2つなら番号の大きいほう、無ければ「記録なしで進める」。記録なしで進めるときは、手順 9 と 11 のコメントを書かず、中身を報告（手順 12）に出す。`## 締め` で始まるコメントの有無は、`sprint-plan` の手順 1 と同じ `gh api "repos/{owner}/{repo}/issues/<記録の番号>/comments" --paginate --jq '.[] | select(.body | startswith("## 締め")) | .body'` で確かめる。
`progress-data.ts` の `sprint` は、開いた記録のうち番号の大きいほうで、記録が無ければ `null` になる。選んだ記録が `sprint.log` と違うとき、または `null` のときは、`sprint` を使わず、選んだ記録の本文（ゴール、計画の表）から読み、状態は `issues` の `s` で引く。記録なしのときは、ゴールと計画を「記録なし」と出し、受け入れ待ちの一覧だけを共有する。Done は手順 7 で閉じたものだけになる。`gh` が使えないときは共有を省き、省いたことを伝える。

数は `daily-scrum` と同じ `scripts/progress-data.ts` で出す（`docs/development.md` の「スプリントとポイント」の数え方に合わせ、`sprint-plan` と `daily-scrum` と食い違わせない）。`<作業場所>` はスクラッチパッドの中の新しいディレクトリにする。スクリプトの `gh` はカレントのリポジトリを読むので、リポジトリの中から走らせる。

```bash
git fetch origin
mkdir -p <作業場所>
git archive origin/main scripts/progress-data.ts | tar -x -C <作業場所>
node <作業場所>/scripts/progress-data.ts <作業場所>/data.json
```

`data.json` の `sprint`（番号、期間、ゴール、計画の一覧、計画と済みなどの数）と、`issues`（`s` が状態）を読み、計画の各 Issue を状態で分けて、次の形で出す。出すだけで止まらず、続けて手順 2 に進む。

```text
スプリント <番号>（<開始日>〜<終了日>）
ゴール: <ゴール>
計画 <pt> pt（<件数> 件）: Done <pt> pt（<件数>）、受け入れ待ち <pt> pt（<件数>）、まだ <pt> pt（<件数>）、取り下げ <件数>
途中で足した分: <pt> pt（Done <pt> pt）
Done: #<番号> <題>、…
受け入れ待ち: #<番号> <題>、…
まだ: #<番号> <題>（<状態>）、…
```

- Done は `s` が `done`（受け入れで閉じた）、受け入れ待ちは `accept`、まだは残り。計画の一覧に無く `sprint:<番号>` が付いたものは「途中で足した分」にまとめる
- 取り下げは、`issues` に出ない計画の Issue（`not_planned` と `duplicate` で閉じたもの）の件数
- 手順 8 のデモに使うため、Done の番号の一覧（`sprint:<番号>` が付いて、すでに `completed` で閉じていたもの。計画の済みと途中で足した分の済み）を控える

### 2. 受け入れ待ちを一覧にする

```bash
gh api "repos/{owner}/{repo}/issues?state=open&per_page=100" --paginate --jq '.[] | select(.pull_request | not) | {number, title, labels: [.labels[].name], milestone: .milestone.title, parent: (.parent_issue_url // "" | split("/") | last), subs: .sub_issues_summary}'
```

受け入れ待ちの読み方は `docs/development.md` の「Issue の状態」と同じにする。スプリントの記録の Issue（`sprint-log`）は作業ではないので、一覧から外す。閉じるのは `sprint-plan` が締めで行う。
スプリントの終わりに行うときは、今のスプリント（`sprint:<番号>`）の Issue を先に並べる。

- `status:accepting` の付いた Issue
- 子を持つストーリーとエピック（`subs.total > 0`）で、開いている子がすべて受け入れ待ちのもの。`sub_issues_summary` は子のラベルを持たないので、親ごとに子を引いて確かめる。子を持つ子には同じ判定を当てる。子を閉じ終えてから親を確かめるので、親は子の後ろに並べる

```bash
gh api "repos/{owner}/{repo}/issues/<親>/sub_issues?per_page=100" --jq '.[] | {number, state, labels: [.labels[].name], subs: .sub_issues_summary.total}'
```

Issue ごとに本文の受け入れ条件（ストーリー）か完了条件（タスク、エピック）のチェックボックスを読み、PR を引く（ブランチ名の `<番号>-` の先頭か、本文の行頭の `Refs #<番号>`。文中の `Refs` は経緯の説明のことがあるので数えない。`accepting.yml` と同じ）。受け入れは遅れて行うので、古い PR まで送る。

```bash
gh api "repos/{owner}/{repo}/pulls?state=closed&per_page=100" --paginate --jq '.[] | select(.merged_at != null) | {number, title, head: .head.ref, merged_at, refs: ([.body // "" | scan("(?i)(?:^|\\n)[ \\t]*(?:closes|fixes|refs) #([0-9]+)") | .[0]])}'
```

MCP で代えるときは、一覧を `list_issues`（`labels` に `status:accepting`）で引き、親と子は1件ずつ `issue_read` の `get` と `get_sub_issues` で引く。PR は `search_pull_requests`（`repo:<owner>/<repo> is:merged <番号>`）で引き、本文とブランチ名で当たりを確かめる。

受け入れ待ちが1件も無ければ、手順 3 から 7 を飛ばして手順 8 に進む。

### 3. 確かめる場所を決める

条件ごとに、確かめる場所の案を置く。

| 場所 | 向く条件 | 開き方 |
| --- | --- | --- |
| 本番 | 本番でしか起きないこと（デプロイ、本物のログイン、ドメイン、Workers Logs） | 人が自分のブラウザで開く。セッションは URL と操作を出す |
| 手元 | 画面のふるまい、ロールの違い、seed のデータで足りること | 下の「手元を立てる」 |
| 手元の preview | 本番と同じ配り方に頼ること（CSP とセキュリティのヘッダー、画面の資産の配信） | `pnpm dev` の代わりに `pnpm preview` を立て、`pnpm dev:open --preview` で開く |
| PR ごとのプレビュー | 手元と同じ。#374 が入ってから使う | PR に付いた URL |
| PR の記録 | 画面で見られないこと（`batch()` で1つのトランザクションにした、履歴の行、CI の時間、テストの件数） | 下の「画面で見られない条件」 |

Issue ごとに、場所と条件の数を表にして出し、`AskUserQuestion` で、どれから確かめるか、場所の案でよいかを聞く。推す案を先頭にする（手元でまとめて確かめられるものを先に、本番で人が操作するものを後に）。

#### 手元を立てる

本体の作業コピーで `pnpm dev` を立てない（`worktrees/` の変更で読み直しが続く。#367）。`origin/main` の detached のワークツリーを切って立てる。detached のワークツリーには `post-checkout` がラベルを付けない。

```bash
git fetch origin main
git worktree add --detach worktrees/review-<日付> origin/main
```

同じ名前のワークツリーが既にあれば（同じ日の2回目）、切らずに `git -C worktrees/review-<日付> checkout --detach origin/main` で新しい `main` へ移して使う。

ワークツリーで `pnpm install`、`pnpm db:seed`、`pnpm dev` を走らせる（`pnpm dev` はバックグラウンドで立てる）。ポートはワークツリーの名前から決まる。名前に番号が無いので、ほかのワークツリーと重なることがあり、ぶつかって落ちたらワークツリーの `.dev-port-offset` に空いている値を書く（`docs/development.md` の「ポート」）。本物の OAuth のログインを確かめるときだけ、ワークツリーの `.dev-port-offset` に 0 を書く。本体の作業コピーかほかのワークツリーがオフセット 0 で立っていればぶつかるので、人に断って止めてもらってから立てる。
画面は `pnpm dev:open <who> <path>` で開く（`docs/development.md` の「開発とテストでのログイン」）。ブラウザを閉じるまで戻らないので、バックグラウンドで走らせる。毎回新しい context に seed の Cookie を置くので、人の普段のブラウザに残った HttpOnly の Cookie と混ざらない。ロールを替えるときは、前のブラウザのバックグラウンドのタスクを止めてから開き直す。画面を出せない環境（クラウドのセッション）では、手元を場所の案から外し、人の手元のセッションに回すか、PR の記録で示す。

D1（`.wrangler/state`）はワークツリーごとに分かれるので、seed もこのワークツリーで当てる。確かめるために D1 を書き換える（上限、ログインの ID など）のは、このワークツリーの D1 だけにし、書く前に人に断り、何を書き換えたかを控える（手順 12 で報告する）。

### 4. 条件の前に、人の判断とセッションの前提を見せる

手順 3 の後に一度だけ行うのではなく、手順 5 で次の Issue に移るたびに、その Issue の最初の条件を宣言する前に、本文の3節の中身を出す。人が条件を確かめる前に、自分が決めたことと、セッションが人に聞かずに置いたことと、やらないことに触れていないかを見分けられるようにするため（`docs/development.md` の「開発の流れ」）。本文は、そのときに `gh api repos/{owner}/{repo}/issues/<番号> --jq .body` で取り直す（手順 2 の一覧は本文を持たない）。

```text
#<番号> の判断:
人が決めたこと:
- <行。そのまま写す>（無ければ「無し。人に聞かずに進めた」）
セッションが置いた前提（<件数>件）:
- <行>
やらないこと:
- <最後の点検の行>（無ければ「点検の行が無い」）
```

- 「人が決めたこと」は、行を言い換えず並べる
- 「セッションが置いた前提」は、件数と全部の行を出す。着手前と実装中の行を、日付の順のまま見せる
- 「やらないこと」は、最後の `点検（` の行だけを出す（`触れた:` の行もそのまま出す）
- 古い Issue の「着手前に詰めたこと」は、セッションが書いた節として「セッションが置いた前提」に数える。3節も「着手前に詰めたこと」も無い Issue は、「3節が無い（節を足す前に起票した）」と出す

問いは足さない。人が異議を出したら、手順 10 の候補にためる（前提を認めない、やらないことに触れたことを認めない、など）。合否は条件ごとに人が決めるので、この一覧では止まらず、続けて手順 5 に進む。

### 5. 1条件ずつ宣言して止まる

条件ごとに、次の形で出して止まる。1回に出すのは1条件だけにする。

```text
#<番号> の条件 <n>/<全部>: <チェックボックスの文>
場所: <手元の /aoba を admin で開いた画面 など>
これを確認してください:
- <見る点 1（どこを押して、何が出れば合格か）>
- <見る点 2>
```

手元なら画面をその状態まで進めてから出す（`pnpm dev:open` で開き、操作が要るなら人に頼む手順を書く）。見る点は、条件の文を画面の上の言葉に置き換えたものにする。言葉の辞書のゲームとスクラムの両方で変わる条件は、両方を見る点に入れる。
本番で確かめる条件の操作が行を書く（ワークスペースを作る、言葉づかいを切り替えるなど）なら、何を書くかを宣言に含め、人の答えの後に、書いたもの（名前、画面）を控える（手順 12 で報告する。最後にまとめて聞くと忘れる）。

人の答えで次へ進む。

- 「OK」: 手順 6 で印を付け、次の条件へ
- 合わない（条件を満たさない）: 受け入れの不合格。印を付けず、直しの Issue の候補（手順 10）にためる。元の Issue は `status:accepting` のまま開いておく（`docs/development.md` の「Issue の運用」）
- 気になる（条件は満たすが、要望や仕様の穴がある）: 印を付け、見つけたことの候補（手順 10）にためる
- 後で: 印を付けずに次へ。Issue は手順 7 で閉じない

#### 画面で見られない条件

画面で見られない条件は、次のどれかで示す。

- コード: 受け入れる時点の `main` のコミットの SHA を付けた GitHub の URL に、行の範囲を付ける（`https://github.com/{owner}/{repo}/blob/<SHA>/src/server/operations/tasks.ts#L40-L58`）。ブランチ名の URL は後で行がずれるので使わない。どの行が条件のどこに当たるかを添える
- D1: 確かめるワークツリーの D1 を `pnpm exec wrangler d1 execute DB --local --command "<SELECT 文>"` で読んだ結果。組織の中の表は組織で絞って読む
- PR の記録: PR の本文の `## 確認方法`、CI の実行の時間、テストの件数。PR と実行の URL を添える

### 6. 印を付ける

人の「OK」を受けたら、本文を取り直し、[check-criterion.py](check-criterion.py) で印を付けた本文を作って書き戻す。

```bash
gh api repos/{owner}/{repo}/issues/<番号> --jq .body
```

出力を Write でスクラッチパッドの `body-<番号>.md` に書き（`gh` のリダイレクトは使わない）、次を走らせる。<条件の文字列> は、チェックボックスの文から、その行だけを指す部分を渡す。

```bash
python3 -I <このディレクトリの絶対パス>/check-criterion.py <本文> <条件の文字列> <出力>
```

- 最後の行が「本文を書き換える」なら、`gh api -X PATCH repos/{owner}/{repo}/issues/<番号> -F body=@<出力>` で書き戻す（MCP では、出力の中身を `issue_write` の `update` の `body` に渡す）。書いた後に本文を取り直し、その行だけが変わったことを確かめる
- 「本文は変わらない」なら、既に印がある。書き戻さない
- 終了コードが 1 なら、該当が無いか、チェック済みの行も含めて2行以上に当たっている。標準エラーの候補を見て、文字列を長くして打ち直す（チェック済みも数えるのは、前の条件に当てたつもりの文字列で、人が OK と言っていない条件に印を付けないため）
- 終了コードが 2 なら、引数の誤りか、本文と出力のファイルを読み書きできない。標準エラーの理由を見て直す

本文は `gh` の出力から Write で写すので、写しで行が落ちたり改行が変わったりしうる。書き戻した後に取り直した本文と、書き戻す前に取った本文を比べ、違いが印の1行だけであることを確かめる。ほかの行が変わっていれば、取り直した本文で同じ手順をやり直す。

### 7. 閉じるかを聞く

Issue の受け入れ条件（ストーリー）か完了条件（タスク、エピック）の節のチェックボックスにすべて印が付いたら、`AskUserQuestion` で閉じるかを聞く。推す案（閉じる）を先頭にし、「開いたまま残す」も並べる。数えるのはその節だけで、「確認方法」や「やること」のチェックボックスは数えない。その節にチェックボックスが1つも無い Issue は、閉じるかを聞く前に、何を確かめれば受け入れたことになるかを人に確かめる。
閉じると答えたときだけ閉じる（MCP では `issue_write` の `update` に `state: closed` と `state_reason: completed` を渡す）。閉じた Issue が Done になるので、番号を控える（手順 8 のデモに出す）。

```bash
gh api -X PATCH repos/{owner}/{repo}/issues/<番号> -f state=closed -f state_reason=completed
```

子を持つストーリーとエピックは、子をすべて閉じてから親の条件に移る（`docs/development.md` の「Issue の運用」の、閉じる人と条件）。
受け入れで不合格だった Issue の直し（`bug`）を受け入れたら、続けて元の Issue の印の無い条件を手順 5 のとおり宣言し直し、人の「OK」で印を付ける。元の条件がすべて埋まったら、元と直しを一緒に閉じるかを聞く（同じ節の、合格したら元と直しを一緒に閉じる決まり）。

### 8. Done のデモを動画で見せる

手元のセッションだけで行う。画面を出せない環境（クラウドのセッション）では、「動画を飛ばした」と伝えて手順 9 に進む。デモに出すのは、Done の Issue だけ。手順 7 で閉じた Issue と、手順 1 で控えた、すでに `completed` で閉じていた `sprint:<番号>` の Issue を合わせる。開いたまま残した Issue、「後で」にした Issue、不合格だった Issue は出さない。Done の Issue が1つも無ければ、「Done が無いのでデモを飛ばした」と伝えて手順 9 に進む。

合否は手順 5 から 7 で決まっている。ここは、Done になったものの動きを、全部まとめて見る場にする。録画と手順書の書き方は `acceptance-video` に従う。ここでは、まとめて撮る流れだけを書く。確かめる場所に「手元」を選んでいなくても、デモは手元の preview で撮るので、手順 3 の「手元を立てる」でワークツリーを切る（切っていなければ、切って `pnpm install` までする）。

1. 動画の対象を決める。Done の Issue ごとに、手順 2 と同じ引き方で紐づく PR（すでに閉じていた Issue の PR も引く）すべての変更したファイルを集める（`gh api "repos/{owner}/{repo}/pulls/<PR の番号>/files" --paginate --jq '.[] | {filename, status}'`。和集合にする）。`*.test.ts` と、`status` が `removed` のファイルは数えない。残ったファイルで、次の順に決める
   1. `.svelte`、`.css`、言葉の辞書（`src/shared/vocabulary.ts`）、`src/app.html`、`static/`、`src/hooks.client.ts` のどれかに当たれば、画面が変わる Issue として対象にする
   2. 当たらず、`src/lib/` と `src/routes/` の `.ts` だけ、または `src/server/` と `src/shared/operations/` だけが変わった Issue は、画面が変わるか分からないので、`AskUserQuestion` で、撮るかを人に聞く
   3. どれにも当たらない Issue は、「画面のコードを変えていない」と理由を付けて飛ばす。紐づく PR が引けない Issue は、「紐づく PR が見つからない」と理由を付けて飛ばす
   4. 子を持つストーリーとエピックは、子のどれかが今回の動画の対象になっている（Done の一覧にあり、人が撮るのを断っておらず、手順書を作れている）ときだけ、「子 #<番号> の動画で足りる」と理由を付けて飛ばす。どの子も対象でないときは、親自身の紐づく PR で、上と同じに決める。飛ばした親の子が撮れなかったときは、手順 12 で、親の理由に「子 #<番号> が撮れなかった」を足す
2. 対象が 6 本を超えるときは、撮る前に `AskUserQuestion` で、全部撮るか、絞るかを聞く（理由: 1 本あたり約 30 秒の録画と合成がかかる）
3. 対象の Issue ごとに、`acceptance-video` の手順 1 で手順書を書き、`--check` を通す。`--check` を通らない手順書は、一覧に出す前に直し、直せなければその Issue を「手順書を作れなかった（理由）」で撮れなかった扱いにする。書いた人の確認（`OWNER`、`COLLABORATOR`、`github-actions[bot]` 以外なら、要旨を見せて続けるかを聞く）は、まとめた承認とは別に、Issue ごとに先に行う。全部の手順書を、Issue の作者と `association`、場面ごとの字幕と操作を並べた 1 つの一覧にして出し、`AskUserQuestion` で、録画してよいかを 1 回で聞く。質問には「録画は、このワークツリーの D1 を書き換え、終わりに seed で戻す」を含める。直したい Issue があれば、その手順書だけ直して、もう一度一覧を出す
4. 撮る前に、手順 3 の「手元を立てる」で立てた `pnpm dev` と `pnpm dev:open` のバックグラウンドのタスクがあれば止める。`pnpm preview` が既に立っていれば（手順 3 で「手元の preview」を選んだとき）、立て直さずに `curl` の応答を確かめて使う。無ければ、`acceptance-video` の手順 3 で立てて、応答を待つ（`pnpm dev` と `pnpm preview` は API のポートが同じで、同時には立てられない。`record.mjs` は API のポートの preview につなぐ）
5. Issue を 1 本ずつ撮る。毎回 `pnpm db:seed` から始め、`acceptance-video` の手順 4 の seed、録画、合成の 3 コマンドを走らせる。動画の置き場所は、スクラッチパッドの `acceptance-videos-<日付>/` に 1 つ決める。1 本が失敗しても、残りは撮り、失敗した Issue と理由を控える。合成が終了コード 3（30 秒超え）なら、承認した手順書の `read` と `hold` の待ちだけを縮めて（場面と字幕は変えない）1 回だけ撮り直し、縮めた分を手順 12 の報告に出す。それでも超えたら撮れなかった扱いにする。失敗した録画が mp4 を残していても、`manifest.json` の `video` には入れない
6. 全部撮り終えたら、`pnpm db:seed` で D1 を戻す。条件の確認は終わっているので、preview は止め（止めたことを `curl` の無応答で確かめる）、止めたことを手順 12 に控える
7. 置き場所に `manifest.json` を書き（親を子の動画で足りるとして飛ばしたのに、その子が撮れなかったときは、親の理由に「子 #<番号> が撮れなかった」を足す。Done にならなかった Issue は入れない）、`acceptance-video` の `gallery.mjs` で 1 枚の HTML に並べて開く。書き方と開き方は `acceptance-video` の「まとめて撮る」に従う。人が動画を見て回ったら、手順 9 に進む

飛ばした Issue、撮れなかった Issue、動画の置き場所、止めた preview、録画で書き換えて seed で戻した D1 は、手順 12 で報告する。

### 9. ステークホルダーの意見と要望を受け取る

`AskUserQuestion` で、デモを見て、またはスプリントの間に、ステークホルダーの意見、要望、市場や状況の変化があるかを聞く。選択肢は「ある（Other に書く、またはこのまま続けて話す）」と「特に無い」にする。人が話し終えるまで、聞き取りを続ける。

聞き取った内容を、セッションの言葉で要旨にし、次の3つに分けて人に見せる。人が直した点は、直した形で写す。

- 意見: 動きや出来への感想、指摘
- 要望と不具合: 足してほしいこと、直してほしいこと。手順 10 の起票の候補にためる（種別は、要望か不具合）
- 状況の変化: 市場、競合、チームやステークホルダーの事情。人が話したものだけ。調べて足さない

「特に無い」なら、書かずに手順 10 に進む。記録の Issue がある（手順 1）ときは、要旨が確定してから、記録の Issue に次のコメントで残す。コメントは `## レビュー` で始め、締めの `## 締め` と区別する（`sprint-plan` がこの印で読む）。

```markdown
## レビュー（<日付>）意見と要望

### 意見
- <要旨>

### 要望と不具合
- <種別>: <要旨>

### 状況の変化
- <要旨>
```

無い区分の見出しは書かない。コメントは公開リポジトリの Issue に残るので、要旨を見せるときに伝える。本文はスクラッチパッドのファイルに書いてから渡す（MCP では `add_issue_comment`）。

```bash
gh api repos/{owner}/{repo}/issues/<記録の番号>/comments -F body=@<file> --jq .html_url
```

### 10. 見つけたことを起票の候補にする

確かめ終えたら（または人が打ち切ったら）、ためた候補をまとめて出す。手順 4 で人が出した異議と、手順 9 の要望と不具合も候補に入れる。種別は、前提が決めた仕様を人が認めないなら仕様の穴、やらないことに触れた変更を戻すなら不具合、前提とは別の案なら要望にする。候補ごとに、種別（要望、不具合、仕様の穴）、見つけた Issue と条件（手順 4 の異議なら、異議を出した行。手順 9 の意見なら、意見の要旨）、再現の手順か画面、階層と親の案、マイルストーンの案を置く。
`AskUserQuestion`（`multiSelect`）でどれを起票するかを聞き、選ばれたものを `backlog-add` で起票する。受け入れの不合格の直しは、`bug` を付け、元と同じストーリーの子にし、本文で元の Issue を指す（`docs/development.md` の「Issue の運用」）。条件の外で見つけた不具合は、親の無いタスクにしてよい。マイルストーンは、初版の受け入れで見つけた不具合を「初版」、要望は人に聞いて決める。起票した番号は、手順 11 の「足す」に使う。

### 11. バックログを見直す

意見、要望、状況の変化、受け入れの結果を踏まえて、バックログの優先順位と中身を見直し、次のスプリントの方向性を人とすり合わせる。決めるのは方向性までで、ラベル、ポイント、計画は触らない（`sprint-plan` が、残した方向性を読んで次の計画の案に使う）。

見直しの候補を、次の4つの操作で並べる。

| 操作 | 意味 |
| --- | --- |
| 上げる | 次の計画で先に入れる |
| 下げる | 次の計画で後ろにする |
| 外す | 次の計画の候補に入れない（バックログに戻す案を含む） |
| 足す | 手順 10 で起票した Issue、または起票していないが次の計画に入れたいもの |

候補は、開いた末端の Issue（`sprint-pick` の手順 1 と 2 の分け方で「着手できる」と「待ち」に入るもの、今のスプリントで開いたまま残るもの）と、手順 10 で起票した Issue から、手順 9 の意見と状況の変化、手順 1 のゴール、手順 5 の不合格に結び付くものだけを選ぶ。理由に、結び付く意見か状況の変化を1行で添える。件数は、人が判断できる数（目安は 7 つまで）に絞る。

`AskUserQuestion`（`multiSelect`）で、どの候補を採るかを聞く。細かい直しと、次のスプリントの方向性（1〜2 文）は「Other」のメモで受ける。方向性が決まらなければ、無しとして進める。決まった内容を、記録の Issue がある（手順 1）ときは、次のコメントで残す。

```markdown
## レビュー（<日付>）バックログの見直し

方向性: <人が決めた 1〜2 文。無ければ「無し」>

| 操作 | Issue | 理由 |
| --- | --- | --- |
| 上げる | #<番号> <題> | <結び付く意見か状況の変化> |
| 下げる | #<番号> <題> | <理由> |
| 外す | #<番号> <題> | <理由> |
| 足す | #<番号> <題> | <理由> |
```

採らなかった候補は書かない。採ったものが無く方向性も無ければ、コメントを書かない。

```bash
gh api repos/{owner}/{repo}/issues/<記録の番号>/comments -F body=@<file> --jq .html_url
```

### 12. 残したものと片付けを報告する

終わりに、次をまとめて報告する。

- 手順 1 で共有したゴールと状況
- 閉じた Issue（Done になったもの）、印を付けたが開いたまま残した Issue と残した理由、確かめていない条件
- 起票した Issue
- 記録の Issue に残したコメント（手順 9 の意見と要望、手順 11 の見直しの方向性）の URL。記録なしで進めたときは、コメントにするはずだった中身
- 本番に残したもの: 確かめるために人が本番で書いた行（作ったワークスペース、言葉づかいの切り替えなど）。消すか戻すかは人が決めるので、何をどの画面で書いたかを並べる
- 手元に残したもの: 書き換えた D1 の値、立てたサーバー、開いたブラウザ、確かめるためのワークツリー
- 手順 8 で撮った動画: 置き場所、飛ばした Issue と理由、撮れなかった Issue と理由、止めた preview（止めたバックグラウンドのタスクと、応答しないことの確認）、録画で書き換えて seed で戻した D1

手元の片付けは、人に断ってから行う。立てた `pnpm dev`（か `pnpm preview`）と `pnpm dev:open` のバックグラウンドのタスクを止め（`pkill` は使わない）、確かめるワークツリーを消す。D1 はワークツリーの中にあるので、書き換えた値も一緒に消える。人が続けて使うためにワークツリーを残すと答えたら、消さずに、ワークツリーの中で `pnpm db:seed` を打って D1 を戻す。

```bash
git worktree remove worktrees/review-<日付>
```
