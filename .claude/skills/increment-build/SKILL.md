# increment-build

## 仕事

1つのタスク（または子の無いストーリー）の Issue を、実装して `done-check` に渡す。`done-check` が `pr-create` と `pr-feedback` へ続け、PR、レビューへの対応、マージの後片付けまでを受け持つ。
終わりは「`pr-feedback` が後片付けを終えている」状態。
人が担うのは判断だけにする。判断が要る点は推す案を先頭にした `AskUserQuestion` で聞き、チャットの文章で選ばせない。

## 入力

Issue の番号。並べて進めているほかの Issue があれば、その番号と重なりうるファイル、`DEV_PORT_OFFSET` の値（`backlog-pick` のプロンプトが渡す）。

## 手順

### 1. 着手してよいかを確かめる

```bash
gh api repos/{owner}/{repo}/issues/<番号> --jq '{state, title, pr: (.pull_request != null), labels: [.labels[].name], blocked: .issue_dependencies_summary.blocked_by, subs: .sub_issues_summary.total, parent: (.parent_issue_url // "" | split("/") | last)}'
gh api "repos/{owner}/{repo}/pulls?state=open&per_page=100" --jq '.[] | {number, head: .head.ref, refs: ([.body // "" | scan("(?i)(?:closes|fixes|refs) #([0-9]+)") | .[0]])}'
```

`gh` が無いか認証で失敗するときは、`pr-create/github-mcp.md` に従い、GitHub の MCP ツールで代える。Issue は `issue_read` の `get`、`get_labels`、`get_parent`、開いた PR は `list_pull_requests`（`fields` に `number`、`head`、`body` を入れる）で読む。`issue_read` は `blocked` を返さないので、本文と親の Issue の「前に要るもの」を読んで確かめる。

次のどれかなら止まり、理由を伝える。

- 閉じている、PR の番号だった、`epic` か子を持つ（子のタスクを進める）
- その Issue を指す開いた PR がある（ブランチ名の `<番号>-` の先頭か、本文の `Closes` と `Refs`）
- `status:in-progress` か `status:refining` が付いている（ほかのセッションか人が受け持っている）。前のセッションが落ちて残ったもの、人がこのセッションで続けるよう言ったものだけ続ける。手元のワークツリーが残っていれば、それを使う
- `blocked` が 0 でない、または親のストーリーの `blocked` が 0 でない（前に要るものが開いている）
- 人が行う Issue（題が「確認:」で始まる、要件を決める、本番やアカウントやドメインの操作）
- `migration` が付いていて、ほかに `migration` の付いた作業中の Issue か開いた PR がある
- このセッションが既に2つの Issue を受け持った（次は新しいセッションで始める）

並べている相手がいれば、両方の「やること」から変えるファイルを比べ、`docs/development.md` の「並行して作業するときの決まり」で並べてよいかを確かめる。

### 2. 詰める

Issue の本文、コメント、親の Issue、本文が指す `docs/` を読む。
本文に書かれていない難所があれば、`status:refining` を付けてから `backlog-refine` で1つずつ聞く。調べれば分かることは聞かずに決めて伝える。`backlog-refine` の落とし先は、手順 3 の Issue の本文と決まっている。
難所が無ければ飛ばす。人に聞けない実行では、前提を自分で置いて手順 3 で Issue に書き、PR の本文にも書く（`pr-create` に渡す）。

### 3. 記録する

決めたことを Issue の本文に「着手前に詰めたこと（日付、backlog-refine）」の節で足し、やることと完了条件も直す。
後の Issue に関わることは、その Issue にコメントで申し送る。決めたことを会話だけに残さない（並べたセッションと次のセッションが読めないため）。

### 4. ワークツリーを切る

ブランチとワークツリーの名前 `<番号>-<短い名前>` を、ファイルを書き始める前に決める（後で名前を変えると、フックが自分の変更と数えなくなる）。

```bash
git fetch origin
git worktree add worktrees/<名前> -b <名前> origin/main
```

`post-checkout` が `status:in-progress` を付けて `status:refining` を外す。
ワークツリーで `pnpm install` を走らせる（依存はワークツリーごとに入れる。`docs/development.md` の「ワークツリーで作業する」）。
以降の git、`pnpm`、`done-check` は、ワークツリーの絶対パスの中で行う。Bash のカレントは呼び出しごとに本体へ戻るので、コマンドごとに `cd <絶対パス> ||` を付けるか `git -C <絶対パス>` で打つ。

クラウドのセッションはワークツリーを切らず、ラベルを手で付け替える（`docs/development.md` の「Issue の状態」）。
Issue に、ブランチ名とセッションの識別をコメントで残す（同じ文書の「並行して作業するときの決まり」）。

### 5. 実装を委譲する

`ucan:implementer` に渡す。無い環境（クラウド）では Agent ツールの汎用のサブエージェントに渡す。渡すのは、ワークツリーの絶対パス、Issue の番号とやること、完了条件、変えてよい範囲、受け入れ条件の5つ。
やることが次のどれかに触れるなら、渡す前に下の「テストを先に書く」を行う。テストの書き手と実装の書き手を分け、実装の思い込みをテストに持ち込ませないため（すり抜けとランタイムの癖は、同じ書き手だとテストからも実装からも同じように抜け、レビューまで見つからない）。

- `.claude/hooks/` と `.githooks/`（守る仕組み）
- 認証、認可、権限の検査（`src/server/auth/`、`src/server/crypto/`、`src/server/operations/register.ts` と `guards.ts`）
- Workers のランタイムに頼る処理（外への `fetch`、Cookie、リダイレクト、ストリーム、`scripts/headers.ts` のセキュリティのヘッダー）

触れないものは、テストも実装と一緒に書かせる（受け入れ条件の1つ目）。

受け入れ条件は次のとおり。触る範囲に合わないものは外し、外した理由を渡す。

- 完了条件を確かめるテストを実装と一緒に書く。API の操作を足したら、権限と組織の分離のテストが通る（`add-operation`）。「テストを先に書く」を行ったときは、コミットしたテストを書き換えずにすべて通す。テストが誤っていると見たら、書き換えずに理由を添えて戻る
- 仕様を変えたら、同じ差分で `docs/` を直す
- `pnpm check`、`pnpm lint`、`pnpm format:check`、`pnpm test`、`pnpm build` が通る
- マイグレーションを足したら `pnpm db:migrate:fresh` が通る（書き方は `d1-migration`）
- 画面か API の流れを変えたら、変えた画面と流れに関わる e2e のファイルが通る（`pnpm e2e e2e/members.test.ts` のようにファイルを渡す）。どの画面にも効くものを変えたときと、迷ったときは全件が通る。ファイルの選び方と、全件を走らせる変更の一覧は `docs/development.md` の「開発の流れ」に従う。`DEV_PORT_OFFSET` を渡されていれば、`pnpm e2e` と `pnpm dev` に付ける
- `.claude/hooks/` を変えたら `node --test .claude/hooks/*.test.mjs` が通る
- コミットしない。ファイルは Edit と Write で書く（Bash で書いたファイルはフックがコミットを止める）。`pkill` を使わない

画面を作るなら `ui-polish` を読ませる。

#### テストを先に書く

1. **書く。** Agent ツールの汎用のサブエージェントに、テストだけを書かせる。渡すのは、ワークツリーの絶対パス、Issue の番号、完了条件、手順 3 で Issue に書いた決めたこと、呼び口（操作の定義、関数の名前と引数、置くファイル）の5つ。実装の案は渡さない（理由: 渡すと、テストがその案の追認になる）。呼び口が Issue で決まっていなければ、先に決めて Issue に足してから渡す（理由: テストの書き手が推測で名前を置くと、実装の書き手がそれに合わせるか、テストを書き換えるかになる）。次を書かせる
   - 完了条件と決めたことの1つずつに、通る場合と断る場合
   - フックと守る仕組みなら、すり抜けの手口を並べたもの。リダイレクト、ヒアストリングとヒアドキュメント、`cd` と `pushd`、`scp`、`rsync`、`tee`、引用符と否定、変数とエイリアス、ほかのシェルとインタープリタ。前に塞いだ手口を壊していないことも入れる（`.claude/hooks/guards.test.mjs` の既存の例）
   - Workers のランタイムに頼る処理なら、テストは Workers の実行環境で走らせる。`fetch` をモックにするときは、モックが返す振る舞い（`redirect` の各値、ヘッダー、本文を読める回数など）が本物の workerd と同じかを、モックを使わない小さなテストで先に確かめる
   - 書いたテストを走らせ、すべてが、まだ無い振る舞いのために落ちることを確かめる。import の誤りや書き間違いで落ちているものは直させる
2. **コミットする。** 落ちることを自分で走らせ直して確かめ、テストだけを `test:` のコミットにする。後の手順で、実装の書き手がテストを書き換えていないかをこのコミットとの差分で見る。
3. **実装させる。** 手順 5 の初めに挙げた5つを `ucan:implementer`（クラウドは汎用のサブエージェント）に渡す。
4. **崩しにかかる。** 戻ったら、別の汎用のサブエージェントに、実装を崩すテストを足させる。渡すのは、ワークツリーの絶対パス、Issue の番号、完了条件、2 のテストのコミット以降の差分の範囲。新しく足したテストのうち、通ったものは、前のテストと重ならない手口を確かめるものだけを残させる（回帰を止める）。落ちるテストが出たら、テストを 2 と同じくコミットし、実装した同じエージェントに SendMessage で渡して直させてから、もう一度崩しにかからせる。落ちるテストが出ない周が来るか、3周したら止める（理由: 周回に上限が無いと、トークンも時間も読めなくなる）。3周目で落ちたテストも直させてから止め、まだ崩せそうな筋が残っていれば Issue にコメントで残し、PR の本文にも書く
5. **記録する。** テストの区分（完了条件、断る場合、すり抜け、ランタイム）ごとの件数と、崩しにかかった周の数と各周で落ちた件数を、`pr-create` に渡す。PR の本文の「確認方法」に書かせる

### 6. 受け取る

戻ったら、受け入れ条件の検査を自分で走らせ直す。エージェントの報告を検査の結果として扱わない。
`git status --short` に身に覚えのない変更があれば止まり、人に確かめる。
「テストを先に書く」を行ったときは、テストのコミットから後で、そのテストのファイルの既存の行が書き換わっていないかを `git diff <テストのコミット> -- <テストのファイル>` で確かめる。書き換わっていれば、理由を確かめ、誤ったテストを直したものだけを残し、理由を PR の本文に書く。
通ったらコミットし、Skill ツールで `done-check` を起動する。レビューと直し方の基準は `done-check` に従う。直す量が多ければ、実装したエージェントに SendMessage でまとめて直させ、戻らなければ自分で直す。

### 7. 渡した後

`done-check` から `pr-create`、`pr-feedback` へ続ける。ストーリーの最後のタスクなら、`pr-feedback` の説明資料で親のストーリーの受け入れ条件を示す。
マージの後は `pr-feedback` の後片付けまで続ける。

## 止まる条件

- 手順 1 のどれかに当てはまる
- 詰めた結果、Issue を分けたほうがよい（`backlog-add` に戻す）
- 検査が落ちて、原因が分からない
- 「テストを先に書く」で、実装の書き手がテストを誤りと見て戻り、どちらが正しいかを Issue と `docs/` から決められない（人に聞く）
