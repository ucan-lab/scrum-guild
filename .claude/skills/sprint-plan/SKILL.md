# sprint-plan

## 仕事

今のスプリントを締め、次のスプリントの約束を人と決めて GitHub に書く。決まりと数え方は `docs/development.md` の「スプリントとポイント」。
終わりは「前の記録の Issue に締めのコメントが付いて閉じ、次の `sprint:<番号>` のラベルと記録の Issue ができ、選んだ Issue に `sprint:<番号>` と `pt:` が付いている」状態。
何を入れるかとポイントを決めるのは人で、セッションは数を出し、案を置き、人の答えを GitHub に写す。

## 絶対にやらないこと

- 人の答えを待たずにラベルを付け外ししない。記録の Issue も作らない（理由: スプリントの約束は人が決める。人に聞けない実行では止まる）
- 記録の Issue のほかに Issue を閉じない。閉じるのは受け入れで、`sprint-review` が受け持つ
- 持ち越す Issue の `pt:` を変えない（理由: 前のスプリントの計画と済みの基準がずれる）
- 子を持つストーリーとエピックに `sprint:<番号>` と `pt:` を付けない（理由: 子と二重に数える）
- `sprint-review` と同時に走らせない。締めの数を出してから書き込むまでの間に Issue が閉じると、締めの数と持ち越しが食い違う

## GitHub の操作

`gh api` の REST で読み書きする。クラウドのセッションでは、GraphQL を使う `gh issue` が 403 で止まるため。
`{owner}` と `{repo}` は `gh` がカレントのリポジトリに置き換える。`gh` は1行に1つで打ち、パイプやリダイレクトでつながない（加工は `--jq` で行う）。
`gh` が無いか認証で失敗するときは、`pr-create/github-mcp.md` に従い、GitHub の MCP ツールで代える。ラベルを作る MCP のツールが無ければ、ラベルの作成だけ人に頼む。
作業ファイルはスクラッチパッドに置く。スクラッチパッドが無い環境では `/tmp` の下に置く。
ラベルの名前の `:` は、パスに入れるときだけ `%3A` にする（`issues/<番号>/labels/sprint%3A<番号>`）。
日付は日本時間で数える。開始日は手順 6 を行う日、終了日はその6日後。

## 手順

### 1. 今のスプリントを引く

```bash
gh api "repos/{owner}/{repo}/issues?labels=sprint-log&state=all&per_page=100" --jq '.[] | {number, title, state, body}'
```

開いている記録の Issue の数と、締めのコメント（`## 締め` で始まるコメント）があるかで分ける。コメントは `gh api "repos/{owner}/{repo}/issues/<記録の番号>/comments" --paginate --jq '.[] | select(.body | startswith("## 締め")) | .body'` で引く。
次のスプリントの番号は、今のスプリントの番号に 1 を足したもの。

| 開いている記録 | 進み方 |
| --- | --- |
| 無い | 閉じた記録に締めのコメントの無いものがあれば、止まって人に確かめる（前のスプリントの持ち越しが宙に浮くため）。無ければ最初のスプリントで、番号は閉じた記録の最大の番号の次（無ければ 1）。手順 4 へ進む |
| 1つで、締めのコメントが無く、計画の一覧の Issue に `sprint:<番号>` が1件も付いていない | 前の実行が、前の記録の無い状態から手順 6-2 の後で止まった。この記録を次のスプリントの記録として使い、手順 6-3 から続ける（計画はこの記録の本文のとおり） |
| 1つで、締めのコメントが無い（上の行に当たらない） | 今のスプリント。題から番号と期間を、本文から計画の一覧とゴールを読む。今日が終了日より前なら、`AskUserQuestion` で今締めるか（推す案は「終了日まで待つ」）を聞き、待つと答えたら何も書かずに終える |
| 1つで、締めのコメントがある | 前の実行が手順 6-1 の後で止まった。持ち越す Issue、バックログに戻す Issue、この締めのベロシティは締めのコメントから読み、出し直さない。人に止まっていたことを伝えてから手順 4 へ進む。手順 5 では持ち越しとバックログに戻すものを聞き直さない |
| 2つで、番号の小さいほうに締めのコメントがある | 前の実行が手順 6-2 の後で止まった。大きいほうを次のスプリントの記録として使い、手順 6-3 から続ける（計画は大きいほうの本文のとおり） |
| それ以外 | 止まり、人にどの記録が今のスプリントかを確かめる |

### 2. 受け入れ待ちを示す

今のスプリントの Issue を引く。

```bash
gh api "repos/{owner}/{repo}/issues?labels=sprint:<番号>&state=all&per_page=100" --paginate --jq '.[] | select(.pull_request | not) | {number, title, state, state_reason, labels: [.labels[].name]}'
```

計画の一覧にあって、ここに出ない Issue（途中でスプリントから外したもの）は、`gh api repos/{owner}/{repo}/issues/<番号> --jq '{number, state, state_reason, labels: [.labels[].name]}'` で1件ずつ引く。

開いていて `status:accepting` の付いたものの件数とポイントを出す。
1件以上あれば、`AskUserQuestion` で先に `sprint-review` を行うかを聞く。推す案は「先に `sprint-review` を行う」（`docs/development.md` の「開発の流れ」の 9）。
行うと答えたら、Skill ツールで `sprint-review` を起動し、終わってから手順 1 の Issue を引き直す。見送ると答えたら、受け入れ待ちのまま持ち越し、締めのコメントに見送ったことを書く。

### 3. 締めの数を出す

手順 2 で引いた Issue から、`docs/development.md` の「スプリントとポイント」の数え方で、計画、計画の済み、途中で足した分、途中で足した分の済み、取り下げ、受け入れ待ち、持ち越し、ベロシティを出す。計画のポイントは記録の Issue の本文の値を使い、今のラベルからは数えない。`duplicate` で閉じた計画の Issue は `not_planned` と同じく取り下げに、スプリントの間に `sprint:<番号>` を外して締めの前に受け入れで閉じた計画の Issue は、取り下げでなく計画の済みに数える。

持ち越しとバックログに戻すものは、手順 5 の人の答えで決まるので、締めのコメントに書く数は手順 5 の後に分ける（持ち越しは次へ付け替えるもの、バックログに戻すものは取り下げ）。

直近のベロシティは、この締めのベロシティと、ほかの記録の Issue の締めのコメントの `ベロシティ:` の行を、新しい順に3つまで並べる。締めのコメントの無い記録は飛ばす。

```bash
gh api "repos/{owner}/{repo}/issues?labels=sprint-log&state=closed&per_page=5&sort=created&direction=desc" --jq '.[] | {number, title}'
```

### 4. 候補を並べる

次の順で候補を並べ、表にして見せる（番号、題、ポイント、入れる理由）。

1. 持ち越し（手順 3）。受け入れ待ちのものは作業が無いので入れる案にし、人が受け入れで閉じれば済みに入る
2. `backlog-pick` の手順 1 と 2 の分け方で「着手できる」に入る Issue。マイルストーン「初版」を先に、親のサブ Issue の並び（作る順）で並べる
3. 「待ち」の Issue のうち、待っている前に要るものがすべて候補に入るもの

`sprint-log` の Issue、子を持つストーリーとエピック、人が行う Issue（題が「確認:」で始まる、要件を決める、本番やアカウントやドメインの操作）は候補に入れない。

`pt:` の無い候補は、本文の「やること」と完了条件から見積もりの案（1、2、3、5、8）を置き、理由を1行添える。8 を超えると見たものは候補から外し、`backlog-add` で分ける案にする。

合計の案は、直近のベロシティの平均を目安に、候補の上から切る。最初のスプリントは比べるものが無いので、直近7日に受け入れで閉じた末端の Issue の件数を添え、合計は人に決めてもらう。

### 5. 人と決める

`AskUserQuestion` で次を聞く。候補が多く選択肢に並ばないので、選択肢は案のまとまりにし、細かい直しは「Other」のメモで受ける。

- 入れる Issue とポイント: 推す案（手順 4 の切り方、番号と合計を書く）、持ち越しだけ、の2つ。番号の足し引きとポイントの直しはメモで受ける。ポイントを直せるのは、持ち越しでない Issue だけ
- ゴール: 入れる Issue から1文の案を置く
- 持ち越さない開いた Issue があれば、`sprint:<番号>` を外してバックログに戻すか

人に聞けない実行では、ここで止まり、案だけを出す。

### 6. GitHub に書く

人の答えのとおりに、次の順で書く。締めの数を先に記録の Issue に残し、どこで落ちても手順 1 から続けられるようにするため。

書き始める前に、持ち越しと入れる Issue の状態を1件ずつ引き直す（`gh api repos/{owner}/{repo}/issues/<番号> --jq '{state, state_reason, labels: [.labels[].name]}'`）。人が考えている間に受け入れで閉じたものがあれば、締めの数を出し直し、次の計画からその Issue を外し、変わった数を人に伝えてから書く。

1. 前の記録の Issue に締めのコメントを足す（最初のスプリントと、締めのコメントが既にあるときは飛ばす）。数は手順 3 で出したもの

   ```markdown
   ## 締め（<日付>）

   | 数 | ポイント | 件数 |
   | --- | --- | --- |
   | 計画 | <数> | <数> |
   | 計画の済み | <数> | <数> |
   | 途中で足した分 | <数> | <数> |
   | 途中で足した分の済み | <数> | <数> |
   | 取り下げ | <数> | <数> |
   | 受け入れ待ち | <数> | <数> |
   | 持ち越し | <数> | <数> |

   ベロシティ: <計画の済みと途中で足した分の済みの合計>
   持ち越し先: スプリント <次の番号>（#<番号>、#<番号>）
   バックログに戻した: #<番号>
   受け入れ: <行った / 見送った>
   ```

   ```bash
   gh api repos/{owner}/{repo}/issues/<前の記録の番号>/comments -F body=@<file> --jq .html_url
   ```

2. 次の記録の Issue を作る。本文はスクラッチパッドのファイルに書いてから渡す

   ```bash
   gh api repos/{owner}/{repo}/issues -f title="スプリント <番号>（<開始日>〜<終了日>）" -F body=@<file> -f 'labels[]=sprint-log' --jq '{number, url: .html_url}'
   ```

   本文の形。計画の表は後の数え方が番号、題、ポイントの列を読み、PR の列は読まない。PR の列は人が見るためのもので、計画のときは空にし、人が入れるときの書き方は問わない。題に `|` があれば `\|` にする

   ```markdown
   ## ゴール

   <1文>

   ## 期間

   <開始日>〜<終了日>

   ## 計画

   | 番号 | 題 | ポイント | PR |
   | --- | --- | --- | --- |
   | #<番号> | <題> | <数> | |
   | 合計 | | <数> | |
   ```

3. スプリントのラベルを作る。既にあれば（422）作らずに進む

   ```bash
   gh api repos/{owner}/{repo}/labels -f name="sprint:<番号>" -f color=BFD4F2 -f description="<開始日>〜<終了日> 記録 #<記録の番号>"
   ```

4. 入れる Issue にラベルを付ける。付けてから、持ち越すものの前の `sprint:<番号>` を外す（外す対象が無い 404 は無視して進む）。ポイントは記録の計画の値にそろえ、それと違う `pt:` はすべて外して、`pt:` が1つだけになるようにする（途中で落ちて再開したときも同じ）。書き始める前の引き直しの後に閉じた Issue があれば、付けずに、記録の本文の計画の一覧からその行を外して合計を直す（`gh api -X PATCH repos/{owner}/{repo}/issues/<記録の番号> -F body=@<file>`）

   ```bash
   gh api repos/{owner}/{repo}/issues/<番号> --jq '{state, labels: [.labels[].name]}'
   gh api -X POST repos/{owner}/{repo}/issues/<番号>/labels -f 'labels[]=sprint:<番号>' -f 'labels[]=pt:<数>'
   gh api -X DELETE repos/{owner}/{repo}/issues/<番号>/labels/sprint%3A<前の番号>
   ```

   バックログに戻すと答えた Issue は、前の `sprint:<番号>` を外すだけにする。

5. 前の記録の Issue を閉じる（最初のスプリントでは飛ばす）

   ```bash
   gh api -X PATCH repos/{owner}/{repo}/issues/<前の記録の番号> -f state=closed -f state_reason=completed
   ```

書いた後に、次で付いたラベルを確かめる。各 Issue の `pt:` が1つだけで、記録の Issue の計画の値と一致することも見る。

```bash
gh api "repos/{owner}/{repo}/issues?labels=sprint:<番号>&state=all&per_page=100" --paginate --jq '.[] | {number, labels: [.labels[].name]}'
```

## 出力

- 締めた数と、前の記録の Issue の URL
- 次のスプリントのゴール、期間、入れた Issue とポイントの合計、記録の Issue の URL
- 締めの後は `retro` でスプリントを振り返れることと、手元のセッションなら `daily-scrum` で開発ボードを出し直せることを添える

## 止まる条件

- 手順 1 の表の「それ以外」に当たる
- 人に聞けない実行で、手順 5 に来た
- `gh api` が失敗し、MCP ツールでも代えられない。失敗したコマンドと応答を出す
