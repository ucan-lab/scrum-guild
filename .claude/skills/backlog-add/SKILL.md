# backlog-add

## GitHub の操作

Issue の読み書きは `gh api` の REST で行う。クラウドのセッションでは、GraphQL を使う `gh issue` が 403 で止まるため。
`{owner}` と `{repo}` は `gh` がカレントのリポジトリに置き換える。置き換わらずに 404 になるときは、`git remote get-url origin` から owner と repo を読んで直に書く。
`gh` が無いか認証で失敗するときは、`pr-create/github-mcp.md` に従い、GitHub の MCP ツールで代える（Issue の作成は `issue_write` の `create`。作るときに `parent_issue_number` を渡せば親につながり、既にある Issue をつなぐときだけ `sub_issue_write` を使う。前に要るものは `issue_dependency_write`）。

## 手順

要件が固まったあと、着手前に実装計画を Issue に書く。

### 絶対にやらないこと

- ソースコードを変更しない（理由: 計画が決まる前に手を動かすと、計画がコードの後追いになる）
- 完了条件を書かずに計画を出さない（理由: 後工程の done-check と CI の AI レビューが判定できなくなる）
- 影響範囲を調べずに書かない（理由: 呼び出し元を見落とすと、着手後に計画ごと崩れる）
- 最初に思いついた案をそのまま計画にしない（理由: 1 案しか見ていない状態では、その案の代償が見えない）
- 1 つの Issue に収まらない量を 1 つに詰めない

### 1. 要件を確認する

`docs/` の要件と関係する文書（`requirements.md`、`data-model.md`、`design.md`、`development.md`）を読む。
確認が要る点が残っているなら、計画に入る前に潰す。
`docs/` で決まっている点は潰さずに、計画の「背景」に前提として書く。
既にある Issue の計画を書くときは、ここでその Issue に `status:refining` を付ける（`docs/development.md` の「Issue の状態」）。`gh api repos/{owner}/{repo}/issues/<番号> --jq '[.labels[].name]'` で `status:in-progress` が無いことを確かめてから、`gh api -X POST repos/{owner}/{repo}/issues/<番号>/labels -f 'labels[]=status:refining'` で付ける。新しく立てる Issue には付けない。

### 2. 影響範囲を調べる

変更対象のコードを開いて、次の 3 つを押さえる。

- 変更する関数やクラスの呼び出し元
- 壊れる可能性のある既存のテスト
- 設定値、環境変数、DB スキーマへの波及

参照側のガード（三項演算子、early return、テンプレートの条件分岐）まで読む。

### 3. 案を 2 つ並べて選ぶ

実装方針が 1 通りに定まらない変更では、対案を 1 つ出して比較してから選ぶ。

1. 自分の案を、やること、データの持ち方、影響範囲の 3 点で 5 行以内にまとめる。
2. 別のサブエージェントに同じ論点を渡して独立に案を出させる。手元で `ucan:fable-advisor` が使えればそれを、使えなければ（クラウド）Agent ツールの汎用のサブエージェントを使う。渡すのは「判断したい論点」「関連ファイル」「制約と完了条件」の 3 つ。**自分の案は渡さない**（理由: 渡すとその案の追認になり、対案として機能しない）。
3. 2 案を突き合わせ、割れた点だけを比較する。軸は、既存コードとの整合、壊れる範囲の広さ、後から変えやすいか。
4. 採用案と、却下した案とその理由を次の手順の「背景」に 1 行ずつ残す。
5. **決着しなければ割れたままユーザーに渡す**。どちらを採るかで完了条件が変わるのに決め手が無いときは、`AskUserQuestion` で 2 案を並べて判断を仰ぐ。理由を後付けして片方に寄せない（理由: 比較を通した体裁だけ整えた計画は、1 案で書いた計画より始末が悪い）。

飛ばしてよいのは、変更が 1 箇所で完結し、書き方の選択肢が実質 1 つしかないとき。飛ばしたときはその旨を 1 行書く。

### 4. 計画を書く

Issue はエピック、ストーリー、タスクの3階層で書く（`docs/development.md` の「Issue の運用」）。書き始める前に、書く Issue の階層と親を決める。

| 書くもの | 当てはまるとき | 親 | 形 |
| --- | --- | --- | --- |
| エピック（`epic`） | 確かめられるふるまいが2つ以上まとまる | 無し | 下の 6 つ。「やること」に子のストーリーの並ぶ順と前に要るものを書く |
| ストーリー（`story`） | 確かめられる1つのふるまい。1つの PR に収まるときもストーリーにする。土台の作業（マイグレーション、入口、CI）は、運用者か開発者が確かめられるふるまいを受け入れ条件にした土台のストーリーにまとめる | エピックか無し | `.github/ISSUE_TEMPLATE/story.md`。タスクに分けないときは「やること」「確認方法」「マイグレーション」も書く |
| タスク | ストーリーの中の、1つの PR で入れる変更 | ストーリー。不具合と単発の作業は無し | 下の 6 つ（`.github/ISSUE_TEMPLATE/plan.md`） |

タスクをエピックの直下に置かない（理由: Scrum Guild の木で、タスクの親は無しかストーリーと決まっている。`docs/requirements.md` の「概念」）。
親は、開いている `epic` と `story` の Issue から選ぶ（`gh api "repos/{owner}/{repo}/issues?labels=epic&state=open" --jq '.[] | {number, title}'`、`story` も同じ）。合う親が無ければ、親の案も一緒に書く。

タスクとエピックに書くのは次の 6 つ。

| 見出し | 中身 |
| --- | --- |
| 背景 | なぜやるか。要望と要件へのリンク |
| やること | 変更する対象と、どう変えるか |
| 完了条件 | 満たされたかを他人が判定できる形で書く |
| 確認方法 | 動作確認の手順 |
| 触る領域 | 付ける `area:` のラベル。人が差分を読む領域（`docs/development.md` の「マージの判定」）なら `needs-human` も |
| マイグレーション | 有りか無しか。有りなら `migration` のラベル |

### 5. 詰める

決まっていない分岐が残っていれば backlog-refine を使って 1 つずつ潰す。
分岐が多すぎて 1 セッションで潰し切れないなら、`wayfinder` で地図を作ってから戻る。

### 6. 大きければ分割する

次のどれかに当てはまったらサブ Issue に分ける。

- 完了条件が 2 つ以上の独立した機能にまたがる
- 別々の人が並行して着手できる
- レビューする差分が読み切れない量になる

分ける先は1つ下の階層にする。エピックはストーリーに、ストーリーはタスクに分ける。分けた元が1つ下の階層の大きさだったときは、手順 4 の表で階層を決め直す。

- ストーリーの受け入れ条件は、確かめる人（利用者、運用者、開発者）から見えるふるまいで、本番か e2e で確かめられる形で書く。テーブルや関数の名前で書かない（理由: ストーリーは人が受け入れる単位で、技術の言葉で書くと人が確かめられない）
- 1つの PR で収まるストーリーは、タスクに分けない
- 親には、子の並ぶ順と前に要るもの、全体の完了条件を残す

### 7. 登録する

投稿の前にユーザーに内容を確認する。

親から先に作る。子をつなぐには親の番号が要るため。

```bash
gh api repos/{owner}/{repo}/issues -f title="<件名>" -F body=@<file> -f 'labels[]=<名前>' -F milestone=<番号> --jq '{number, id, url: .html_url}'
```

本文はファイルに書いてから渡す（理由: シェルで組むと改行が潰れる）。既にある Issue の本文は `gh api -X PATCH repos/{owner}/{repo}/issues/<番号> -F body=@<file>` で直す。
ラベルは、「触る領域」と「マイグレーション」で決めたものと、階層のもの（エピックは `epic`、ストーリーは `story`、タスクには階層のラベルを付けない）を付ける。マイルストーンは入るリリースのものを付ける。番号は `gh api repos/{owner}/{repo}/milestones --jq '.[] | {number, title}'` で引く。

子は親のサブ Issue としてつなぐ。渡すのは子の番号ではなく、REST の `id`（作成の応答の `id`、または `gh api repos/{owner}/{repo}/issues/<子の番号> --jq .id`）である。

```bash
gh api repos/{owner}/{repo}/issues/<親の番号>/sub_issues -F sub_issue_id=<子の id>
```

- サブ Issue は足した順に並ぶ。着手する順に足す
- 子が既に別の親を持つと 422 になる。付け替えるときは `-F replace_parent=true` を足す
- つないだ後に `gh api repos/{owner}/{repo}/issues/<親の番号>/sub_issues --jq '.[].number'` で並びを確かめる

本文の表で子を並べるだけにしない（理由: サブ Issue でつながないと、GitHub の親の進み具合に出ない）。

前に要るものは、待つ側の Issue に依存関係（blocked by）でつなぐ。渡すのは前に要る Issue の REST の `id`（`gh api repos/{owner}/{repo}/issues/<番号> --jq .id`）。

```bash
gh api -X POST repos/{owner}/{repo}/issues/<待つ側の番号>/dependencies/blocked_by -F issue_id=<前に要る Issue の id>
```

- 前に要る Issue が決まったら、本文に表があるかに関わらずすべてつなぐ（理由: `backlog-pick` は依存関係だけを読んで着手できるかを決め、本文の表を読まない。つなぎ忘れた Issue は着手できる扱いになる）
- ストーリーをタスクに分けたら、ストーリーが待つものを、最初に着手するタスクにもつなぐ
- 閉じた Issue はつながなくてよい。開いていて `status:accepting`（受け入れ待ち）の無い依存だけが着手を止める。受け入れ待ちの Issue は、待つ側に着手させてよいので、つないだまま残す
- つなぎ間違えたら `gh api -X DELETE repos/{owner}/{repo}/issues/<待つ側の番号>/dependencies/blocked_by/<前に要る Issue の id>` で外す
- つないだ後に `gh api repos/{owner}/{repo}/issues/<待つ側の番号>/dependencies/blocked_by --jq '[.[].number]'` で確かめる
