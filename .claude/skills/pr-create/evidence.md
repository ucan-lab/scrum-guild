# エビデンス節の確かめ（前に立てた PR）

`pr-create` は、PR の本文に画像を載せず、`## エビデンス` 節も書かない（2026-10-29 に決めた。クラウドのセッションは画像を上げられず、本文を書く GitHub の MCP の書き込みは `<img>` を逃がすため）。変更前と変更後の画像は、CI の `evidence` のジョブが PR に付けるコメント（見出しは「e2e の画面の差分」）で見る。

この文書は、決める前に立てた PR で本文に `## エビデンス` 節が残っているときにだけ使う。CI の段「PR の本文に画像を埋め込む」は、節の無い本文を書き換えない。前は 1 で画面を決め、2 で節を書いていたので、残した手順の番号は 3 のままにする（`pr-feedback` と `.github/workflows/ci.yml` が「3」で指すため）。

## 3. 画像の埋め込みを確かめる

画像は CI の `evidence` のジョブが埋め込む。コメントを書き換えた後の段「PR の本文に画像を埋め込む」が [embed-evidence.py](embed-evidence.py) を走らせ、出力が「本文を書き換える」なら本文を書き換え、取り直した本文を `--check` で確かめる。埋め込めないとき（下の 2 の理由のどれか）は本文を書き換えずに成功で終わる。前の push のコメントのまま走ったときに、理由の文で前の画像を消させないため。付かなかった理由の文はセッションが書く。

セッションは `pr-feedback` の手順 5 で、check-runs がすべて `completed` になった後に確かめる。push のたびに毎回行う。本文の `<!-- evidence: <SHA> -->` が今の head と同じでも飛ばさない（同じコミットで CI を走らせ直すと画像が変わることがあり、本文に印を足しても SHA は変わらないため）。

1. コメント、本文、PR の head の SHA を取る。本文は書き換える直前に取り直す（人や他のセッションの編集を消さないため）

   ```bash
   gh api "repos/{owner}/{repo}/issues/<n>/comments" --paginate --slurp > "<スクラッチパッドの絶対パス>/evidence-comments.json"
   gh api "repos/{owner}/{repo}/pulls/<n>" --jq .body > "<スクラッチパッドの絶対パス>/pr-body.md"
   gh api "repos/{owner}/{repo}/pulls/<n>" --jq .head.sha
   ```

2. スクリプトを走らせて報告を見る。`evidence` のチェックが成功し、報告に「埋め込めない」が出ていなければ、CI が埋め込んだ後なので、最後の行は「本文は変わらない」になるはず（「埋め込めない」が出たら 4）

   ```bash
   python3 -I <このディレクトリの絶対パス>/embed-evidence.py <本文> <コメント> <出力> <head の SHA> [<付かなかった理由>]
   ```

   スクリプトは、コメントの目印 `<!-- e2e-evidence -->` の次の行の JSON（`<!-- e2e-evidence-data {...} -->`。`scripts/evidence.ts` の `evidenceData`）を読み、`## エビデンス` 節の中だけを書き換える。印ごとに画像の表を入れ、`<!-- evidence: ... -->` を head の SHA にし、コメントへのリンクを入れる。次のときは画像を入れず、印の中に「CI の画像は付かなかった: <理由>」と書く。前の push で画像を入れた印は消さずに残す（節の `<!-- evidence: <SHA> -->` がその画像の head を示す）
   - コメントが無い、またはコメントに JSON の行が無い
   - コメントの `headSha` が今の head と違う（前の push のコメントが残っている）
   - CI が比べられなかった（`comparedSha` が `null`）
   - 付かなかった理由を渡した

3. `evidence` のチェックが成功していないときは、最後に付かなかった理由を渡して走らせ直す。CI は理由の文を書かないので、ここで書く
   - チェックが失敗した: ジョブの注記とログから理由を取る（例 `evidence のジョブが失敗した`）
   - チェックが無いか `skipped`: `evidence` が動かない PR（文書だけ、fork、Bot の PR）。例 `evidence が動かない PR（文書だけの差分）`
   - 成功したが上げる先の用意が無い（ジョブの注記「e2e の画像を上げない」）: コメントが付かず、埋め込む段も飛ぶので、注記の文を理由に渡す

   出力の最後の行が「本文を書き換える」のときだけ、`gh api -X PATCH repos/{owner}/{repo}/pulls/<n> -F body=@<出力>` で書き換える。書き換えると `label` のワークフロー（`edited` で動く）が走るので、check-runs を取り直し、`label` が `completed` になるまで待つ（CI の書き込みは `GITHUB_TOKEN` なので `label` を起こさないが、セッションの書き込みは起こす）
4. `evidence` のチェックが成功したのに「本文を書き換える」と出たら、報告の先頭の行で分ける
   - 「埋め込めない: <理由>」: コメントが無い、JSON の行が無い、比べられなかった、URL の形が違うなどで、CI の段は本文を書き換えずに終わっている。出力の印の中は理由の文になっているので、3 と同じく書き換える
   - 「埋め込んだ画面: ...」: CI の段「PR の本文に画像を埋め込む」のログを見て理由を確かめる（例 段の後に人が本文を編集した、段が落ちた）。手元のセッション（`gh` が使える）なら、3 と同じく `gh api -X PATCH` で書き換えてよい。クラウドのセッション（MCP の経路）では、画像を含む出力を書き戻さず、理由を説明資料に書く

   クラウドのセッションは、どちらでも、書き換える直前に取り直した本文に `<img` があれば書き戻さない（書き戻すとその画像が逃がされる）。人に手元の `gh` で書き換えてもらう（5 の終わりのとおりコマンドと出力を渡す）
5. 本文を書き換えた後は毎回、本文を取り直してファイルに書き、`--check` を走らせる。終了コードが 1 なら、`<img>` が `&lt;img` に逃がされている

   ```bash
   python3 -I <このディレクトリの絶対パス>/embed-evidence.py --check <取り直した本文>
   ```

   MCP の経路で理由の文を書き戻すとき、前の push の画像が本文に残っていると（スクリプトは前の画像を消さずに残す）、その画像が逃がされる。崩れたら、次の push の CI が埋め直す。push しないなら、人に手元の `gh` で直してもらう（`gh api -X PATCH repos/{owner}/{repo}/pulls/<n> -F body=@<出力>` のコマンドと、出力のファイルの中身を渡す）
6. スクリプトが出した次のものを、`pr-feedback` の説明資料の「確かめたこと」に書く
   - コメントに出たのに印の無い画面: PR が変えたと判定していない画面。本文には載せない。揺れか意図しない変更のどちらかなので、画像を見て判断を添える
   - 印があるのにコメントに無い画面: 20 画面の上限を超えたか、e2e がその状態を写していないか、`main` と同じ画像になった。印の中は「出ていない」と書いた文章になる
   - 埋め込めなかった理由

`gh` が使えないセッションは、[github-mcp.md](github-mcp.md) のとおり MCP ツールで代える。コメントは `issue_read` の `get_comments`、本文と head の SHA は `pull_request_read` の `get` で読み、スクリプトの形（コメントはページの配列の配列、本文はファイル）に書き出してから走らせる。書き換えは `update_pull_request` の `body` で行うが、`<img>` を `&lt;img` に逃がすので、画像を入れる書き換えには使わない（画像は CI が入れる）。書き戻した後は `pull_request_read` の `get` で本文を取り直し、ファイルに書いて `--check` を走らせる。
