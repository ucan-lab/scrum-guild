# requirements

## 仕事

Backlog に来たお客さんの要望を、実装に渡せる要件にする。
要望をそのまま書き写さない。何を作れば要望が満たされるかまで落とす。

## 絶対にやらないこと

- Backlog の課題を書き換えない（理由: 正本は Backlog にある。読むだけにして、返信はユーザーが投稿する）
- ソースコードを変更しない（理由: この段階では何を作るかが決まっていない）
- 開いていないコードの挙動を断定しない（理由: 要件を誤ると後工程が全部ずれる）
- 要望に書かれていない機能を足さない（理由: 頼まれていないものを作ることになる）

## 入力

Backlog の課題キー（例 `ABI-123`）。

## 手順

### 1. 課題を読む

```
mcp__backlog-abi__get_issue          issueIdOrKey: <課題キー>
mcp__backlog-abi__get_issue_comments issueIdOrKey: <課題キー>
```

dg のスペースなら `mcp__backlog-dg__` を使う。
コメント欄で要望が変わっていたり補足が付いていることが多いので必ず読む。

### 2. 要望と要件を分ける

| 区分 | 中身 |
| --- | --- |
| 要望 | お客さんが書いた「こうしたい」 |
| 要件 | それを満たすために作るもの |

要望から要件が一意に決まらないところを洗い出す。ここが確認事項になる。

### 3. 技術的な懸念を調べる

既存の実装がどうなっているかを、コードを開いて確認する。
押さえるのは影響範囲、既存の挙動、制約の 3 つ。

参照側のガード（三項演算子、early return、テンプレートの条件分岐）まで読んでから影響を判断する。

### 4. 決まらないところを詰める

grill-me を使って、決定が要る分岐を 1 つずつ潰す。

### 5. まとめる

要件、影響範囲、確認が要る点を分けて書く。
Backlog に返す文面にするときは shiwake を使う。投稿はユーザーが行う。

### 6. issue-plan に引き継ぐ

お客さんに確認が要る点が無ければ、Skill ツールで `issue-plan` を書くモードで起動し、手順 5 の出力を渡す。

確認が要る点が残っていれば、`AskUserQuestion` で次のどちらにするか聞く。

- お客さんの回答を待って止まる
- 確認が要る点を計画の前提として明記し、issue-plan に進む

## 出力

- 要件の一覧
- 影響範囲（変更が要るファイルと機能）
- お客さんに確認が要る点

## 完了条件

- 要望のそれぞれが、要件か「確認が要る点」のどちらかに分類されている
- 技術的な懸念について、コードを読んだ結果が書かれている（推測で埋めていない）

## 止まる条件

- 要望の意図が読み取れない。推測で要件にせず確認が要る点に回す
- 既存の実装が要望と矛盾する。どちらを正とするか確認する
- 要望の範囲が大きく、1 つの要件群に収まらない。分割を提案する
