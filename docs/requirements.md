# scrum-quest 要件定義

状態: 確定。次はデータモデル（D1 のテーブル）と画面構成の設計

## 目的

Backlog や GitHub に散らばったチームのタスクを1か所に集め、次の3つを1つの道具で薄く回す。

- 実行: 今日と今週にやるタスクを選んで進める
- 計画: エピック、ストーリー、ポイントで数週間先まで見通す
- 記録: 何をいつ終えたかを区分と月で残し、振り返りと請求の根拠にする

加えて、ゲームの仕組みで、メンバーが自分からタスクを起票し、詳細を書き、仕事を進めるように促す。リーダーが詳細を書いたり、メンバーから聞き取って書き足したりする手間を減らす。

## 前提

- 正本は scrum-quest。Backlog と GitHub はタスクの入口として使う。
- 初版からチームで使う。ユーザー、ワークスペース、メンバーの招待を初版に含める。
- OSS として公開する。利用者が自分の Cloudflare アカウントに立てられることを前提にし、特定の個人や会社の設定をコードに持たない。
- ライセンスは MIT。GitHub のリポジトリは private で作り、初版ができた時点で履歴と設定を点検してから public にする。

## 技術の前提

| 項目 | 決定 |
| --- | --- |
| 稼働先 | Cloudflare Workers |
| DB | Cloudflare D1 |
| API | Hono |
| 画面 | Svelte の SPA（Vite でビルドし、Workers Static Assets で配る） |
| 認証 | GitHub OAuth |
| 定期処理 | Cron Triggers |

API（`/api/*`）、画面の配信、定期処理を1つの Worker にまとめる。デプロイの単位は1つで、利用者は D1 の作成、シークレットの登録、デプロイの3手順で立てられる。

## 概念

| 概念 | 何か |
| --- | --- |
| ワークスペース | タスクの集まりの単位。チームや用途ごとに作り、メンバーを持つ |
| 接続 | ワークスペースに登録した取り込み元（Backlog のスペース、GitHub のアカウントや組織） |
| エピック | 期日のある成果。ストーリーが複数入る |
| ストーリー | エピックの中で、1スプリントで終わる確認できる区切り |
| タスク | 実際の作業。手で作るか、取り込み元から取り込む |
| スプリント | 月曜始まりの期間 |
| 区分 | エピックに振る分類（保守、追加案件など）。一覧はワークスペースごとに利用者が定義する |

取り込んだタスクも手で作ったタスクも、同じ1つのタスクとして DB に持つ。違いは取り込み元への参照を持つかどうかだけにする。

## メンバーと権限

会社にたとえると、立てた scrum-quest 全体が会社、ワークスペースがチーム、オーナーがチームリーダー、管理者が社長にあたる。

ワークスペースのメンバーは、ワークスペースごとにオーナーとメンバーのどちらかのロールを持つ。1人が複数のワークスペースでオーナーになれる。

| ロール | できること |
| --- | --- |
| オーナー | メンバーができることに加え、ワークスペースの設定（列、詳細の決まった欄、タイムゾーン、ポイントの換算比率、休日）、メンバーの配分、接続、メンバーの管理 |
| メンバー | タスク、ストーリー、エピック、スプリントの操作 |

- ワークスペースのロールとは別に、立てた scrum-quest 全体の管理者を置く。立てた人として設定で指定した GitHub ユーザーは管理者で、管理者は別のユーザーを管理者に指名できる。管理者は、所属していないワークスペースも含めてすべてのワークスペースを見られ、オーナーと同じ操作ができる。
- オーナーは GitHub のユーザー名でメンバーを招待する。招待した人が GitHub でログインすると、そのワークスペースのメンバーになる。ユーザー名は変えられるため、招待のときに GitHub のユーザー ID に解決して突き合わせる。
- ログインできるのは、立てた人として設定で指定した GitHub ユーザーと、いずれかのワークスペースに招待された人だけ。ログインできる人は新しいワークスペースを作れ、作った人がそのオーナーになる。

## 取り込み

- 対象は Backlog の課題、GitHub の Issue、PR、レビュー依頼。
- Cron Triggers で定期的に取り込み元を読み、DB に保存する。画面を開いたときに取り込み元を叩かない。
- 接続ごとに、取り込む範囲を Backlog のプロジェクト、GitHub のオーナーやリポジトリの単位で絞れる（対象を挙げるか、除外を挙げる）。
- 新しく取り込んだタスクは受信箱に入る。利用者は受信箱から、バックログへ入れるか、アーカイブするかを選ぶ。
- アーカイブしたタスクは一覧と受信箱に出さない。同期で取り込み元の属性は更新するが、取り込み元で完了しても通知しない。アーカイブの一覧から受信箱へ戻せる。
- 取り込み後は、取り込み元が持つ属性（タイトル、取り込み元での状態、期限、URL）だけを同期で更新する。scrum-quest が持つ属性（列、スプリント、親、ポイント、期日、担当）は同期で書き換えない。
- 取り込んだタスクをスプリントに入れたときの列は、接続ごとに設定する「取り込み元の状態から列への対応」で決める。対応のない状態は先頭の列に置く。完了の列は対応先にしない。
- 取り込み元で完了したタスクは自動で完了にせず、「取り込み元で完了」の印を付けて担当者（いなければ接続の登録者）に通知する。受信箱にあるタスクは印だけ付けて通知しない。完了にするかは利用者が決める。
- 取り込み元で開き直されたら印を外す。scrum-quest で完了にしたタスクが開き直されたときは担当者に通知する。
- 取り込み元には書き戻さない。
- 接続はワークスペースに属し、登録したメンバーの認証情報でその人の担当分を取り込む。取り込んだタスクは取り込んだ時点で登録したメンバーが担当になり、その後は scrum-quest で担当を替えられる。取り込んだタスクはワークスペースの全員が見られる。
- 取り込んだタスクは、種別（Backlog の課題、GitHub の Issue、PR、レビュー依頼）、取り込み元の不変の ID（課題キーや番号のように移動で変わるものではない ID）、取り込み元の応答そのもの（JSON）を持つ。
- 取り込み済みの項目は、取り込み元で担当が外れても、取り込む範囲の外へ移っても、不変の ID で取りに行って同期を続ける。削除や権限の喪失で取れなかった項目には「取り込み元で見つからない」の印と最後に確認できた日時を付け、担当者に知らせる。接続の取得そのものが失敗したときは、その接続の項目を動かさない。
- 同じワークスペースでは、同じ取り込み元の項目を1件のタスクにまとめる。一意のキーはワークスペース、取り込み元の不変の ID、種別の組。担当は最初に取り込んだ接続の登録者。レビュー依頼だけはレビュアーごとに別のタスクにする。
- 同じ項目が別々のワークスペースに入ることは許し、それぞれ独立したタスクにする。重ならないよう取り込む範囲を絞るのは運用に任せる。
- 接続の認証情報（Backlog の API キーなど）は暗号化して DB に保存する。
- 取り込み元は共通の型で実装する。型が持つのは、接続の設定項目、取り込み元からの取得、取り込み元の状態の一覧、タスクへの変換。Backlog と GitHub もこの型で実装し、新しい取り込み元はこの型の実装をリポジトリに足して加える。

## ゲームの仕組み

- 協力型にする。チームの目標はクエストのクリアで、メンバー間の順位は出さない。
- 見立ては冒険者ギルド。エピックはギルドの掲示板に貼るクエスト、ストーリーはその達成目標、タスクは目標をこなすためのミッション。
- クエストはメンバーの誰でも掲示でき、掲示した人が依頼主としてクリア報酬（経験値）を決める。額は決まった段階（小、中、大など）から選び、各段階の値は固定。クリアまで変えられ、変えたらパーティに知らせる。
- クエストに参加するメンバーがパーティ。メンバーが自分で受注して加わるほか、依頼主がメンバーを割り振れる。配下のタスクの担当になった人も自動でパーティに加わる。依頼主自身もパーティに入れる。
- 割り振られた人はすぐにパーティに入り、本人に知らせが届く。パーティからはいつでも自分で抜けられる。
- クリア報酬は、クリアした時点のパーティ全員に同額。行動ごとの経験値とは別に、クエストのクリアで払う。
- クリア報酬の変更、パーティへの割り振り、クエストのクリアと中止ができるのは、依頼主とオーナー（管理者を含む）。
- 依頼主がワークスペースを離れても、依頼主の表示は離脱済みとして残る。依頼主の操作はオーナーが代わりに行い、オーナーは依頼主を別のメンバーに替えられる。
- クエストは中止できる。中止したクエストにクリア報酬は出ないが、確定済みの経験値は残る。期日を過ぎても色で示すだけで、失敗の状態は設けない。
- 画面の言葉づかいは、ワークスペースの設定で「ゲームの言葉」（クエスト、達成目標、パーティ、依頼主、受注）と「スクラムの言葉」（エピック、ストーリー、参加者、作成者、参加）を切り替えられる。既定はゲームの言葉。切り替わるのは言葉だけで、経験値や報酬の仕組みはどちらでも同じ。
- 見た目は業務の道具として落ち着いたもの。ゲームらしさはアイコンとクリア時の短い演出にとどめる。
- DB と API の名前はスクラムの言葉（epic、story、task）。
- 個人の成長は経験値などで見せる。
- 経験値は付与の明細（行動、受け取った人、ワークスペース、タスク、値、確定日時）で持ち、合計は明細から出す。同じ付与の重複は一意制約で防ぐ。
- 経験値はワークスペースごとに貯まる。本人は、所属するすべてのワークスペースの合計も見られる。
- 報酬を与える行動は次の4つ。
  - タスクの起票
  - タスクの詳細を書く
  - タスクやストーリーを完了する
  - レビューや手助け
- レビューは、取り込んだレビュー依頼のタスクを完了にしたときに数える。
- 手助けは、タスクの担当者が助けてくれたメンバーに「感謝」を送ったときに数える。自分には送れず、同じタスクで同じ相手に送れるのは1回だけ。
- 経験値は行動ごとに固定の値を付ける。起票と詳細の経験値が確定するのは、スプリントを終えた時点でそのスプリントに入っていたタスクだけで、途中で外したタスクやスプリントに入らない起票は報われない。同じタスクの同じ行動で有効な付与は1回だけ。
- ストーリーとエピックは、配下がすべて完了したら手で完了にできる。記録するのは完了日時と完了にした人。
- ストーリー完了の経験値の受け取り手は、配下のタスクで完了の経験値を受け取った人全員（1人1回ずつ）。
- 起票の経験値は手で作ったタスクにだけ付き、作った人のものになる。取り込んだタスクには起票者がいない。
- タスク完了の経験値は完了した時点の担当者に、担当がいなければ完了にした人に付く。
- 完了を未完了に戻したら、完了の経験値を打ち消しの明細で取り消し、もう一度完了にしたら付け直す。
- 経験値の付いたタスクは、削除やアーカイブをしても経験値が残るよう論理削除で扱う。
- ゲームの点数はストーリーポイントと別に持つ。ストーリーポイントは見積もりと請求の根拠に使うため、報酬に結び付けない。

## 体力（作業量の把握）

メンバーの作業量が基準から外れていないかを、スプリントの計画時と月の単位で気付けるようにする。表示で知らせるだけで、スプリントに入れる操作は止めない。

- 作業量は、メンバーが担当するタスクのポイントを時間に換算して出す。換算の比率（1ポイント = 何時間）はワークスペースで設定する。
- 基準はワークスペースではなくユーザーに持たせる。既定は月 160 時間、許容幅は ±20 時間で、短時間勤務などは本人が自分の基準を変えられる。
- 月の途中で稼働を始めた、または終えた月は、ユーザーの稼働開始日から稼働終了日までの稼働日で基準を按分する。ワークスペースへの参加日と離脱日も按分の対象。
- 按分でも合わない月に備え、本人がその月のユーザーの基準を時間で上書きできる。
- メンバーは複数のワークスペースに所属できる。ワークスペースごとに、そのメンバーの月ごとの配分（30% など）を持つ。
  - 配分はそのワークスペースのオーナーが決める。
  - その月の配分が未設定なら、直近に決めた配分を引き継ぐ。一度も決めていなければ 100%。
  - ワークスペースでの基準と許容幅は、ユーザーの基準と許容幅に配分を掛けた値。30% なら基準 48 時間、許容幅 ±6 時間。
  - 配分の合計が 100% を超えた月は、本人にだけ知らせる。オーナーには他のワークスペースの配分を見せない。管理者は、全ワークスペースの配分の合計と体力の合計を見られる。
  - 本人は、所属するすべてのワークスペースの作業量の合計を、ユーザーの基準と並べて見られる。
- 稼働日は月曜〜金曜から、ワークスペースに登録した休日と、本人が登録した休みを除いた日。休みはユーザーに持たせ、所属するすべてのワークスペースに効かせる。
- ワークスペースでの月の基準を、その月の稼働日数で割って1日あたりの基準を出す。
- スプリントでは、スプリントに入れた担当タスクの換算時間を、期間中の稼働日ぶんの基準と比べる。
- 月では、その月に重なるスプリントの換算時間を、稼働日の割合で月に振り分けて合計し、月の基準と比べる。
- 基準に許容幅を足した量を超えたら超過、引いた量を下回ったら余力ありとして色で示す。
- ポイントが振られていない担当タスクは時間に数えず、件数を添えて示す。
- ワークスペースでの体力は、そのワークスペースの全員が見られる。

## 機能

### 初版

- 受信箱: 新しく取り込んだタスクを並べ、バックログへ入れるかアーカイブするかを選ぶ
- アーカイブ: 自分のチームで扱わない取り込んだタスクを退け、必要なら受信箱へ戻す
- バックログ: エピック、ストーリー、タスクの木で並べる
- スプリント: 月曜始まりで長さは1〜4週。その回だけ伸ばすこともできる。終わらなかったタスクは次へ持ち越す
- 列: ワークスペースごとに利用者が定義する。完了の列だけは固定で持つ
- 担当: タスクに担当を0〜1人持つ。手で作ったタスクの既定は担当なし
- ポイント: タスクにフィボナッチ（1、2、3、5、8、13）で振り、階層ごとに合計を出す
- 期日: タスク、ストーリー、エピックに振る
  - 表示する期日は1つ。scrum-quest で振った期日があればそれを、なければ取り込み元の期限を出す
  - 期日を過ぎたら赤、今週（月〜日）中なら橙で出す。完了したタスクは色を付けない
  - 期限を運用していない取り込み元のために、接続ごとに取り込み元の期限を無視する設定を持つ
  - 今日と今週の判定は、ワークスペースに設定したタイムゾーンで行う
- 詳細: タスクに、決まった欄、本文（Markdown）、コメントを持つ。取り込んだタスクにも書ける
  - 決まった欄はワークスペースごとに利用者が定義する。既定は「完了条件」の1つ
  - 「詳細を書いた」の報酬は、スプリントを終えた時点で決まった欄がすべて埋まっているかで判定し、最後の欄を埋めた人が受け取る。確定したあとに欄の定義や中身が変わっても、確定した経験値は動かさない
  - 起票者とメンバーのやり取りはコメントに残す
- リンク: エピックと手で作ったタスクに資料の URL を1つ
- 完了日の記録: タスクを完了にした日時を保存する
- 体力: メンバーごとに、スプリントと月の作業量を基準と並べて示す。本人は自分の基準と休みを登録し、全ワークスペースの合計を見られる
- 通知: ユーザーごとの画面内の通知一覧で、既読を持つ。メールや Slack には送らない。知らせるのは、取り込み元での完了と開き直し、取り込み元で見つからないタスク、自分の接続の取り込みの失敗、自分のタスクへのコメント（起票者と担当者へ）、担当への割り当て、パーティへの割り振り、クリア報酬の変更、受け取った感謝
- ゲームの仕組み: 「ゲームの仕組み」の節の内容（経験値、クエストの掲示、クリア報酬、パーティ、受注、感謝、クリア時の演出）をすべて初版に入れる
- 画面の対象: PC のブラウザ。スマホでは表示が崩れない程度にとどめる

### 後回し

- 区分: エピックに振り、配下のストーリーとタスクが引き継ぐ
- 計上月: 月ごとに計上する区分では、タスクに計上月を持つ。既定は完了した月
- PR と課題の紐付け: PR の本文の参照から課題と自動で関連付け、課題の付け先を引き継ぐ
- スクラムの言葉への切り替え。初版はゲームの言葉だけで出す
- スマホ向けの画面: 今日と今週のタスク、受信箱、経験値とチームの目標を見られ、列の移動、起票、受信箱の仕分けができる。バックログの並べ替えと設定は PC で行う
- 振り返りの画面（週ごとの完了ポイントと平均）。完了日は初版から記録するので、後から画面だけ足せる
- スプリントのボス戦。スプリントに入れたポイントの合計をボスの体力にし、完了したタスクのポイントで削る。討伐すると参加メンバー全員にボーナスの経験値が入る
- GitHub リポジトリのディレクトリにある Markdown の取り込み（1ファイルを1タスクにする）。それまでは手で作るタスクで代える

## Non-Goals

- 取り込み元への書き戻し
- 取り込み元で完了したタスクを自動で完了にすること
- 現行 kanban からのデータ移行
- Cloudflare 以外への対応（初版）
- メンバー間の順位付け
