# Scrum Guild 要件定義

状態: 確定。データモデルは `data-model.md`、画面とデザインは `design.md`。

## 名前

Scrum Guild（スクラムギルド）。画面の見出しや文書では `Scrum Guild`、リポジトリ、パッケージ、ドメイン（`scrum-guild.dev`）やコードの中では `scrum-guild` と書く。

scrum-quest、Scrum Guild と改めてきた。経緯、決めた理由、重なりの確認は `naming.md` に残した。

## 目的

チームのタスクを1か所に集め、次の3つを1つの道具で薄く回す。タスクは Scrum Guild で直接作れるほか、課題管理やコード管理の道具（Backlog、GitHub など）に散らばったものを取り込める。

- 実行: 今日と今週にやるタスクを選んで進める
- 計画: エピック、ストーリー、ポイントで数週間先まで見通す
- 記録: 何をいつ終えたかを区分と月で残し、振り返りと請求の根拠にする

加えて、ゲームの仕組みで、メンバーが自分からタスクを起票し、詳細を書き、仕事を進めるように促す。リーダーが詳細を書いたり、メンバーから聞き取って書き足したりする手間を減らす。

## 前提

- 正本は Scrum Guild。取り込み元はタスクの入口として使う。
- Scrum Guild は単体で動く。取り込み元を1つも登録しないワークスペースでも、取り込みにかかわるもの（受信箱、アーカイブ、接続）を除くすべての機能が使える。
- 特定の取り込み元に依存しない。チームによって課題管理は Backlog、Jira、Asana、Notion、コード管理は GitHub、GitLab、Bitbucket などと道具が違うため、取り込み元は共通の型の実装として足す（「取り込み」の節）。初版で用意する取り込み元は Backlog と GitHub。
- 初版からチームで使う。ユーザー、ワークスペース、メンバーの招待を初版に含める。
- 自分たちで運用するサービスとして提供する。OSS としては公開せず、リポジトリは private のままにする。権利はすべて ucan-lab が持つ（`LICENSE`）。はじめは OSS を考えていたが、サービスとして提供するために改めた。経緯と進め方は `business.md`。

## 技術の前提

| 項目 | 決定 |
| --- | --- |
| 稼働先 | Cloudflare Workers だけ（Workers Paid） |
| DB | Cloudflare D1 |
| ファイル | Cloudflare R2（添付ファイル） |
| API | Hono |
| 画面 | SvelteKit の SPA モード（SSR を使わず静的に書き出し、Workers Static Assets で配る） |
| 認証 | ログインの手段を差し替えられる型で持つ。初版は GitHub OAuth と Google（OpenID Connect） |
| 定期処理 | Cron Triggers |
| 処理の上限 | 1回の定期処理の上限を設定値で持つ |

API（`/api/*`）、画面の配信、定期処理を1つの Worker にまとめる。

### 作りの決まり

- D1 の機能は直接使ってよい。他の稼働先へ移すための層は持たない。
- DB への書き込みは、文を並べて D1 の `batch()` で1つのトランザクションとして送る。D1 は対話的なトランザクションを持たないため。
- マイグレーションは SQL のファイルで持ち、wrangler で適用する。
- 設定は wrangler の設定に、シークレットは Workers のシークレットに持つ。
- 公開する URL を設定に持ち、OAuth の戻り先と Origin の検査に使う。

## 運用

- wrangler の設定はリポジトリにコミットする。シークレットの値は git の対象にしない。
- 運用の手順書をリポジトリに置く。書くのは、GitHub OAuth App と Google の OAuth クライアントの作成、D1 と R2 のバケットの用意、シークレットの登録、マイグレーションの適用、デプロイ。
- シークレットは、ログインの手段ごとのクライアント ID と秘密（初版は GitHub OAuth と Google）、認証情報の暗号鍵、運用者のログインの ID。手順書に一覧で載せる。
- 新しい版は、マイグレーションの適用、デプロイの順で出し、手順書に書く。
- アプリにバックアップの機能は持たない。D1 の Time Travel（30日）に任せ、長く残すときは wrangler d1 export を定期に取る。手順書に書く。添付ファイルはバックアップを取らず、消したものは戻せない。D1 を過去に戻して、消したファイルを指す行が戻ったときは、画面で「ファイルが見つからない」と示す。
- 想定する規模は、1つの組織でユーザー50人、ワークスペース20、タスク5万件まで。組織の数は初めは数十までとし、全組織を1つの D1 に入れる。D1 の容量（1つのデータベースで 10GB）や負荷が足りなくなったら、決まった数の D1 に組織を振り分ける。そのために、共通の表と組織の中の表を分けて扱う。分け方と目安は `data-model.md` の「データベースの分け方」に書く。画面の API は 500ms 以内を目安にする。積載量は集計を保存せず、表示のたびに計算する。
- 対応するブラウザは Chrome、Edge、Firefox、Safari の最新版。デプロイ直後に画面と API の版がずれたら、画面の再読み込みを促す。
- 夏時間は IANA のタイムゾーン名で扱う。
- 開発は wrangler dev とローカルの D1 で行う。テストも Workers の実行環境で回す。ステージングは持たない。道具の版はリポジトリで固定する。
- 外部への通信は取り込み元とログインの手段だけで、テレメトリは送らない。
- アプリ側のレート制限は、ログイン、画面のエラーの送信（ログイン前も受ける）、手動の同期、招待する人の解決（招待の前に GitHub のユーザー名を確かめる操作）、完成の定義の変更（長い本文と変更の履歴を書く操作）、コメントの作成と編集（長い本文を何件でも足せる操作）にだけ設ける。
- 退会は管理者がユーザーを無効にして行い、そのユーザーの接続の認証情報を消す。名前、完了の記録、経験値は残す。ログインの手段の側のアカウント（GitHub アカウント、Google アカウント）の凍結や削除は追わない。手段の側のアカウントを止めても、Scrum Guild のセッションが残る間は入れるので、辞めた人は管理者が Scrum Guild で無効にする。管理者向けの説明に書く。
- 本文とコメントはそれぞれ10万字まで。添付ファイルは1ファイル50MBまで、組織ごとの合計は組織の段階の上限まで（「組織と運用者」の節）。添付ファイルは Worker で受けながら R2 へ流し、Worker の中に丸ごと持たない。取り込み元の応答 JSON を保存するときも、D1 の行の上限を超えないよう大きすぎる分は切り詰める。

## 日付と時刻

- 日時（完了日時、作成日時、確定日時など）は UTC の ISO 8601 で持ち、画面ではブラウザのタイムゾーンで出す。
- 日付（期日、スプリントの開始日と最終日、休日、休み、稼働開始日と稼働終了日、今日やるの日付）はタイムゾーンを持たない YYYY-MM-DD で持つ。
- 今日、今週、完了した月は、ワークスペースに設定したタイムゾーンで決める。ユーザーはタイムゾーンを持たず、休みの日付はどのワークスペースでもそのまま使う。
- 定期処理は UTC で動き、日をまたぐ判定は各ワークスペースのタイムゾーンで行う。

## 概念

| 概念 | 何か |
| --- | --- |
| ワークスペース | タスクの集まりの単位。チームや用途ごとに作り、メンバーを持つ |
| 接続 | ワークスペースに登録した取り込み元（Backlog のスペース、GitHub のアカウントや組織） |
| エピック | 成果のまとまり。期日を振れ、ストーリーが複数入る |
| ストーリー | 1スプリントで終わる確認できる区切り。エピックに入れられる |
| タスク | 実際の作業。手で作るか、取り込み元から取り込む |
| スプリント | 開始日と最終日を持つ期間 |
| 区分 | エピックや親のないストーリーとタスクに振る分類（保守、追加案件など）。一覧はワークスペースごとにリーダーが定義する |
| リポジトリ | タスクがどのリポジトリの作業かを示す印。一覧はワークスペースごとにリーダーが定義する |

取り込んだタスクも手で作ったタスクも、同じ1つのタスクとして DB に持つ。違いは取り込み元への参照を持つかどうかだけにする。

- タスクの親は、なしかストーリー。エピックの直下には置かない。
- ストーリーの親は、なしかエピック。

### 削除

- タスク、ストーリー、エピック、スプリント、コメントの削除はすべて論理削除で、削除日時を付けて画面から隠す。削除したものを戻す画面は初版に持たない。
- タスク、ストーリー、エピックを削除できるのは、作った人とリーダー（管理者を含む）。スプリントを削除できるのはリーダーだけで、始まっていないスプリントに限る。スプリントを削除すると、入っていたタスクはバックログへ戻る。
- 取り込んだタスクは削除せず、アーカイブで外す。
- エピックやストーリーを削除するときは、配下を親なしで残すか、まとめて削除するかを選ぶ。まとめて削除では、配下の取り込んだタスクは削除せずにアーカイブへ移す。完了したエピックとストーリーも削除でき、完了の記録と経験値は残る。
- まとめて削除では、リーダー（管理者を含む）でない人は、削除していない配下（エピックなら配下のストーリーとその下のタスク、ストーリーならタスク。完了したものも含む）がすべて自分の作ったもののときだけ削除できる。他の人の作ったものが配下にあれば、まとめて削除はリーダーに任せる（親なしで残す削除はできる）。取り込んだタスクは作った人がおらず、削除せずアーカイブへ移すだけなので、この判定に数えない。
- 親なしで残すのは直接の子だけで、エピックを削除すると配下のストーリーが親なしになり、その下のタスクはストーリーの下のまま。残した子は親なしのものの末尾に元の並びで移り、親から引き継いでいた区分を写す（削除の前後で集計の区分を変えない）。

## 組織と運用者

- 1つのアプリと1つの D1 に複数の組織を入れる。組織は契約の単位で、顧客の会社やチームが1つの組織を持つ。
- 組織の中のもの（ユーザー、ワークスペースとその中のすべて、組織の休日、組織の設定）は組織ごとに分かれ、他の組織からは見えない。
- 組織は URL の先頭に、運用者が付けた英小文字、数字、ハイフンの名前（slug）で示す（`https://scrum-guild.dev/<slug>/...`、API は `/api/<slug>/...`）。`api`、`login`、`operator`、`invite` などアプリが使う名前は付けられない。slug は後から変えない。ワークスペースの画面は `/<slug>/w/<ワークスペースの ID>/...`、組織の画面は `/<slug>/...` に置く。
- 同じアカウントで複数の組織に入れる（複数の顧客の仕事をする人など）。ユーザーの名前、管理者の印、稼働、休み、経験値、テーマは組織ごとに別に持ち、他の組織の値は見えない。
- 入れる組織が2つ以上ある人は、ログインの直後に組織を選ぶ。入れる組織が1つなら、その組織へ入る。届いた招待はすべての組織の分をまとめて出し、届いた招待がある人には、入れる組織が1つでも組織を選ぶ画面を出す。選ぶ画面の「入れる組織」に並べるのは、管理者か、ワークスペースに所属のある組織だけで、承諾待ちの招待だけの組織は「届いた招待」に組織の名前だけを出す。
- 運用者は Scrum Guild を運用する側の人で、シークレットにログインの ID の一覧で持つ。運用者の画面で、組織の作成（slug、名前、最初の管理者。ログインの手段を選び、GitHub ならユーザー名、Google ならメールアドレスで指す）、停止と再開、管理者の指名し直し、人数と添付ファイルの上限の変更ができる。
- 運用者は、管理者の指名し直しで自分を指名できない（GitHub で解決した人が、運用者のアカウントに結んだ GitHub のログインのどれかなら断る）。これは運用者が誤って自分を指名するのを防ぐためのもので、運用者が意図して組織の中に入る道は塞がない。自分の Google のメールアドレスで指名して招待の URL を自分で開くこと（Google のメールアドレスは、運用者のログインの `sub` と突き合わせられない）と、アカウントに結んでいない別の GitHub のアカウントで指名することは止められない。どの指名し直しも、その組織の変更の履歴に運用者の操作として残り、組織の管理者が見られる。この危険は受け入れ、運用の手順書で統制する（2026-10-28 に人が決めた。#217 のコメント）。組織の作成の最初の管理者には、自分のチームの組織を作る使い方があるので自分を指名できる。
- 運用者は、管理者として指名されない限り、組織の中のデータを画面で見られない。組織の一覧には、人数と人数の上限、ワークスペース数（閉じていないもの）、タスク数（削除していないもの。受信箱、アーカイブ、閉じたワークスペースの分も含む）、添付ファイルの上限、最後に使われた日時（組織の人のだれかが最後に使った日時）と、管理者の状態（管理者がいない、指名した人のログイン待ち、招待の URL の期限切れ）だけを出す。人の名前や ID は出さない。人数が上限に達した組織には印を付ける。添付ファイルの使った量の合計は、添付ファイルを作る Issue（#68）まで出さない。
- 組織は人数の上限と添付ファイルの合計の上限を持ち、運用者が決める。運用者の画面では、値段の段階（小さい組織は15人と30GB、標準は50人と100GB）から選ぶか、51人以上の組織のために値を入れる（どちらも 1 以上の整数。添付ファイルは GB の整数で入れる）。停止中の組織の上限も変えられる。既定は小さい組織の値。段階と値段の決まりは `business.md` の「値段の考え方」。
- 人数は、管理者と、いずれかのワークスペースに所属しているか招待されている人を数える。無効にした人と、すべてのワークスペースから離れた人は数えない。人数が上限に達した組織では新しい人を招待できず、招待の画面で上限に達したことを示す。すでに組織にいる人（数えられている人）を別のワークスペースへ招待するのは、上限に達していてもできる。段階を下げて人数が上限を超えたときは、今いる人をそのまま残し、上限を下回るまで、まだ数えられていない人の招待と管理者への指名だけを止める。
- 初版では、組織を作れるのは運用者だけにする。利用者が自分で申し込んで組織を作る仕組みと課金はアプリに入れない（`business.md`）。
- 停止した組織には誰も入れず、定期処理（取り込み、日をまたぐ処理）も止める。停止には、一時的な停止（支払いの遅れなど）と解約の2つがある。解約した組織は、停止から30日後に運用者がデータをすべて消す。添付ファイルも R2 から消す。消す予定日の当日までは再開できる。消す手順は運用の手順書に書く。停止より前に組織に入っていた要求は、停止の後でもその要求の書き込みを終えうる（`data-model.md` の「入ってから書くまでの停止」）。
- 停止した組織を開いたとき、停止していなければ入れた人（無効でない管理者、今の所属がある人、承諾待ちの招待がある人）には、停止していることと運用者に問い合わせることを伝える（API は 403 の `organization_suspended`）。ほかの人には、組織が無いときと同じ「見つかりません」（404）を返し、組織があることを外に漏らさない。停止した組織にしか入れない人は、ログインできる条件を失うのでセッションが消え、ログインの画面には「入れる組織がありません」でなく、所属する組織が停止していることを出す。組織の選択の画面には停止した組織を出さない。
- 運用者による組織の停止、再開、停止の理由の切り替え、管理者の指名し直し、人数と添付ファイルの上限の変更は、その組織の変更の履歴に運用者の操作として残す。停止中の組織は、再開せずに停止の理由（一時的な停止と解約）を切り替えられる。停止した日時は変わらず、解約にすると切り替えた日の UTC の日付の30日後が消す予定日になり、一時的な停止にすると消す予定日が空になる。同じ理由への切り替えはできない。履歴の書き込みに失敗しても、これらの操作（停止、再開、停止の理由の切り替え、上限の変更）は成功として返す。再開は確認を挟まず、停止は理由（一時的な停止か解約）を選ぶ確認を挟む。解約の消す予定日は、停止した日時の UTC の日付の30日後で、予定日の当日（UTC の日付）までは再開でき、一時的な停止へも切り替えられる。予定日を過ぎた組織は、データを消している途中で戻さないよう、再開も一時的な停止への切り替えもできない（確認を挟んでも、別の運用者が確認を押せば消している途中で再開されるので、断る。2026-10-28 に人が決めた。#408）。予定日を過ぎた組織には、管理者の指名し直しもできない（消している途中で組織の中に行が足されると、消し残るため）。運用者の画面は、その組織の行に管理者の指名、再開、停止の理由の切り替えを出さず、消す予定日を過ぎたのでどれもできないことを出す。停止の理由を選ぶ確認の「解約」の説明にも、予定日の当日までは再開でき、過ぎるとできないことを添える。予定日を過ぎた後に戻す道は作らず、顧客が戻るなら、データを消した後に組織を作り直す。

## メンバーと権限

会社にたとえると、組織が会社、ワークスペースがチーム、リーダーがチームの長、管理者が社長にあたる。リーダーはワークスペースの権限で、スクラムのプロダクトオーナーとは別物。

ワークスペースのメンバーは、ワークスペースごとにリーダーと一般のどちらかのロールを持つ。「メンバー」はロールを問わずワークスペースに所属する人を指す。1人が複数のワークスペースでリーダーになれる。

| ロール | できること |
| --- | --- |
| リーダー | 一般ができることに加え、ワークスペースの設定（列、詳細の決まった欄、完成の定義、区分、リポジトリ、タイムゾーン、週の始まり、言葉づかい、ポイントの換算比率、ワークスペースの休日）、スプリントの作成、開始、終了、延長、メンバーの配分、他のメンバーの接続の停止と削除、メンバーの管理 |
| 一般 | タスク、ストーリー、エピックの作成、編集、完了（他のメンバーが作ったものを含む）、タスクのスプリントへの出し入れ、自分の接続の登録と編集と削除 |

- ワークスペースのロールとは別に、組織ごとに管理者を置く。管理者は組織のユーザーに印を付けて持つ。ある組織の管理者は、他の組織では何の権限も持たない。
- 組織の最初の管理者は、運用者が組織を作るときに指名する（「組織と運用者」の節）。
- 管理者は同じ組織の別のユーザーを管理者に指名でき、管理者を解除できる（自分も解除できる）。最後の管理者は解除できない。無効にしたユーザーは管理者に指名できない（先に有効に戻す）。管理者は組織の人数に数えるので、人数が上限に達しているときは、まだ人数に数えられていない人（どのワークスペースにも所属せず、承諾待ちの招待も無い人）を管理者に指名できない（招待の上限と同じ）。管理者が全員いなくなったときは、運用者が新しい管理者を指名し直す。
- 管理者は、所属していないワークスペースも含めてすべてのワークスペースで、リーダーと同じ閲覧と操作ができる。所属していないワークスペースでは、担当、討伐隊、経験値、積載量の対象にならない。そこで作業するときは自分をメンバーに加える。
- リーダーはメンバーを招待し、招待のときにロールを選ぶ。招待する人は、ログインの手段を選んで指す。指し方はログインの手段の型が持つ。
  - GitHub ではユーザー名で指す。ユーザー名は変えられるため、招待のときに GitHub のユーザー ID に解決して突き合わせる。
  - Google ではメールアドレスで指す。Google にはメールアドレスから不変の ID（`sub`）を引く手段がないため、招待はメールアドレスで持ち、本人が Google でログインしたときに `sub` に結ぶ。結んだ後は `sub` で見分け、Google の側でメールアドレスが変わっても同じ人として扱う。
  - Google の招待では、招待ごとに使い捨ての秘密を含む招待の URL を作り、招待した人が本人に伝える。結ぶのは、本人がその URL を開いて Google でログインし、Google が確認済みとした（`email_verified` が真の）メールアドレスが招待のメールアドレスと一致したときだけにする。`email_verified` は、Gmail でも Google Workspace でもないアドレスでは Google のアカウントを作った時点の確認にすぎず、今の持ち主を保証しないため、メールアドレスだけでは結ばない。招待の URL は招待した直後の画面にだけ出し、なくしたら招待し直す。
  - メールアドレスは、前後の空白を除き、英字の大文字と小文字を区別せずに比べる。ASCII の外の文字を含むアドレスは受け付けない。Gmail のドットや `+` 以降は読み替えず、本人が Google に登録したとおりの綴りで招待する。
  - Google の招待は、作ってから14日で切れる。結ぶ前に切れたら、リーダーが招待し直す。アドレスが別の人に割り当て直されたときに、古い招待を新しい持ち主が受け取らないようにするため。招待し直すと、同じアドレスへの古い招待は取り消す。
  - 招待の URL を開いた人は、ボタンを押してから Google のログインに進む。すでにログインしていても Google のログインを通し、その時点で確認済みのメールアドレスと突き合わせる。
  - 招待されたのと別の手段でログインしても、その招待には当たらない。ログインできないときの画面で、招待された手段でログインするよう案内する。どのメールアドレスに招待したかは画面に出さない。
- 運用者による管理者の指名も、招待と同じ指し方にする。Google で指名したときは、招待と同じく14日で切れる招待の URL を作り、運用者が管理者になる人に伝える。
  - Google で指名して結ぶのを待っている人は、管理者の数に入れない。最後の管理者の検査にも数えず、運用者の画面には「指名済み、ログイン待ち」と出す。
  - 運用者が指名し直したときは、その組織でまだ結んでいない前の指名（GitHub でまだログインしていない指名と、Google で待つ指名。消した招待の URL は使えなくなる）を消す。ログインした前の管理者は外さない。指名し直しは、管理者の状態に関わらずどの組織にも、停止中の組織にもできる。
  - 指名した人がその組織で無効になっていたら、指名で無効を解く。ただし、指名した後に無効にされていたら、指名には当てない（後から下した無効の判断を、前の指名で覆さないため）。
- 招待は取り消すまで有効（Google の招待は上のとおり14日まで）で、リーダーはいつでも取り消せる。招待された人はログインすると招待の一覧を見て、承諾するか辞退するかを選ぶ。承諾するとそのワークスペースのメンバーになる。
- Scrum Guild は招待をメールで送らない。招待した人が、組織の URL（GitHub の招待）か招待の URL（Google の招待）を本人に伝える。
- タスク、ストーリー、エピックは、作った人や担当者に限らずメンバーなら誰でも編集でき、タスクとストーリーは誰でも完了にできる。エピックをクリアできるのは依頼主とリーダー、削除できるのは作った人とリーダーだけ。
- ワークスペースを閉じられるのは管理者だけ。閉じたワークスペースは読み取り専用になり、接続はすべて停止する。経験値は本人の合計に残る。管理者は閉じたワークスペースを開き直せる。
- リーダーは何人でもよい。リーダーと管理者は、一般のメンバーをリーダーにしたり、自分を含むリーダーを一般に戻したりできる。リーダーがいなくなったワークスペースでは、管理者がリーダーの役を務め、新しいリーダーを任命できる。
- メンバーはリーダーに外されるほか、自分で抜けられる。所属は参加日と離脱日の期間の履歴で持つ。
- メンバーが離れると、未完了のタスクの担当を外して担当なしにし、討伐隊からも外す。完了の記録と経験値は残し、離脱済みとして表示する。その人の接続は停止し、取り込んだタスクは残す。
- 離れた人が再び招待されたら、同じユーザーとして戻り、経験値を引き継ぐ。停止した接続は本人が再開できる。
- セッションはランダムな ID を HttpOnly、Secure、SameSite=Lax の Cookie に入れ、ID のハッシュを DB に持つ。使うたびに期限を延ばし、最後に使ってから 30 日で切れる。ログアウトと、ログインできる条件を失ったときに、その人のセッションをすぐ無効にする。ログアウトは今のセッションを消し、同じ人のほかの端末のセッションは残す。ログインできる条件を失った（入れる組織が1つも無くなり、運用者でもない）人のセッションは、組織の外の呼び出し（ログアウトを除く）と、組織に入れなかった組織の中の呼び出しで消し、401 を返す。運用者の一覧から外れ、入れる組織も無い人も同じ。停止した組織にしか入れない人は、停止の間にセッションが消え、組織が再開した後も、もう一度ログインが要る。1つの組織で無効にされたり外れたりしたときは、セッションを残し、その組織にだけ入れなくする。
- 更新系の API は Origin ヘッダーを検査し、SameSite=Lax の Cookie と併せて CSRF を防ぐ。OAuth と OpenID Connect のログインでは state と PKCE を使い、OpenID Connect では nonce も使う。state は DB に持つほか、HttpOnly の Cookie にも置き、戻り先で DB の行と Cookie の両方と比べる（DB の行だけだと、攻撃者が自分で始めたログインの戻り先の URL を踏ませて、被害者を攻撃者のアカウントでログインさせられる）。ログイン後に戻る画面は、自分のサイトのパスだけを受け付ける。ログインの開始と戻り先は、同じ IP から10分に60回までに抑える。Google の ID トークンの確かめ方は `development.md` の「Google のログイン」に書く。
- 組織に入れるのは、その組織の管理者と、その組織のいずれかのワークスペースに今所属しているか招待されている人だけ。すべてのワークスペースから外れた人はその組織に入れない。管理者はその組織のユーザーを無効にでき、無効にした人はその組織に入れない。自分は無効にできず、最後の管理者も無効にできない。無効にすると、その人をすべてのワークスペース（終了したものも含む）から外し、離脱と同じく未完了のタスクの担当も外す。管理者なら指名も解除し、その人への承諾待ちの招待も取り消す。有効に戻すとログインはできるが、所属と管理者の指名は戻らず、その組織に入るには招待し直すか、管理者に指名し直す（所属を残すと、一覧と担当の候補と人数で、無効の人を除く条件があちこちに要るため）。
- ログインは1回だけ行い、そのまま入れる組織を行き来できる。入れる組織が1つもない人はログインできない。ただし運用者（シークレットのログインの ID の一覧に載った人）は、入れる組織が無くてもログインでき、運用者の画面に入れる。
- ログインの手段は共通の型で実装する。型が持つのは、本人の確認、手段の中の不変の ID と表示名とアバターの取得、招待する人の指し方。人は手段と手段の中の ID の組で見分け、アカウントは特定の手段に依存させない。初版で用意する手段は GitHub と Google。エンジニアでない人（GitHub のアカウントを持たない人）もチームに入るため、Google を用意する。
- Google のログインは本人確認だけに使い、`openid`、`email`、`profile` より広いスコープを求めない。GitHub のスコープは「取り込み」の節の接続の認証情報に書く。
- 初版では、1つのアカウントに結ぶログインの手段は1つだけにする。同じ人が GitHub と Google の両方でログインすると、別のアカウントになり、組織ではユーザーが2人として数えられる。
- Google のメールアドレスは、本人と、招待した画面の承諾待ちの一覧のほかには出さない。Google の人の名前には、Google のプロフィールの名前を使う。
- 新しいワークスペースを作れるのは管理者だけ。作るときに最初のリーダーを指名する（自分でもよい）。

## 取り込み

- 取り込む項目の種別は、課題、PR、レビュー依頼の3つで、取り込み元を問わず共通にする（GitLab のマージリクエストは PR として扱う）。初版の対象は Backlog の課題と、GitHub の Issue、PR、レビュー依頼。
- 定期処理で取り込み元を読み、DB に保存する。画面を開いたときに取り込み元を叩かない。
- 接続を登録したあとの初回は、取り込む範囲の未完了の項目だけを取り込む。以降の差分でも、取り込んでいない項目が完了していたら取り込まない。
- 定期処理の間隔は wrangler の設定で変えられ、既定は15分。接続の登録者は「今すぐ同期」を押せ、受け付けるのは接続ごとに5分に1回まで。最後に成功した日時は受信箱と接続の一覧に出す。
- 同期は差分で行う。接続ごとに前回成功した時点を持ち、それ以降に更新された項目だけを取る。Backlog は更新日の指定が日単位なので前回の日から取り直し、更新日時を比べて処理済みのものを捨てる。
- 取り込み済みの項目は1日1回、不変の ID でまとめて照合し、「取り込み元で見つからない」の印を付けたり外したりする。
- 1回の定期処理では、有効な接続を順に処理し、1回の上限（取り込み元への要求の数、処理時間）に達したら、接続ごとに続きの位置を保存して次の回で続きから再開する。
- 接続ごとに、取り込む範囲を Backlog のプロジェクト、GitHub のユーザーや組織、リポジトリの単位で絞れる。範囲は取り込み元の ID で持ち、画面では取り込み元の一覧から選ぶ。「対象を挙げる」か「すべてから除外を挙げる」のどちらか1つを選ぶ。
- 登録した直後の範囲は対象なしで、範囲を選ぶまで取り込まない。登録の画面で、取り込んだ内容（private なものを含む）がワークスペースの全員に見えることを示す。
- 新しく取り込んだタスクの行き先は、ワークスペースに1つの共有の受信箱。バックログへ入れるかアーカイブするかは、メンバーなら誰でも選べる。
- 取り込んだタスクのアーカイブは、受信箱、バックログ、スプリントのどこからでも行える。アーカイブで外すのはスプリント、列、親で、ポイント、期日、詳細、コメントは受信箱へ戻したあとも残す。手で作ったタスクはアーカイブの対象外で、削除で片付ける。
- アーカイブしたタスクは、アーカイブの一覧にだけ出す。受信箱、バックログ、スプリント、自分の今日、検索の結果、積載量の集計には出さない。同期で取り込み元の属性は更新するが、取り込み元で完了しても通知しない。アーカイブの一覧から受信箱へ戻せる。
- 取り込み後は、取り込み元が持つ属性（タイトル、取り込み元での状態、期限、URL）だけを同期で更新する。これらは Scrum Guild では編集しない。Scrum Guild が持つ属性（列、スプリント、親、ポイント、期日、担当、リポジトリ）は同期で書き換えない。
- 取り込んだタスクをスプリントに入れたときの列は、接続ごとに設定する「取り込み元の状態から列への対応」で決める。対応のない状態は先頭の列に置く。完了の列は対応先にしない。対応は接続と状態名の組で持ち、同じ名前の状態はプロジェクトをまたいで同じ列に置く。
- レビュー依頼は自分宛てのものだけを取り込む。自分のレビューが付くか PR が閉じたら「取り込み元で完了」とみなす。再依頼されたら同じタスクを未完了にして受信箱へ戻す。このとき前回の完了とレビューの経験値は打ち消さず、レビューの経験値は依頼の回ごとに1回付く。
- 取り込み元で完了したタスクは自動で完了にせず、「取り込み元で完了」の印を付けて担当者（いなければ接続の登録者）に通知する。受信箱にあるタスクは印だけ付けて通知しない。完了にするかはメンバーが決める。
- 取り込み元で開き直されたら印を外す。Scrum Guild で完了にしたタスクが開き直されたときは担当者に通知する。
- 取り込み元には書き戻さない。
- 接続はワークスペースに属し、登録したメンバーの認証情報でその人の担当分を取り込む。接続はメンバーが自分の認証情報で登録し、編集と削除も本人が行う。リーダーと管理者は他のメンバーの接続を停止、削除できるが、取り込む範囲は変えられない。他人の認証情報を預かる運用はしない。取り込んだタスクは取り込んだ時点で登録したメンバーが担当になり、その後は Scrum Guild で担当を替えられる。取り込んだタスクはワークスペースの全員が見られる。
- 取り込み元の本文とラベルは画面に出さず、取り込み元の URL で開く。詳細は取り込み元に書き、Scrum Guild にはタスクとして扱うのに要る属性だけを持つ。
- 取り込んだタスクは、取り込み元の種類（Backlog、GitHub など）、種別（課題、PR、レビュー依頼）、取り込み元の不変の ID（課題キーや番号のように移動で変わるものではない ID）、取り込み元が持つ属性（タイトル、キー、状態、期限、URL、プロジェクトやリポジトリの名前）を持つ。
- 取り込み元の応答そのもの（本文とラベルを含む JSON）を保存するかは、管理者が組織の設定で選ぶ。既定は保存しない。保存しない組織では、取り込み元の本文を D1 に一度も書かない。保存しない側に切り替えたら、保存済みの応答を消す。保存する側に切り替えたら、次に同期した項目から保存し、さかのぼって取り直さない。
- 取り込み済みの項目は、取り込み元で担当が外れても、取り込む範囲の外へ移っても、不変の ID で取りに行って同期を続ける。削除や権限の喪失で取れなかった項目には「取り込み元で見つからない」の印と最後に確認できた日時を付け、担当者に知らせる。接続の取得そのものが失敗したときは、その接続の項目を動かさない。
- 同じワークスペースでは、同じ取り込み元の項目を1件のタスクにまとめる。一意のキーはワークスペース、取り込み元の種類、種別、取り込み元の不変の ID の組。担当は最初に取り込んだ接続の登録者。レビュー依頼だけはレビュアーごとに別のタスクにする。
- 同じ項目が別々のワークスペースに入ることは許し、それぞれ独立したタスクにする。重ならないよう取り込む範囲を絞るのは運用に任せる。
- 接続の認証情報は、Backlog は API キー、GitHub は本人が発行した読み取り専用の fine-grained PAT。ログインの GitHub OAuth は本人確認だけに使い、`read:user` より広いスコープを求めない。PAT の期限切れは通知で知らせる。
- 接続は状態（有効、エラー、停止）、最後に成功した日時、直近のエラーの内容と日時、連続して失敗した回数を持つ。接続の一覧で、ワークスペースの全員がこれらを見られる。
- 認証の失敗（失効、期限切れ）では、その場で接続を停止する。再開は、本人が認証情報を更新したとき。それ以外の失敗では止めずに次の回で再試行する。
- 取り込みの失敗は接続の登録者にだけ知らせる。知らせるのは状態が変わったときだけで、同じ失敗が続いても繰り返さない。
- 保存した認証情報は画面にも API にも返さず、末尾の4文字だけを示す。
- 接続の認証情報は暗号化して DB に保存する。暗号文には鍵の版を付け、シークレットに新旧の鍵を並べて置ける。鍵を入れ替えるときは、新しい鍵で暗号文を書き直す処理を走らせてから古い鍵を外す。鍵を失ったときは、各自が認証情報を登録し直す。
- 接続には登録した本人が表示名を付ける。
- Backlog の接続は、スペースのドメイン（backlog.com か backlog.jp）を持つ。GitHub は github.com だけを対象にする。
- 接続の設定のうち、どの取り込み元にもある項目（種類、状態、取り込む範囲、状態から列への対応、期限を無視する設定）は表の列で持つ。取り込み元に固有の項目は、型が検証する JSON で持つ。
- GitHub の検索 API は1回に1,000件までしか返さないため、更新日時の範囲で検索を分ける。クエリが長くなるときは、リポジトリごとにクエリを分ける。
- Backlog の接続は、登録のときに本人のユーザー ID を取得して保存し、担当の絞り込みに使う。
- 取り込み元は共通の型で実装する。型が持つのは、接続の設定項目、取り込む範囲の種類、取り込み元からの取得、取り込み元の状態の一覧、タスクへの変換。Backlog と GitHub もこの型で実装し、新しい取り込み元はこの型の実装をリポジトリに足して加える。
- 取り込み元に固有の処理と値は型の実装の中に閉じ、それ以外のコード、画面、DB の制約に書かない。取り込み元を足すときに、型の実装と言葉の辞書のほかを変えずに済むようにする。上に書いた Backlog と GitHub の決まり（更新日の単位、スペースのドメイン、検索の件数の上限、ユーザー ID）も、それぞれの型の実装が持つ。

## ゲームの仕組み

- 経験値は自分から動くことを促すためのもので、人の評価に使わない。README にもそう書く。
- 協力型にする。チームの目標はレイドのクリアで、メンバー間の順位は出さない。
- 見立ては冒険者ギルド。組織がギルドで、ワークスペースはギルドに属するパーティ。エピックはパーティの掲示板に貼る、討伐隊を組んで挑むレイド、ストーリーはその達成目標、タスクは目標をこなすために1つずつ片付けるクエスト。
- レイドはメンバーの誰でも掲示でき、掲示した人が依頼主としてクリア報酬（経験値）を決める。額は決まった段階（小、中、大など）から選び、各段階の値は固定。クリアまで変えられ、変えたら討伐隊に知らせる。
- レイドに参加するメンバーが討伐隊。メンバーが自分で受注して加わるほか、依頼主がメンバーを割り振れる。配下のタスクの担当になった人も自動で討伐隊に加わる。依頼主自身も討伐隊に入れる。
- 割り振られた人はすぐに討伐隊に入り、本人に知らせが届く。討伐隊からはいつでも自分で抜けられる。
- クリア報酬は、クリアした時点の討伐隊全員に同額。行動ごとの経験値とは別に、レイドのクリアで払う。
- クリア報酬の変更、討伐隊への割り振り、レイドのクリアと中止ができるのは、依頼主とリーダー（管理者を含む）。
- 依頼主がワークスペースを離れても、依頼主の表示は離脱済みとして残る。依頼主の操作はリーダーが代わりに行い、リーダーは依頼主を別のメンバーに替えられる。
- レイドは中止できる。中止したレイドにクリア報酬は出ないが、確定済みの経験値は残る。期日を過ぎても色で示すだけで、失敗の状態は設けない。
- 画面の言葉づかいは、ワークスペースの設定で「ゲームの言葉」（レイド、達成目標、クエスト、討伐隊、依頼主、受注）と「スクラムの言葉」（エピック、ストーリー、タスク、参加者、作成者、参加）を切り替えられる。既定はゲームの言葉。切り替わるのは言葉だけで、経験値や報酬の仕組みはどちらでも同じ。ワークスペースの外の言葉（冒険者ギルド、ギルドマスター）は、管理者が組織の設定で切り替える。
- 見た目はテーマで切り替える。テーマは「シンプル（自動）」「シンプル（ライト）」「シンプル（ダーク）」「中世風」「現代風」の5つ。
  - シンプルは業務の道具として落ち着いた見た目。会社に入れても違和感のないもの。ただし、レベル、クリア、レベルアップの場面はゲームらしく作り込む。自動は OS のライトとダークの設定に合わせる。
  - 中世風は冒険者ギルドの帳簿（紙と墨、判子）。ライトだけ。
  - 現代風は近未来の端末のウィンドウ（暗い地に光る枠）。ダークだけ。
  - 管理者が組織の設定で既定のテーマを決め、各ユーザーが自分の設定で上書きできる。上書きしなければ組織の既定に従う。組織の既定の初期値はシンプル（自動）。
  - テーマと言葉づかいは別に選ぶ。シンプルとスクラムの言葉を組み合わせれば普通の業務の道具になる。
  - テーマで変わるのは見た目（色、書体、角と線と影、決まった少しの飾り）だけで、画面の構成、情報、操作は同じ。
- DB と API の名前はスクラムの言葉（epic、story、task）。主キーは UUIDv7 の文字列。
- ゲームの仕組みは無効にできない。ゲームらしさを抑えたいときはスクラムの言葉に切り替える。
- 個人の成長は経験値などで見せる。
- 経験値は付与の明細（行動、受け取った人、ワークスペース、タスク、値、確定日時）で持ち、合計は明細から出す。同じ付与の重複は一意制約で防ぐ。
- 未完了のタスクで、完了すれば付く起票と詳細の経験値は、本人に「見込み」として確定分と分けて示す。
- 経験値はワークスペースごとに貯まる。本人は、所属するすべてのワークスペースの合計も見られる。
- 他のメンバーに見せるのはレベルだけで、経験値の数値と明細は本人だけが見られる。メンバーを経験値で並べる画面は持たない。チーム全体の経験値の合計は全員が見られる。
- レベルは、組織の中の本人の経験値の合計（所属するすべてのワークスペースの合計）から出す。組織ごとにレベルは1つ。
- レベル `L` に達するのに要る経験値の合計は `50 × L × (L − 1)`。レベル1は0から始まり、上限は設けない。
  - 次のレベルまでに要る経験値は `100 × L` で、レベルが1つ上がるごとに100ずつ増える。序盤は早く上がり、後半ほどゆっくりになるが、上がる間隔が際限なく延びることはない。
  - 目安は、1人が1スプリント（2週間）で約400の経験値を得る前提で、レベル5（1000）が約1か月、レベル10（4500）が約5か月、レベル20（19000）が約2年。
  - レベルは合計から毎回計算するので、打ち消しで合計が減るとレベルも下がる。合計が0を下回ってもレベル1より下げない。
- 感謝はタスクに送った人と受け取った人を残し、ワークスペースの全員が見られる。人ごとの受け取った数は本人だけが見られる。
- 報酬を与える行動は次の4つ。
  - タスクの起票
  - タスクの詳細を書く
  - タスクやストーリーを完了する
  - レビューや手助け
- レビューは、取り込んだレビュー依頼のタスクを完了にしたときに数える。レビュー依頼のタスクに付くのは、完了の経験値ではなくレビューの経験値。
- 手助けは、タスクの担当者が助けてくれたメンバーに「感謝」を送ったときに数える。送れるのは担当者だけで、担当がいなければ作った人。自分には送れず、同じタスクで同じ相手に送れるのは1回だけ。
- 感謝は未完了のタスクにも送れ、タスクが完了するまでは取り消せる。手助けの経験値はタスクが完了したときに相手ごとに確定し、完了を戻すと打ち消す。同じ人から同じ相手への感謝で付く経験値は、1週（ワークスペースの週の始まりから7日。確定した日で数える）あたりの回数に上限を設ける。
- 経験値は行動ごとに固定の値を付ける。起票と詳細の経験値は、タスクを完了にした時点で確定する。スプリントの有無は問わず、スプリントを回さないチームでも同じように付く。完了しないタスクの起票と詳細は報われない。同じタスクの同じ行動で有効な付与は1回だけ。
- ストーリーとエピックは、配下がすべて完了したら手で完了にできる。記録するのは完了日時と完了にした人。
- 完了したストーリーやエピックには配下を足せず、配下のタスクやストーリーを未完了に戻すこともできない。ストーリーやエピックの完了は取り消せ、取り消すと完了の経験値とクリア報酬を打ち消しの明細で取り消す。
- ストーリー完了の経験値の受け取り手は、配下のタスクで完了の経験値を受け取った人全員（1人1回ずつ）。
- 起票と完了の経験値は、ポイントが1以上のタスクにだけ付く。どちらも完了にした時点のポイントで判定する。
- 起票の経験値は手で作ったタスクにだけ付き、作った人のものになる。取り込んだタスクには起票者がいない。
- タスク完了の経験値は完了した時点の担当者に、担当がいなければ完了にした人に付く。
- 完了を未完了に戻したら、完了、起票、詳細の経験値を打ち消しの明細で取り消し、もう一度完了にしたら付け直す。
- 経験値の付いたタスクは、削除やアーカイブをしても経験値が残るよう論理削除で扱う。
- 行動ごとの経験値、クリア報酬の段階の値、レベルの式、感謝の回数の上限はコードの定数で持ち、どの組織でも同じ。値を変えても確定済みの明細は動かさない。経験値を手で足し引きする操作は持たない。
- 経験値はポイントと別に持つ。ポイントは見積もりと請求の根拠に使うため、報酬の額に結び付けない。

## 積載量（作業量の把握）

メンバーの作業量が基準から外れていないかを、スプリントの計画時と月の単位で気付けるようにする。表示で知らせるだけで、スプリントに入れる操作は止めない。

- 作業量は、メンバーが担当するタスクのポイントを時間に換算して出す。換算の比率（1ポイント = 何時間）はワークスペースで設定する。
- 基準はワークスペースではなくユーザーに持たせ、1日の時間で持つ。既定は8時間で、短時間勤務などは本人が自分の基準を変えられる。
- 稼働する曜日もユーザーに持たせ、既定は月曜〜金曜。週3日勤務などは本人が変えられる。
- 許容幅は基準に対する割合で持ち、既定は ±12.5%（稼働日20日の月なら 160 時間に対して ±20 時間）。本人が変えられ、按分や配分を掛けたどの基準にも同じ割合を使う。
- 稼働日は、本人の稼働する曜日から休日と休みを除いた日。
  - 休日は2種類。組織の休日（祝日など）は管理者が、ワークスペースの休日はリーダーが登録する。
  - 休みは本人が登録し、所属するすべてのワークスペースに効かせる。休みは終日と半日の2種類で、半日は稼働日0.5日分。
  - 組織の休日は、管理者が日付の一覧を貼り付けて一括で登録できる。
  - ワークスペースでの積載量は、組織の休日、そのワークスペースの休日、本人の休みを除いて稼働日を数える。本人の合計で除くのは、組織の休日と本人の休みだけ。
- ユーザーの月の基準は、1日の時間に稼働日数を掛けた値。稼働開始日より前と稼働終了日より後の日は数えない。
- 稼働開始日と稼働終了日はユーザーに持たせ、本人と管理者が設定する。既定は未設定で、未設定なら期間で区切らない。
- 按分でも合わない月に備え、本人がその月のユーザーの基準を時間で上書きできる。上書きした月は、上書きした時間を稼働日数で割った値をその月の1日の時間として使う。
- メンバーは複数のワークスペースに所属できる。ワークスペースごとに、そのメンバーの月ごとの配分（30% など）を持つ。
  - 配分はそのワークスペースのリーダーが決める。値は 0〜100% を 5% 刻みで、0% のメンバーは積載量の対象にしない。
  - 配分の既定は未設定。未設定の間は積載量を出さず「配分未設定」と示す。所属するワークスペースが1つだけなら 100% とみなす。
  - ワークスペースでの基準は、1日の時間に配分と、そのワークスペースに所属していた期間の稼働日数を掛けた値。8時間、30%、稼働日20日なら 48 時間。
  - 配分の合計が 100% を超えた月は、本人にだけ知らせる。リーダーには他のワークスペースの配分を見せない。管理者は、全ワークスペースの配分の合計と積載量の合計を見られる。
  - 本人は、所属するすべてのワークスペースの作業量の合計を、ユーザーの基準と並べて見られる。
- 1日の時間、許容幅、稼働する曜日、換算比率、配分は、適用開始月を付けた履歴で持つ。変えても過去の月の値は動かない。その月の設定がなければ、それより前で最も新しい設定を使う。
- スプリントでは、スプリントに入れた担当タスクの換算時間を、期間中の稼働日ごとの基準の合計と比べる。月をまたぐスプリントでは、日ごとにその月の基準を使う。
- 月では、その月に重なるスプリントの換算時間を、稼働日の割合で月に振り分けて合計し、月の基準と比べる。
- 持ち越したタスクは、最後に入っているスプリントでだけ数える。担当とポイントは、完了したタスクなら完了の記録の値、未完了のタスクなら今の値を使う。
- 基準に許容幅を足した量を超えたら超過（重量オーバー）、引いた量を下回ったら余力ありとして色で示す。ちょうどの値は範囲内とする。時間は0.1時間に丸めて出し、判定は丸める前の値で行う。
- 稼働日が0日の期間は、基準と許容幅を0とする。担当の作業量があれば超過、なければ色を付けない。基準を上書きした月の稼働日が0日なら、その月の1日の時間を0とする。
- ポイントが振られていない担当タスクは時間に数えず、件数を添えて示す。1件でもあれば、余力ありの色は付けない。
- 月の基準と比べるのは、その月のうちスプリントのある稼働日の分だけ。スプリントが1つもない月は、余力ありではなく「計画なし」と示す。
- ワークスペースでの積載量（基準、作業量、配分、休みの日付）は、そのワークスペースの全員が見られる。休みには理由を持たせない。ユーザーの1日の時間、他のワークスペースの配分、全ワークスペースの合計は、本人と管理者だけが見られる。

## 機能

ワークスペースを作った直後の既定値は、列が言葉づかいに合わせて「未着手、作業中、レビュー、完了」か「出発前、遂行中、査定中、完遂」、換算比率が1ポイント = 4時間、タイムゾーンが作った人のブラウザのもの、週の始まりが月曜、決まった欄が1つで、名前は言葉づかいに合わせて「受け入れ基準」か「達成条件」。区分、リポジトリ、完成の定義は持たない。

### 初版

- 受信箱: 新しく取り込んだタスクを並べ、バックログへ入れるかアーカイブするかを選ぶ
- アーカイブ: 自分のチームで扱わない取り込んだタスクを退け、必要なら受信箱へ戻す
- バックログ: エピック、ストーリー、タスクの木で並べる
- 絞り込みと検索: 担当、区分、リポジトリ、エピック、接続、取り込み元のプロジェクトやリポジトリで絞り込める。文字の検索はタイトルと取り込み元のキーを対象にし、本文とコメントは対象にしない。バックログの絞り込みは次の決まりで行う（#165。接続、取り込み元のプロジェクトやリポジトリ、取り込み元のキーの検索は、取り込み（#67）で同じ形に足す）
  - 当たったかどうかはタスクで決める。当たったタスクの親のストーリーとエピックは道筋として残し、当たるタスクが1つも無い親は隠す
  - 区分（エピック、ストーリー、タスクの順に引き継ぎを解いた値）、エピック、検索は、ストーリーとエピックそのものにも当てる。親が当たったときは、配下のタスクのうち、ほかの条件にも当たるものを全部出す。担当かリポジトリ（タスクにしか無い条件）でも絞っているときは、当たるタスクを持たない親を出さない
  - 違う種類の絞り込みは「かつ」で組み合わせる。1つの絞り込みで選べるのは1つだけ。選択肢は「すべて」と各値と「なし」（担当なし、区分なし、リポジトリなし、エピックなし）。エピックなしは、親のないストーリーと親のないタスクだけを出す。担当は先頭に「自分」を置き、今所属している人に加えて、離脱した人で未完了のタスクの担当に残っている人も並べる
  - 検索は、前後の空白を外し、半角と全角の空白で語に分けて「かつ」で探す。どの語も1つの行（タスク、ストーリー、エピックのどれか）のタイトルにそろったときだけ当たりとし、親と子にまたがってそろったものは当てない。英字の大文字と小文字は区別せず、全角と半角はそろえない。`%` と `_` は普通の文字として探す。検索の文字は 100 字まで、語は 5 つまで
  - 絞っても、ポイントの合計（済み / 全部）と、ストーリーの「完了 N 件」は、そのストーリーやエピック全体の値を出す。完了したタスクは行を出さないので、絞り込みの対象にならない
  - 絞り込みは URL に残し、再読み込みとリンクで同じ絞り込みで開く。「自分」はリンクを受け取った人自身になる
  - 絞っている間は並べ替えさせない（親の移動はできる）。絞り込みを外すと並べ替えられることを案内する
- 計画: 先のスプリントにタスクを入れ、積載量と並べて見る。スプリントの計画画面に、延長したスプリントを除いた直近3スプリントの完了ポイントの平均（ベロシティ）を出す。エピックごとに残りのポイントと期日を並べる
- 並び順: バックログの各階層と列の中の並びを、手で並べ替えて保存する。バックログの並びが優先順位になる。新しく入ったものは末尾に置く
- 自分の今日: 所属するすべてのワークスペースから、自分が担当するタスク（今日やるの印、今日と今週が期日のもの、進行中のスプリントのもの）を1つの画面に並べる。操作は各ワークスペースの画面で行う
- スプリント: 開始日と最終日を日付で持ち、長さは1〜28日。開始日はスプリントごとに選べる
  - 作るときは、前のスプリントの最終日の翌日を開始日に、前のスプリントと同じ長さを初期値にする。前がなければ、今日より後で最初のワークスペースの週の始まりを開始日に、14日を長さの初期値にする
  - スプリントはワークスペースごとに持ち、期間を重ねない。進行中のスプリントは同時に1つで、先のスプリントを何本でも作ってタスクを入れておける
  - 始められるのは、最終日がワークスペースの今日より前でないスプリント。開始日より前に始めてもよい
  - スプリントの作成、開始、終了、長さの変更、延長はリーダー（管理者を含む）が行う。タスクの出し入れはメンバーも行える
  - 終了は手動で行う。最終日を過ぎたら終了を促す表示を出す。終了するときに、終わらなかったタスクの持ち越し先として次のスプリントかバックログを選ぶ
  - 延長は進行中のスプリントだけで、日単位で伸ばす。次のスプリントと重なるときは、次以降のスプリントを同じ日数だけ後ろへずらす
  - 終了したスプリントの期間と中身は変えられない
  - スプリントは名前を任意で持ち、なければ期間を名前として出す
  - スプリントはゴールを文で任意で持つ。開始の画面でゴールの欄を示すが、空でも開始できる。ゴールは計画、スプリント、自分の今日の画面に出す
  - 終了するときに、リーダーがゴールを達成したかどうかを記録する。ゴールのないスプリントでは記録しない。達成に経験値は付けない
  - 完了したタスクはスプリントの完了の列に残る。バックログでは完了したものを折りたたんで示す
  - スプリントの画面でカードを完了の列へ移すと完了になる（完了の記録にそのスプリントが残り、経験値も付く）
  - 完了を戻すと、完了の前にいた列の末尾へ戻る。その列が削除されていれば先頭の列へ戻す。スプリントの外で完了したものは列なしで戻る。戻すと完了の記録を消し、その完了で付いた経験値を打ち消す
  - 終了したスプリントの中で完了したタスクは戻せない。「戻す」を出さず、API も断る。直すときはリーダーが完了の記録を修正する。ベロシティと積載量の数字を、終了の後から動かさないため。完了したストーリーの下のタスクも戻せない（先にストーリーの完了を取り消す）
  - タスクとスプリントの所属は履歴で持ち、いつどのスプリントに入って、どう出たか（完了、持ち越し、外した）を残す。持ち越しは同じタスクを次へ移す
- 列: ワークスペースごとにリーダーが定義し、名前もリーダーが付ける。付けた名前は言葉づかいを切り替えても訳さない。完了の列だけは固定で持ち、名前は言葉づかいに合わせて「完了」か「完遂」と出す
  - リーダーは列を並べ替えられる。完了の列は常に末尾に置く
  - タスクが残っている列を削除するときは、移し先の列を選ぶ。取り込み元の状態からその列への対応は外れ、その状態は先頭の列に置く扱いになる。完了の列と、完了以外で最後に残った1つの列は削除できない
- 担当: タスクに担当を0〜1人持つ。手で作ったタスクの既定は担当なし
- 階層の合計: ストーリーとエピックでは、ポイントを「完了 / 全体」で示す
- ポイント: タスクにだけ 0 とフィボナッチ（1、2、3、5、8、13）で振る。振らない（未設定）こともでき、未設定が未見積もりを表す。ストーリーとエピックのポイントは配下の合計
  - スプリントに入れる単位もタスク。ストーリーをまとめて入れる操作は、配下のタスクを入れる操作として持つ
  - 入れられるのは、バックログの未完了のタスクで、入れる先は始まっていないか進行中のスプリント。まとめて入れるときは入れられるものだけを入れ、入れなかった件数を理由（完了済み、見つからない、既に入っている）ごとに示す。完了したタスクはスプリントから外せない（先に完了を戻す）
- 期日: タスク、ストーリー、エピックに振れる。どれも任意
  - 表示する期日は1つ。Scrum Guild で振った期日があればそれを、なければ取り込み元の期限を出す。どちらの期日かを添えて示す
  - 期日を過ぎたら赤、今週中なら橙で出す。今週は、ワークスペースに設定した週の始まり（既定は月曜）からの7日間。完了したタスクは色を付けない
  - 期限を運用していない取り込み元のために、接続ごとに取り込み元の期限を無視する設定を持つ
  - 今日と今週の判定は、ワークスペースに設定したタイムゾーンで行う
- 詳細: タスクに、決まった欄、本文（Markdown）、コメントを持つ。取り込んだタスクにも書ける
  - 決まった欄はワークスペースごとにリーダーが定義し、名前もリーダーが付ける。付けた名前は言葉づかいを切り替えても訳さない
  - 「詳細を書いた」の報酬は、タスクを完了にした時点で決まった欄がすべて埋まっているかで判定し、最後の欄を埋めた人が受け取る。確定したあとに欄の定義や中身が変わっても、確定した経験値は動かさない
  - 決まった欄が空のタスクには印を付ける。スプリントに入れるときと計画の画面で、未記入の件数を示す。入れる操作は止めない
  - 起票者とメンバーのやり取りはコメントに残す
  - ストーリーは固定の「受け入れ基準」の欄と本文（Markdown）を持つ。ワークスペースで定義する決まった欄はタスクにだけ効く。ストーリーの詳細に経験値は付かない
  - コメントを編集できるのは書いた人だけで、編集したものには「編集済み」を示す。削除できるのは書いた人とリーダーで、削除したコメントは「削除されました」と残す
  - Markdown は生の HTML を許さず、無害化して描く。リンクと取り込んだ URL は http と https だけを受け付ける。画面には CSP を付ける
  - Markdown の画像は、Scrum Guild の添付ファイルだけを画面に出す。外部の URL の画像は出さず、リンクとして示す
- 完成の定義: すべてのタスクに共通する完了の基準を、ワークスペースに Markdown で1つ持ち、リーダーが編集する。完了の列と、タスクの完了の操作の横と、バックログの木の上（畳んで1つ）に出す。空なら出さない。確認のダイアログは挟まず、完了の操作は止めない
- リンク: エピック、ストーリー、手で作ったタスクに資料の URL を1つ
- 添付ファイル: タスク、ストーリー、エピック、コメントにファイルを添付できる。取り込んだタスクにも添付できる
  - 本文、受け入れ基準、決まった欄、コメントを書く欄に、画像を貼り付けるかドラッグすると、添付してその画像を Markdown で差し込む。添付の欄からも選んで上げられ、添付したファイルは一覧で示す
  - 1ファイル50MBまで。画面の録画を添えられる大きさにする。種類は問わない。PNG、JPEG、GIF、WebP は画像として、MP4 と WebM は動画として画面で再生し、それ以外（SVG を含む）はダウンロードとして渡す
  - 組織の合計が上限に達したら、新しく添付できない。管理者には組織の設定で今の合計と上限を示す。合計が上限の80%を超えたら、管理者に通知する
  - 組織ごとの上限は値段の段に合わせ、小さい組織は30GB、標準は100GBにする（`business.md`）。運用者が組織ごとに決め、作るときの既定は30GB
  - 添付ファイルを見られるのは、そのワークスペースのメンバーだけ。ファイルは公開の URL を持たず、権限を確かめてから返す
  - 添付ファイルを消せるのは、上げた人とリーダー（管理者を含む）。消したファイルは戻せない
  - タスク、ストーリー、エピックを削除しても、添付ファイルは消さない（論理削除で残すため）。コメントを削除したら、そのコメントの添付ファイルは消す
  - 書いている途中で上げて、保存しなかったファイルは、1日たったら消す
- エピックの本文: エピックに本文（Markdown）を1つ持つ。経験値は付かない
- 区分: エピックに振り、配下のストーリーとタスクが引き継ぐ。親のないストーリーとタスクには直接振る。振らなくてもよく、振っていないものは「区分なし」として集計する。区分を削除したら、振っていたものは区分なしに戻し、完了の記録は元の区分のまま残す。一覧はワークスペースごとにリーダーが定義し、名前で作れ、並べ替えられる。作った後のタスクの区分（親のないタスクだけ）は、タスクの詳細で振り替えられる
- リポジトリ: タスクがどのリポジトリの作業かを示す。取り込み元の Issue や PR に紐付かないタスク（手で作ったタスク、Backlog の課題）でも分かるようにするため
  - 一覧はワークスペースごとにリーダーが定義し、名前もリーダーが付ける。名前だけで作れ、取り込み元につないでいないワークスペースでも使える。並べ替えられる
  - 各リポジトリに、取り込み元の入る先（GitHub のリポジトリなど）を1つまで結べる。同じ入る先を2つのリポジトリに結べない
  - タスクにだけ0〜1つ振る。振らなくてもよく、振っていないものは「リポジトリなし」と示す。ストーリーとエピックには振らず、親から引き継がない。複数のリポジトリにまたがる作業は、リポジトリごとにタスクを分ける
  - 起票の欄に一覧をボタンで並べ、1回押せば選べる。初期値は「なし」で、一覧が1つだけのワークスペースではそれを初期値にする。タスクの詳細と受信箱の行でも1回押して振り替えられる
  - 取り込んだタスクは、取り込んだときに、入る先が結ばれたリポジトリがあればそれを振る。結ばれていなければ「なし」にして、受信箱や詳細で選ぶ。後から結んでも、取り込み済みのタスクは変えない
  - バックログ、スプリント、受信箱、自分の今日の行とカードに、振ったリポジトリの名前を示す
  - リポジトリを削除したら、振っていたタスクは「なし」に戻す
  - 区分とは別の軸で、完了の記録には持たない
- 計上月: 区分に「月ごとに計上する」の属性を持たせる。この属性を持つ区分のタスクは、完了の記録に計上月を持つ。属性を切り替えても、すでにある完了の記録の計上月は変えない。既定は完了した月（ワークスペースのタイムゾーン）
- 今日やる: 担当者が自分のタスクに「今日やる」の印を付け、付けた日付とともに持つ。日付が変わると印は外れ、未完了のものは前日からの持ち越しとして示す。今日の画面には、この印のタスクと今日が期日のタスクを並べる
- 変更の履歴: タスク、ストーリー、エピックの属性の変更（列、ポイント、担当、期日、親、スプリント、リポジトリなど）と添付ファイルの追加と削除を、誰がいつ何をしたかで残し、それぞれの画面に出す。権限（ロール、管理者、招待、離脱）、配分、接続の登録と停止と削除、完了の記録の修正、削除も同じく残し、リーダーと管理者が見られる
  - 組織の単位の変更（組織の作成、停止、再開、管理者の指名、運用者の操作、ワークスペースの作成、終了、再開）は、組織の管理の画面に新しい順に50件ずつ出し（続きは「古い履歴を読む」で全部を読める）、管理者だけが見られる。運用者の操作は「運用者」とだけ出し、運用者のログインの ID は出さない
- 完了の記録: タスクを完了にした時点の完了日時、完了にした人、ポイント、担当、スプリント、区分、計上月を記録する。振り返りと請求はこの記録を使う
  - スプリントに入っていないタスクも完了にできる。このとき記録のスプリントは空のまま
  - 記録のスプリントは、完了したときに進行中だったスプリント。始まっていないスプリントに入っているタスクを完了にすると、そのスプリントから外れてスプリントの外の完了になり、記録のスプリントは空のまま（始まる前に終えた仕事でベロシティを膨らませない）
  - 未完了に戻すと記録を消し、もう一度完了にしたら新しく記録する
  - 完了したままでも、リーダー（管理者を含む）は記録のポイント、完了日時、計上月を直せる。直しても経験値は動かさない
- 積載量: メンバーごとに、スプリントと月の作業量を基準と並べて示す。本人は自分の基準と休みを登録し、全ワークスペースの合計を見られる
- 通知: ユーザーごとの画面内の通知一覧で、既読を持つ。既読にしてから90日たった通知は消す。メールや Slack には送らない。知らせるのは、取り込み元での完了と開き直し、取り込み元で見つからないタスク、自分の接続の取り込みの失敗、自分のタスクへのコメント（起票者と担当者へ）、担当への割り当て、討伐隊への割り振り、クリア報酬の変更、受け取った感謝、添付ファイルの合計が上限の80%を超えたこと（管理者へ）
- ゲームの仕組み: 「ゲームの仕組み」の節の内容（経験値、レイドの掲示、クリア報酬、討伐隊、受注、感謝、クリア時の演出）をすべて初版に入れる
- 画面の対象: PC のブラウザ。スマホでは表示が崩れない程度にとどめる
- アクセシビリティ: WCAG 2.2 AA を目安にする。色だけで伝えず、期日や超過には文字かアイコンを添える。ドラッグでの操作にはボタンとキーボードでの代わりを用意する。prefers-reduced-motion のときはクリアの演出を止める
- 言語: 画面は日本語だけ。文言は辞書にまとめ、後から英語を足せるようにする。ゲームの言葉とスクラムの言葉の切り替えも同じ辞書で扱う。README は日本語で書く

### 後回し

- 取り込み元をまたいだ紐付け: PR や課題の本文とタイトルにある参照から、別の取り込み元の課題と自動で関連付ける。PR のタスクは課題のタスクの親と区分を引き継ぎ、親が完了したストーリーなら引き継がない。課題どうし（Backlog の課題と GitHub の Issue など）は結び付けて、同じ作業が2件のタスクにならないようにする。参照の見つけ方と突き合わせ方（Backlog や Jira の課題キー、GitHub の `#12` など）は取り込み元の型が持つ。応答を保存しない組織でも動くよう、同期のときに参照だけを抜き出して持つ。それまでは受信箱で片方をアーカイブして扱う
- 取り込み元を足す: 課題管理の Jira、Asana、Notion、コード管理の GitLab、Bitbucket など。共通の型の実装を足して加える
- ログインの手段を足す: Microsoft など。共通の型の実装を足して加える
- 1つのアカウントに複数のログインの手段を結ぶ: ログインした状態で、自分の設定から別の手段を結ぶ。メールアドレスが同じでも自動では結ばない
- スマホ向けの画面: 今日と今週のタスク、受信箱、経験値とチームの目標を見られ、列の移動、起票、受信箱の仕分けができる。バックログの並べ替えと設定は PC で行う
- 実績の画面（週ごとの完了ポイントと平均）。完了日は初版から記録するので、後から画面だけ足せる
- スプリントのボス戦（スクラムの言葉ではバーンダウンチャート）。スプリントに入れたタスクの件数をボスの体力にし、完了したタスクの件数で削る。日ごとの残りの件数をグラフで出す。ポイントは使わない。討伐すると、そのスプリントに担当のタスクを持っていた全員にボーナスの経験値が入る
- GitHub リポジトリのディレクトリにある Markdown の取り込み（1ファイルを1タスクにする）。それまでは手で作るタスクで代える

## Non-Goals

- 取り込み元への書き戻し
- 取り込み元で完了したタスクを自動で完了にすること
- 他のタスク管理ツールからのデータ移行
- Cloudflare 以外の稼働先への対応（Docker などで自分で立てること）
- D1 以外の DB への対応
- メンバー間の順位付け
- 計画に対するスケジュールのずれ（日数）の管理。Scrum Guild は計画の量（積載量）と期日までを扱う

## 未決の論点

- 見積もりと実績の時間（予実）。ワークスペースごとに見積もりの単位をポイントか時間から選べ、タスクにかかった実績の時間も記録して、見積もりとの差を見られるようにする。経験値、レイドの報酬、ボス戦は時間に結び付けない。決めることは、入力の画面、時間で見積もるワークスペースでの積載量（換算比率を使わない）、記録の CSV の列、初版に入れるか後回しにするか

- GitHub リポジトリの Markdown の取り込み（後回し）が、取り込み元の共通の型に合うか。1ファイルを1項目とみなすときの不変の ID、手で作ったタスクとの関係。着手するときに決める
