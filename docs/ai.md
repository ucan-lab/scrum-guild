# AI でタスク管理を軽くする

状態: 案。決まったものは `requirements.md` と `data-model.md` に移す。

## ねらい

要件定義の目的にある「リーダーが詳細を書いたり、メンバーから聞き取って書き足したりする手間を減らす」を、ゲームの仕組みに加えて AI でも進める。AI は下書きを出すまでにとどめ、決めて書き込むのは人にする。

## できること

### 1. ストーリーをタスクに分ける

- エピックの画面で、ストーリーの「タスクに分ける」を押すと、ストーリーのタイトル、受け入れ基準、本文、エピックの本文から、タスクの案を出す。
- 案はタスクごとに、タイトル、決まった欄の下書き、ポイントの案、そう分けた理由を持つ。
- 案は一覧で示し、人が選んだり直したりしてから「この内容で作る」で作る。作ったタスクはストーリーの配下の末尾に置く。
- 配下にタスクがあるストーリーでも使え、すでにあるタスクと重ならない案だけを出す。

### 2. ポイントの案を出す

- タスクの詳細と計画の画面で、未見積もりのタスクにポイントの案を出す。計画の画面では未見積もりのものをまとめて出せる。
- 案の根拠に、同じワークスペースの完了の記録から似たタスクとそのポイントを数件示す。過去の記録が少ないうちは、根拠がないことを示す。
- ポイントは請求の根拠になるので、案を自動で書き込まない。人が選んで初めて振られる。

### 3. 議事録からストーリーを起こす

- バックログの画面の「議事録から起こす」で、議事録の文を貼り付けると、エピック、ストーリー（受け入れ基準を含む）、タスクの木の案を出す。
- すでにあるエピックやストーリーに入るものは、その下に足す案として示す。
- 案は木で示し、人が選んだり直したりしてから作る。作ったものはバックログの末尾に置く。
- 議事録の文は保存しない。残したいときは、作ったエピックやストーリーの本文に人が貼る。

### 4. 画面から Claude に頼む

- どの画面からも開けるアシスタントで、言葉で質問したり操作を頼んだりできる（形は下の「画面の形」）。
  - 質問の例: 「今のスプリントで遅れそうなタスクは」「田中さんの今月の積載量は」「このレイドの残りは」
  - 操作の例: 「このストーリーのタスクを全部今のスプリントに入れて」「期日が過ぎたタスクを一覧にして、担当に今日やるを付けるよう頼むコメントを書いて」
- アシスタントは、開いている画面（ワークスペース、エピック、スプリントなど）を前提として受け取る。開いているワークスペースのタイムゾーンの今日の日付も、この前提と一緒に、ユーザーのメッセージの側に添えて毎回渡す（システムプロンプトに入れると、毎日プロンプトキャッシュが切れるため）。
- アシスタントができる操作は、頼んだ人が画面でできる操作と同じ範囲だけにする。権限は API が検査し、AI のために別の権限を設けない。
- 読むだけの操作はそのまま行う。書き込む操作は、何をどう変えるかを確認の欄で示し、人が「実行」を押してから行う。まとめて変えるときは1回の確認で1つのトランザクションにする。
- 会話はブラウザの中にだけ持ち、DB に残さない。画面を閉じたら消える。

#### 画面の形（#12 で決めた。見本は `design/` の上の帯と、カタログの「AI のアシスタント」）

- 呼ぶ AI は、アプリの中のアシスタントの裏で動くモデル。組織の管理で送る先（Claude か OpenAI）を選べる。送る先を変えても、できることは変わらない。タスクを Claude Code や Codex に渡してリポジトリで作業させること、手元の AI から MCP で操作することは、アプリの中のアシスタントとは別で、`sg mcp`（下の「操作の定義を1か所に持つ」）が受け持つ。
- 上の帯の「アシスタントに頼む」か `Ctrl+K`（Mac は `⌘K`）で、画面の上にパレットを開いて頼む。続けて話したいときだけ「横の欄で続ける」で右の横の欄へ移す。短い操作はパレットで済み、長いやり取りは横の欄で画面を見ながら続けられる。
- 横の欄は、本文を寄せても潰れない広い画面（1500px 以上）では本文を左へ寄せ、それより狭いと右に重ねる。タスクの詳細の引き出しは横の欄の上に出る。
- 入力の下に、前提として渡す画面を札で出す（タスクの詳細を開いていればそのタスク）。札の × で外せる。一覧で選んだ行を渡すのは後回し。
- 頼みごとの例を、入力が空のときに出す。
- 答えは流して出す。道具を呼んでいる間は「タスクを読んでいます」のように何をしているかを1行ずつ出す。答えに出たタスクは押すと詳細が開く。
- 変える前の確認は、行ごとに「タスク、項目、今、変えた後」を出し、行ごとに外せる。5 件を超えたら先頭の 5 件だけを出して残りを畳み、残りを開くまで実行できない（見ていない行を変えない）。ボタンは「N 件を実行する」で、選んだ行を1回で変える。取り消しは持たない。実行した後は、変えた件数と、変更の履歴にあなたの操作として AI を通した印付きで残ることを出す。変更の履歴の画面の印は、見本ではまだ出していない。
- できないとき: 権限が足りない頼みごとは、できない理由と誰に頼めばできるかを答える。失敗したときは、何も変えていないことと、もう一度頼むボタンを出す。往復の上限（下の「Claude の呼び出し」）に達したときも、途中までに分かったこと（流れ終えた文）、その頼みでは何も書き込んでいないこと、もう一度頼むボタンを出す。アシスタントは書き込みを実行せず、人が「実行」を押した後にだけ書き込むので、上限で止まった頼みは何も書き込んでいない。ボタンは、失敗したときも上限のときも、直前の頼みだけを1往復目から送り直し（会話の前の頼みは再実行しない）、上限のときは「頼みを絞ると届きやすい」を添える。上限の表示は、見本ではまだ出していない。組織で無効なときと今月の上限に達したときは、入力を止めて理由を出す（無効なら、管理者には組織の管理への道を添える）。
- 送る先と、会話を保存しないことを、いつも下に出す。
- 呼び名は「アシスタント」。操作の色は押せる所だけに使い、アシスタントの名前や考え中の印は文字と形で示す。現代風でも光らせない（光らせるのはゲームの要所だけ）。

## 作りの方針

### 操作の定義を1か所に持つ

アシスタントの道具（tool use）、公開する API、MCP（`ideas.md` の「外部からの操作」）を、同じ操作の定義から作る。操作ごとに、名前、説明（使うときと使わないとき）、入力の型、読むだけか書き込むか、要る権限を1つの定義に持ち、Hono の API、アシスタントの道具、MCP の道具を、その定義から作る。こうすれば、画面でできることとアシスタントにできることがずれない。

手元の AI 向けの MCP は、`sg mcp`（`cli/`）が stdio で提供する。道具は定義を取り込まず、API の `operation-list` が返す操作の一覧（名前、説明、入力の JSON Schema、`mode`）から、`tools/list` のたびに作る。サーバーに操作の定義を足すと、MCP のコードを書かずに道具が増える。呼び出しは CLI と同じ経路（トークン付きの API）で、MCP のために別の権限を設けない。使い方は `development.md` の「CLI（sg）」。遠隔の MCP は別に考える。

道具が増えるほどモデルは道具を選び間違えるので、定義には次の項目を必須で持たせる。

- 説明は「使うとき」と「使わないとき」の別項目とし、空を許さない。
- 入力の型は厳密にする。対象を指す欄は ID、日付は `YYYY-MM-DD`、状態や区分は決まった選択肢、数は数値の型にして、曖昧な文字列は通さない。題、本文、コメントのように文そのものを渡す欄だけ自由な文を受け、長さの上限を型に持つ。
- 相対的な日付（来週、明日）は、頼みの側で渡された今日の日付からモデルが絶対的な日付に直してから渡す。

### Claude の呼び出し

- Worker から Anthropic の Claude API を直接呼ぶ。TypeScript の公式 SDK（`@anthropic-ai/sdk`）を使う。
- 送る先は組織の管理で選べる形を見本にした（Claude か OpenAI）。OpenAI も初版で出すかは「決めること」に残した。出すなら、この節の構造化出力、プロンプトキャッシュ、道具の定義を送る先ごとの差し替えにし、下の要件との当たりに OpenAI を足す。
- モデルは `wrangler.jsonc` の設定に持つ。既定は `claude-opus-5-5`。機能ごとに変えられるようにし、案を出すだけの軽い処理を安いモデル（`claude-haiku-5-5` など）に替えるかは、下の「評価」で決める。
- モデル名は、公式のモデル一覧の「Claude API ID」にある正式な名前を設定に明示して固定する。4.6 世代以降の日付のない ID（`claude-opus-5-5` など）はそれ自体が固定されたスナップショットで、それより前のモデルは日付付きの ID（`claude-haiku-4-5-20251001` など）を書く。4.6 より前のモデルの日付のない名前は、日付付きの ID を指す別名で、指し先が動きうるので使わない。変更は下の「評価」を通したときだけ行う。
- モデルの廃止は、公開済みのモデルについて少なくとも 60 日前にメールとドキュメントで告知され、廃止後の要求は失敗する。評価の対象の機能（1 から 3）は、告知で推奨された置き換えのモデルを「評価」で確かめてから設定を替える。アシスタントは評価が未定なので、告知を受けたら廃止の期日までに置き換えを決める。
- タスクの案、ポイントの案、議事録からの木は、構造化出力（`output_config.format`）で型の決まった JSON を受け取り、Worker で検証してから画面に返す。
- アシスタントは tool use の往復を Worker で回し、応答は画面へストリーミングで流す。往復には上限と終了条件を置く。
  - 1 往復は、モデルを 1 回呼ぶこと。同時の道具の呼び出しは 1 往復にまとめる。
  - 終了条件は次の4つで、どれかに着いたら止める。
    - 答えを返した。
    - 書き込みの確認待ちに着いた。書き込みの案が出た往復の終わりで止め、同じ往復の案をまとめて確認の欄に出す。その往復が上限に着いていても確認待ちを優先し、同じ往復の読む道具は実行しない。「実行」の後にモデルは再開しない。後の書き込みが前の結果に依存するなら、人が頼み直す。
    - 直せない失敗。API の失敗、道具の内部エラー、同じ入力で 2 回続けた失敗。入力の検証の失敗、対象が見つからない、権限不足はモデルに返して続ける（権限不足は、できない理由を答えさせる）。
    - 上限。往復 8 回と、1 回の頼みの経過時間 60 秒の案で、どちらかに先に着いたら止める。経過時間は往復の間で判定し、残りの時間を次のモデル呼び出しのタイムアウトにして、呼び出しの途中でも打ち切る。
  - 上限の値は `wrangler.jsonc` の `vars` に置く。案の値はベータの利用で見直す。トークンの上限は、下の「費用の上限」の月の上限が受け持つ。
  - 上限で止まるまでに使ったトークンも、通常と同じに記録して月の上限に数える。
- システムプロンプトと道具の定義は固定にし、プロンプトキャッシュを効かせる。
- API キーはシークレットに持ち、運用の手順書のシークレットの一覧に足す。

### 評価

モデルやプロンプトを替えて良くなったか悪くなったかを、機能ごとの評価セットで判定する。

- 評価セットは機能ごとに持つ。対象は「できること」の 1 から 3 だけで、機能ごとに約 20 件とする。1 件は入力、期待する出力、合格の基準を持ち、データはすべて架空にする。
- アシスタント（4）の評価は未定で、アシスタントのモデルは当面替えない。
- 採点の基本は機械判定。型、ポイントの範囲、既存タスクとの重複など、機械で確かめられるものは機械で判定する。理由や下書きの文のように良し悪しが要るものだけ、別のモデルが合格の基準に照らして採点する。採点役のモデルも正式な名前で固定し、替えるときは評価を取り直す。
- 全件を回すのは、モデル、プロンプト、道具の定義、構造化出力の型の定義のどれかを変えたときと、モデルの廃止の告知で置き換えるとき。
- 評価を通す条件は、通過した件数が変更前から 1 件までの低下で、かつ通過率が下限の 90%（約 20 件なら 18 件）を割らないこと。変更前の件数は、変更の直前に同じ評価セットで測った結果とする。
- モデルを安いものに替えるのは、1 機能で 1 ステップずつ。1 ステップは、その機能のモデル名を 1 回替えることで、替えるたびに評価を通す。

### 取り込んだ内容は指示として扱わない

取り込んだ GitHub の Issue や PR には、チームの外の人が書いた文が入る。それを AI に渡すと、文に紛れた指示で AI が意図しない操作をしようとすることがある（プロンプトインジェクション）。次で防ぐ。

- 書き込む操作は必ず人の確認を挟む（上の「画面から Claude に頼む」）。
- アシスタントにウェブの取得など外へ出る道具を持たせない。
- 取り込んだ本文はデータとして囲んで渡し、システムプロンプトで指示として扱わないよう伝える。

### 費用の上限

- 組織ごとに月の利用の上限（トークン数）を持ち、超えたらその月は AI の機能を止めて知らせる。上限の値は運用者が組織ごとに決める。
- ユーザーごとのレート制限を設ける（要件定義の「アプリ側のレート制限」に AI を足す）。
- 呼び出しごとに、組織、ユーザー、ワークスペース、機能、モデル、入力と出力のトークン数、日時を記録する。中身（プロンプトと応答）は記録しない。

## 要件定義と当たるところ

| 要件定義の決まり | 当たり方と案 |
| --- | --- |
| 外部への通信は取り込み元とログインの手段（GitHub、Google）だけ | Anthropic の API が加わる（送る先に OpenAI も出すなら OpenAI も）。要件を「AI の機能を有効にした組織では、選んだ送る先にも送る」に改める |
| 顧客のデータを預かる体制が未決（`business.md`） | タスクや議事録の中身を Anthropic に送ることになる。管理者が組織の設定で AI の機能を有効にするまで使えないようにし、有効にする画面で送る先と送る内容を示す。Anthropic の API でのデータの扱い（学習に使うか、保持の期間）は採用の前に規約で確かめ、利用規約とプライバシーポリシーに書く |
| 起票と詳細の経験値は、メンバーが自分から書くことを促すためのもの | AI の案から作ったタスクにも経験値を付けると、案を出して作るだけで経験値が貯まる。案: AI の案から作ったタスクには起票の経験値を付けない。決まった欄を AI の下書きのまま埋めたものは詳細の経験値を付けず、人が書き直した欄だけを数える。完了の経験値は変えない |
| ポイントは見積もりと請求の根拠 | 案を自動で書き込まない（上の「ポイントの案を出す」） |
| 変更の履歴は誰がいつ何を変えたか | AI を通した操作は、頼んだ人の操作として残し、AI を通したことの印を添える |

## 画面に足すもの（案）

- 画面の上に重ねるもの: アシスタントのパレットと横の欄。上の帯のボタンか `Ctrl+K` で開く（見本を作った）
- エピックの画面: ストーリーの「タスクに分ける」と案の一覧
- タスクの詳細、計画: ポイントの案
- バックログ: 「議事録から起こす」のダイアログと案の木
- 組織の設定: AI の機能を有効にする欄、送る先（Claude か OpenAI）、送る内容の説明、今月の利用量（見本を作った）
- 運用: 組織ごとの AI の利用の上限と今月の利用量

## 値段

AI の費用は使った分だけかかる。組織ごとの定額（`business.md`）に月の上限まで含めるか、AI を別の段にするかを、ベータで実際の利用量を見て決める。

## 進め方の案

1. 初版の土台で、操作の定義を1か所に持つ作りにしておく（後から道具や MCP を足せるように）
2. 「ストーリーをタスクに分ける」と「議事録から起こす」。案を出して人が選ぶ形で、書き込みの危うさが小さい
3. 「ポイントの案を出す」。完了の記録が貯まってから効く
4. アシスタント。操作の定義が揃い、確認の欄の作りが固まってから
